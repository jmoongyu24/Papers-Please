## 0. 이 프로젝트가 풀려는 문제

논문을 찾으려는 사람은 학부생부터 대학원생까지 다양하지만, 공통적으로 겪는 어려움이 있다.
**자기가 읽고 싶은 논문이 실제로 어떤 검색어로 쓰여 있는지 잘 모른다**는 점이다.

- 그 분야를 잘 모르는 사람은 아예 **평소 쓰는 일상적인 말**로 검색한다.
  "사진 보고 글로 설명해주는 인공지능은 어떻게 만들어?" 같은 식이다.
- 어느 정도 아는 사람도 **전문 용어를 쓰긴 하지만 그 논문이 실제로 쓰는 정확한 용어는
  아닌** 경우가 많다. "이미지 설명 생성 모델"이라고 쳤는데 논문은 `image captioning`,
  `vision-language model` 이라고 쓰는 식이다.

어느 경우든 사용자가 친 검색어와 논문이 실제로 쓰는 용어가 어긋나면 원하는 논문이 안 나온다.

### 실측이 다시 정의한 핵심 가치 (정직한 기록)

처음의 핵심 아이디어는 "**입력한 말 → 의도 → 중간 개념 → 정확한 전문 용어** 순서로 단계적으로
변환하면 검색이 계단처럼 좋아진다" 였다. **이 가설은 세 번 검증해서 세 번 다 반증됐다.**

| 구간 (옛 시험용 300문항) | 변환 안 함 | 계층 변환 | 검색보상 학습 모델 |
|---|---|---|---|
| 영어 질문 | **0.327** | 0.259 | 0.354 (차이 불확실) |
| 한국어 질문 | **0.013** | 0.183 | **0.333** (25배, 확실) |

- **영어 질문에서는 어떤 변환기도 기준선을 확실하게 넘지 못한다.** 이미 논문 어휘와 겹치는
  영어 질문은 변환이 오히려 신호를 흐린다.
- **가치는 전부 한국어에서 나온다.** 한국어를 그대로 arXiv 에 넣으면 **88.2% 가 결과 0건**이다
  (arXiv 가 한글을 색인하지 않는다). 변환이 이 구멍을 메운다.
- **성능을 만든 것은 계층 구조가 아니라 '검색 성공을 보상으로 삼은 학습'이다.**

그리고 2026-08-11 에 **두 번째 축**이 생겼다. 논문 71만 편을 통째로 임베딩해 **뜻으로 찾는
로컬 의미 검색**을 붙였더니, 변환기를 쓰지 않고 원본 질문을 그대로 넣어도 옛 전체 파이프라인보다
잘 찾았다. 이것이 지금 성능의 대부분을 만든다(ISSUE #29).

### 그래서 이 시스템의 가치는 세 축이다

| 축 | 내용 | 검증 상태 |
|---|---|---|
| **(A) 언어 다리** | arXiv 가 아예 검색할 수 없는 한국어 질문을, **실제 검색 성공을 보상으로 학습한** 영어 학술 용어로 건너게 한다 | 확정 (25배) |
| **(B) 뜻으로 찾기** | 글자가 안 맞아도 뜻이 맞으면 찾는다. 논문 71만 편 로컬 의미 색인 + 교차 인코더 재정렬 | 확정 (+0.243) |
| **(C) 과정 보여주기** | 변환 과정(의도→개념→용어)을 보여 줘 "내 말이 이런 전문 용어로 바뀌었구나"를 이해시킨다 | **성능 향상 수단이 아니라 설명 기능이다. 이 점을 감추지 않는다** |

### 이번 단계에서 만들 것

> **사용자가 입력한 검색어로 실제로 존재하는 논문의 제목과 초록을 찾아 보여준다.**

찾은 논문을 언어 모델이 요약해 답변을 만들어 주는 기능은 이번에는 하지 않는다.
다만 **추천 이유를 붙이는 것**(이 논문이 왜 당신 질문에 맞는지)까지는 만들었다.

### 지켜야 할 조건

| 조건 | 무슨 뜻인가 |
|---|---|
| 로컬에서 실행 | 서비스가 돌 때 유료 인공지능 서비스(OpenAI)에 의존하지 않고 **내 컴퓨터 안에서** 언어 모델이 돌아야 한다 |
| 배포 가능 | 다른 사람이 명령어 한 줄로 설치·실행할 수 있어야 한다 |
| 오픈소스 공개 | GitHub 공개 + 자유 라이선스 |

> 유료 서비스(OpenAI)는 **평가용 데이터를 미리 만들 때만** 쓴다.
> 실제 서비스가 돌 때는 쓰지 않으므로 위 조건과 충돌하지 않는다.

## 1. 왜 '평가 준비'를 먼저 했는가

이 프로젝트의 핵심 주장은 "**검색어를 변환하면 검색이 더 잘 된다**" 이다.
"더 잘 된다"를 증명하려면 **무엇을 기준으로 얼마나 좋아졌는지 숫자로 재는 도구**가 먼저
있어야 한다. 그래서 ① 평가용 정답지와 ② 점수 매기는 방법을 먼저 만들었다.

이 판단은 옳았다. 이 프로젝트는 **잘못된 결론을 스스로 찾아내 두 번 철회**했는데
(ISSUE #22, #29), 재는 도구가 없었다면 둘 다 그대로 졸업작품 보고서에 들어갔을 것이다.

## 2. 지금의 시스템 구조

```
사용자 질문 (한국어 또는 영어, 일상어 또는 전문어)
   │
   ├─ [특정 논문 지목인가?] paper_resolver — "트랜스포머 최초 논문" 같은 요청을 따로 처리
   │
   ├─ 쿼리 변환기 (Qwen3-4B + LoRA, 검색 성공 보상 학습)
   │     └→ 검색 방식별 검색어 3종 (sparse / dense / arxiv)
   │
   ├─ 채널 A : arXiv 실시간 키워드 검색       ← 최신성·범위 담당
   └─ 채널 B : 로컬 의미 검색 71만 편          ← 정확도 담당
          │
          ▼
     순위 합치기 (RRF) — 점수가 아니라 등수를 더한다
          │
          ▼
     교차 인코더 재정렬 — 질문과 논문을 함께 읽고 다시 줄 세운다
          │
          ▼
     추천 에이전트 — 관련도·이유·종합 요약을 붙인다
          │
          ▼
     화면에 10편
```

### 모듈 넷과 코드 위치

| 모듈 | 코드 | 파일 수 |
|---|---|---|
| ① 쿼리 변환 | `src/rewriter/` | 4 |
| ② 검색 | `src/retrieval/` | 4 |
| ③ 성능 평가 | `evaluation/` | 4 |
| ④ 웹 화면 | `app.py` | 1 |
| 추천 에이전트 | `src/recommend_agent/` | 1 |
| 학습 | `training/` | 2 |
| 공통 부품 | `src/config.py` · `src/schemas.py` · `src/utils.py` | 3 |

**규칙: 디렉터리마다 코드 파일은 4개를 넘지 않는다.** 기능마다 파일을 새로 만들면
"뭐가 뭔지 모르는" 상태가 된다(2026-08-14 에 63개를 22개로 줄이며 세운 규칙).
새 기능은 **되도록 기존 파일 안에** 넣는다.

### 서비스 경로와 실험 경로를 구분할 것

| | 서비스 경로 (`app.py` 가 쓰는 것) | 실험 경로 (평가 전용) |
|---|---|---|
| 변환기 | `dpo` (학습한 모델) | `passthrough` · `hierarchical` · `single_step` · `hyde` 도 비교군으로 |
| 검색 | 로컬 의미 검색 + arXiv 실시간 | 같음 |
| 재정렬 | 교차 인코더 | 임베딩 유사도도 비교군으로 |

**실험 경로에서만 나오는 숫자를 서비스 성능이라고 말하면 안 된다.** 이 프로젝트는 로컬
평가 0.74 와 실제 서비스 0.15 의 격차를 겪은 적이 있다(ISSUE #10).

## 3. 논문 모음(코퍼스)

### 로컬 색인 — 71만 편

- Kaggle arXiv 스냅샷에서 **cs·stat.ML·eess 계열 + 2021년 이후** 조건에 해당하는 논문을
  **전부** 뽑았다. **716,183편**, `data/corpus/corpus-cs2021.jsonl`, 1.03GB.
- 임베딩 `data/embeddings/cs2021.*` — bge-m3(다국어), 2.93GB.
- **표본이 아니라 모집단 전체를 색인했다.** 그래서 표본을 어떻게 뽑았는지에 따른 왜곡 없이
  실력을 잰다. 건초더미를 옛 3만 편의 24배로 키운 것이므로 **더 어려운 조건**이다.

### 실시간 arXiv 검색도 곁들인다

로컬 색인은 만든 시점 이후의 논문을 모른다. 어제 올라온 논문, 다른 분야 논문은 arXiv
실시간 검색이 담당한다. **arXiv 채널의 역할은 정확도가 아니라 최신성과 범위다.**

주의할 점 (코드로 직접 확인한 사실):
- arXiv 는 검색어 1개에 논문 여러 개를 순위대로 돌려준다.
- **요청당 3초 간격 · 단일 연결**을 지켜야 한다. 안 지키면 429/503 이 난다(ISSUE #12).
- `page_size=100` 이라 **top-k 를 줄여도 호출 수는 안 줄어든다.** 줄일 것은 호출 횟수다.
- 한글을 색인하지 않는다. 한국어를 그대로 넣으면 88.2% 가 0건이다.

### arXiv 정책 준수 (`ARXIV_API_POLICY.md`)

- 메타데이터(제목·초록·번호)는 CC0 라 저장해도 된다. **논문 원문은 우리가 제공하면 안 된다.**
- **출처 표기 + "arXiv 의 후원·보증을 받지 않았다"는 문구가 화면에 있어야 한다. 아직 없다.**

## 4. 성능을 무엇과, 어떻게 비교하는가

### 기준선을 반드시 함께 잰다

핵심 주장이 "변환하면 좋아진다"이므로, **변환하지 않은 값(passthrough)** 이 없으면 주장이
검증되지 않는다. 모든 비교에 기준선을 포함한다.

### 지표 두 개를 나란히 본다

| 지표 | 무엇을 재나 | 한계 |
|---|---|---|
| Recall@10 | "질문을 만든 그 논문 1편"이 상위 10편에 들어왔나 | 다른 좋은 논문을 1등에 올려도 0점이다 |
| nDCG@10 | 등급 정답지로 "좋은 논문을 위에 올렸나" | 등급 판정이 필요해 만드는 데 돈이 든다 |

두 숫자가 크게 갈리면 그 차이가 **지표의 한계이지 시스템의 실패가 아니다.**

### 통계 검정을 반드시 붙인다

같은 질문끼리 짝지어 부트스트랩 검정을 돌린다. **p 가 0.05 보다 크면 "차이가 없다"가 아니라
"있는지 없는지 모른다"** 이다. 모르는 차이를 근거로 설정을 고르면 시험지만 소모된다 —
실제로 p=0.889 인 차이를 보고 설정을 골랐다가 시험지를 태운 적이 있다(ISSUE #25).

### 개발용과 시험용을 섞지 않는다

- **개발용(`data/eval/dev.jsonl`)**: 설정을 바꿔 가며 탐색하는 것은 전부 여기서.
- **시험용(`data/eval/test.jsonl`)**: 확정 판정에만. 이걸 보면서 설정을 고르면 시험지가 탄다.

## 5. 남은 계획 (우선순위 순)

### 1순위 — 새 평가셋으로 기준선부터 다시 세운다

지금 인용할 수 있는 숫자가 하나도 없다. 옛 평가셋의 값은 전부 폐기된 시험지에서 잰 것이고,
새 평가셋에서는 아직 아무것도 안 쟀다. **가장 싸고 가장 급하다.**

### 2순위 — 두 채널을 합치는 것이 실제로 이득인지 판정한다

옛 평가셋에서 이미 "+0.003, p=0.889 로 잡음"이 나왔다. 새 평가셋에서도 같으면 **구조를
크게 단순화할 수 있다** — arXiv 호출이 사라지면 3초 제한도, 호출 실패도, 대기 시간도 없어진다.

### 3순위 — 서비스 품질

1. 응답 시간 실측·확정 (사람은 30초를 넘으면 떠난다)
2. **arXiv 정책 표기** — 없으면 공개할 수 없다
3. 화면 재구성 (ISSUE #11)
4. "못 찾았다"고 말할 수 있게 하기 — 의미 검색은 항상 10편을 채워 돌려준다
5. docker 배포 설정 (지금 설정은 3만 편 시절 기준이라 다시 짜야 한다)

### 4순위 — 마무리

`pyproject.toml`, 라이선스(Apache-2.0), 영문 README, 학습 가중치를 HuggingFace Hub 로 배포.

### 하지 않기로 한 것

| 항목 | 이유 |
|---|---|
| Elasticsearch 색인 | 로컬 의미 색인 + arXiv 실시간으로 충분 |
| 어휘 조회 · 상용구 필터 | 편향이었다 (ISSUE #22). 코드 삭제 |
| 검색어 용어 손질(term_repair) | 모든 K 에서 성능이 떨어졌다 (ISSUE #33). 코드 삭제 |
| 정답 논문에서 라벨 뽑아 재학습 | 처음 보는 논문의 고유 용어는 유추 불가 (ISSUE #17) |
| 조회 코퍼스 확대 | 2만 편에서 포화 |
| 후보 깊이 1000 | 기대 이득 +0.005~0.012 인데 재정렬 비용 3.3배 |
| 답변 생성(RAG 요약) | 이번 범위 밖 |

## 6. 예상되는 어려움과 대비책

| 어려움 | 대비 |
|---|---|
| **잘못된 결론을 성과로 착각한다** | 이미 두 번 겪었다. ISSUE #23 점검표를 실험 전에 읽는다 |
| GPU 16GB 에 모델 네 개가 안 들어간다 | 같은 모델을 두 벌 올리지 않고, 임베더·재정렬은 fp16. **조용히 CPU 로 밀리는 것**이 가장 위험하다 |
| 재정렬이 느리다 | 후보 수에 비례한다. 깊이를 늘리기 전에 응답 시간을 먼저 잰다 |
| arXiv 호출 제한 | 3초 간격 + 지수 백오프 + 디스크 캐싱 |
| 시험지를 태운다 | 탐색은 개발용에서만. 시험용은 확정 판정 전용 |
| 색인과 코퍼스의 짝이 어긋난다 | 오류 없이 엉뚱한 논문을 읽는다. 크기 지문 + 표본 대조 + 단위 테스트로 막았다 |

| 의미 검색 (dense) | 임베딩끼리 견줘 **뜻으로** 찾는 검색. 글자가 달라도 찾는다 |
| 단어 일치 검색 (sparse) | 같은 낱말이 나오는지로 찾는 검색. arXiv 키워드 검색이 이쪽이다 |
| RRF | 여러 검색 결과를 **점수가 아니라 등수**로 합치는 방법 |
| 재정렬 (rerank) | 넓게 가져온 후보를 다시 줄 세우는 단계 |
| 교차 인코더 | 질문과 논문을 **함께** 읽어 관련도를 매기는 모델. 느리지만 정확하다 |
| LoRA | 큰 모델은 얼려 두고 작은 보조 행렬만 학습하는 방법 |
| SFT | 지도 미세조정. "이게 정답이다"를 예시로 보여 준다 |
| DPO | 선호 학습. "이게 저것보다 낫다"를 쌍으로 보여 준다 |
| Recall@K | 상위 K편 안에 정답이 들어온 비율 |
| nDCG@K | 상위 K편이 얼마나 만족스러운가. 등급 정답지가 있어야 잰다 |
| 후보 상한 | 후보 집합 안에 정답이 들어 있는 비율. 재정렬로도 이 값을 넘을 수 없다 |
| 부트스트랩 | 표본을 다시 뽑기를 반복해 "이 차이가 우연인가"를 재는 방법 |
