## 0. 이 프로젝트가 풀려는 문제

논문을 찾으려는 사람은 학부생부터 대학원생까지 다양하지만, 공통적으로 겪는 어려움이
있습니다. **자기가 읽고 싶은 논문이 실제로 어떤 검색어(키워드)로 쓰여 있는지 잘 모른다**는
점입니다.

- 그 분야를 잘 모르는 사람(예: 학부생)은 아예 **평소 쓰는 일상적인 말**로 검색합니다.
  예를 들면 "사진 보고 글로 설명해주는 인공지능은 어떻게 만들어?" 같은 식입니다.
- 어느 정도 아는 사람(예: 대학원생)도, **전문 용어를 쓰긴 하지만 그 논문이 실제로 쓰는
  정확한 용어는 아닌** 경우가 많습니다. 예를 들어 "이미지 설명 생성 모델"이라고 쳤는데,
  정작 논문은 "image captioning", "vision-language model"이라는 용어를 쓰는 식입니다.

즉, 사용자가 입력하는 검색어에는 일상어뿐 아니라 **부정확하거나 덜 다듬어진 전문 용어가
섞여 들어올 수 있습니다.** 어느 경우든, 사용자가 친 검색어와 논문이 실제로 쓰는 전문
용어가 어긋나면 원하는 논문이 잘 나오지 않습니다. (이렇게 잘 모르는 사용자를 통틀어
'비전문가'라고 부르지만, 대학원생처럼 어느 정도 아는 사람도 포함하는 넓은 뜻입니다.)

**핵심 아이디어:** 큰 언어 모델(사람의 말을 이해하고 만들어내는 인공지능)을 이용해,
사용자가 입력한 검색어를 **그 분야에서 실제로 통용되는 정확한 영어 학술 용어로 매핑**해
준 다음 검색하면, 원하는 논문이 훨씬 잘 나올 것이다.

이 변환은 **입력한 말 → 의도 → 중간 개념 → 정확한 전문 용어** 순서로 단계적으로 추론해
만들며(이를 '계층적/단계적 변환'이라 부름), 그 과정을 사용자에게 그대로 보여 준다.

> **2026-08-07 실측으로 다시 정의한 부분 (정직한 기록 — 두 번째 수정)**
>
> 시험용 질문 300개 전체를 실제 서비스 경로(arXiv 실시간)로 재서, 처음으로
> **변환을 아예 안 한 기준선**과 비교했다. 그 결과 위 문단의 "(A) 비전문가·다국어"라는
> 표현이 정확하지 않음이 드러났다.
>
> | 구간 | 변환 안 함 | 계층 변환 | 최종 학습 모델 |
> |---|---|---|---|
> | 영어 질문 (147개) | **0.327** | 0.259 | 0.354 (차이 불확실) |
> | 한국어 질문 (153개) | **0.013** | 0.183 | **0.333** (25배, 확실) |
>
> - **영어 질문에서는 어떤 변환기도 기준선을 확실하게 넘지 못한다.** 이미 논문 어휘와
>   겹치는 영어 질문은 변환이 오히려 신호를 흐린다.
> - **가치는 전부 한국어에서 나온다.** 한국어를 그대로 arXiv에 넣으면 **88.2%가 결과 0건**이다
>   (arXiv가 한글을 색인하지 않기 때문). 변환이 이 구멍을 메운다.
> - **계층 구조 자체의 이득은 세 번 검증해서 세 번 다 안 나왔다.** 성능을 만드는 것은
>   계층이 아니라 **검색 성공을 보상으로 삼은 학습**이다.
>
> **따라서 이 시스템의 가치는 다음 두 축으로 서술한다.**
> - **(A) 성능** — 한국어처럼 **arXiv가 아예 검색할 수 없는 언어의 질문을, 검색 가능한 영어
>   학술 용어로 건너게 한다.** 이때 필요한 어휘는 사람이 정한 것이 아니라 **실제 검색 성공을
>   보상으로 학습**해서 얻는다.
> - **(B) 사용자 경험** — 변환 과정(의도→개념→용어)을 보여줘 "내 말이 이런 전문 용어로
>   바뀌었구나"를 이해시킨다. 단 이것은 **검색 성능 향상 수단이 아니라 설명 기능**이며,
>   그 점을 감추지 않는다.
>
> 근거와 상세는 [ISSUE.md](ISSUE.md) #13, 원자료는 `results/test300_*.jsonl`.

### 이번 단계에서 만들 것 (목표를 좁힘)

이번 프로젝트의 목표는 다음 한 문장으로 정리됩니다.

> **사용자가 입력한 검색어를 전문 용어로 다듬어 검색해서, 실제로 존재하는 논문의
> 제목과 초록을 찾아 보여준다.**

- 여기까지가 이번 목표입니다. 찾은 논문 내용을 언어 모델이 다시 요약하거나 가공해서
  답변을 만들어 주는 기능(예: "이 논문들을 종합하면…")은 **이번에는 하지 않고 나중에**
  합니다.
- 그리고 검색 기능을 본격적으로 만들기 전에, **성능을 객관적으로 측정할 준비**
  (평가용 데이터 만들기 + 평가 방법 정하기)를 **먼저** 합니다. 자세한 이유는 1절에
  적었습니다.

### 지켜야 할 조건

| 조건 | 무슨 뜻인가 |
|---|---|
| 로컬에서 실행 | 서비스를 실제로 돌릴 때, 인터넷의 유료 인공지능 서비스(예: OpenAI)에 의존하지 않고 **내 컴퓨터 안에서** 언어 모델이 돌아가야 한다 |
| 배포 가능 | 다른 사람이 명령어 한 줄로 전체 프로그램을 설치·실행할 수 있어야 한다 |
| 오픈소스 공개 | GitHub에 코드를 공개한다. 누구나 자유롭게 쓸 수 있는 라이선스를 붙인다 |

> 참고: 유료 인공지능 서비스(OpenAI)는 **평가용 데이터를 미리 만들 때만** 씁니다.
> 실제 서비스가 돌아갈 때는 쓰지 않으므로 위 '로컬 실행' 조건과 충돌하지 않습니다.

## 1. 진행 순서 — 왜 '평가 준비'를 먼저 하는가

보통은 "일단 만들고 나중에 평가하자"고 생각하기 쉽지만, 이 프로젝트에서는 순서를
뒤집습니다. 이유는 다음과 같습니다.

- 이 프로젝트의 핵심 주장은 "**쿼리(검색어)를 변환하면 검색이 더 잘 된다**" 입니다.
  "더 잘 된다"를 증명하려면, **무엇을 기준으로 얼마나 좋아졌는지 숫자로 재는 도구**가
  반드시 있어야 합니다. 이 도구가 없으면, 아무리 좋은 변환기를 만들어도 그게 정말
  좋은지 말할 수 없습니다.
- 그래서 **① 평가용 정답지(어떤 질문에 어떤 논문이 정답인지 모아둔 데이터)** 와
  **② 점수를 매기는 방법**을 먼저 만듭니다. 이게 준비되면, 그 다음부터는 검색기와
  변환기를 만들 때마다 곧바로 "점수가 올랐는지"를 확인하며 개선할 수 있습니다.

정리한 전체 순서:

| 단계 | 하는 일 | 왜 이 순서인가 |
|---|---|---|
| 1단계 | 프로젝트 뼈대 정리 + **논문 모음(코퍼스) 만들기** | 평가 정답지도, 검색도 전부 이 논문 모음 위에서 이뤄지므로 가장 먼저 필요 |
| 2단계 | **평가용 데이터 만들기 + 평가 방법 마련** ← 지금 집중할 곳 | 위에서 설명한 이유. "얼마나 좋아졌나"를 잴 자를 먼저 만든다 |
| 3단계 | 검색 모듈 만들기 (세 가지 검색 방식) | 평가할 대상(검색기)이 있어야 점수를 낼 수 있다 |
| 4단계 | 쿼리 변환 모듈 만들기 + **첫 성능 비교표** | 변환 전/후를 비교하는 첫 숫자가 나오는 지점 |
| 5단계 | 변환 방식 개선 + 본격 비교 실험 | 첫 숫자를 기준으로 계속 개선 |
| 6단계 | 웹 화면 만들기 | 사람에게 보여줄 데모 |
| 7단계 | 마무리 (실사용자 평가, 보고서) | |

**2단계까지 마치면, 이후 언제든 "동작하는 시스템 + 성능 숫자"를 가질 수 있는 상태가
됩니다.** 일정이 밀리더라도 졸업작품으로 성립하는 상태를 최대한 일찍 확보하는 것이
이 순서의 목적입니다.

## 2. 시스템의 큰 그림 (모듈 4개)

프로그램은 크게 네 덩어리(모듈)로 나뉩니다. 각 모듈이 어떤 일을 하고 서로 어떻게
연결되는지 그림으로 보면:

```
             사용자가 입력한 질문(검색어)
                        │
                        ▼
        ┌───────────────────────────────┐
        │  ① 쿼리 변환 모듈               │   일상어 → 중간 개념 → 전문 용어
        │  (내 컴퓨터에서 도는 언어 모델)  │   단계별로 바꿈
        └───────────────┬───────────────┘
                        │ 변환된 전문 검색어
                        ▼
        ┌───────────────────────────────┐
        │  ② 검색 모듈                    │   논문 모음에서
        │  세 가지 검색 방식              │   관련 논문을 찾아 순위 매김
        └───────────────┬───────────────┘
                        │ 찾은 논문 목록 (제목 + 초록)
                        ▼
        ┌───────────────────────────────┐
        │  ④ 웹 화면 모듈                 │   변환 과정과 결과를
        │                                │   사람이 보기 좋게 보여줌
        └───────────────────────────────┘

        ┌───────────────────────────────┐
        │  ③ 성능 평가 모듈               │   ①과 ②를 여러 방식으로 조합해
        │  (개발 단계에서만 돌림)          │   "어느 방식이 더 좋은가" 숫자로 비교
        └───────────────────────────────┘
```

- **①, ②, ④**는 실제 서비스에 들어가는 부품입니다.
- **③ 성능 평가 모듈**은 서비스에 직접 들어가지는 않지만, 개발 과정에서 "지금 만든 게
  정말 나아졌나"를 판단하는 가장 중요한 도구입니다. 이번 프로젝트에서 특히 공들이는
  부분입니다.

각 모듈이 담당하는 일, 내부 구조, 구현할 코드, 현재 진행 정도는 모두
[MODULE_SPECIFICATION.md](MODULE_SPECIFICATION.md)에 자세히 적혀 있습니다.
여기서는 방향만 짧게 정리합니다.

### ① 쿼리 변환 모듈

- 사용자가 입력한 검색어를 받아 **입력한 말 → 중간 개념 → 전문 학술 용어 → 최종 검색어**의
  단계를 거쳐 다듬습니다. 입력에 이미 전문 용어가 섞여 있어도(대학원생의 경우) 더 정확한
  용어로 보정합니다. 이 단계별 사고 과정을 언어 모델에게 시키는 방식을
  '단계별 추론(Chain of Thought)'이라고 합니다.
- 쓰는 언어 모델: **Qwen3-4B** (Alibaba가 무료로 공개한, 40억 개의 값으로 이루어진
  언어 모델). 크기가 작아 내 컴퓨터에서도 돌릴 수 있고, 한국어 질문을 이해하고 영어
  전문 용어를 만들어낼 수 있으며, 라이선스가 자유롭습니다.
- 모델을 내 컴퓨터에서 돌리는 프로그램으로 **Ollama**를 씁니다.

### ② 검색 모듈

논문을 찾는 방식은 크게 두 가지가 있고, 우리는 둘을 합친 세 번째 방식까지 씁니다.

1. **단어 일치 기반 검색** — 검색어의 단어가 논문에 실제로 들어 있는지로 찾습니다.
   전통적인 검색 방식입니다. 도구로 Elasticsearch(단어 일치 검색을 해주는 검색 엔진 소프트웨어)를 씁니다.
2. **의미 기반 검색** — 문장을 '의미를 담은 숫자 목록'으로 바꾼 뒤, 숫자가 비슷한
   논문을 찾습니다. 단어가 정확히 안 겹쳐도 뜻이 비슷하면 찾아냅니다. 숫자로 바꾸는
   모델로 bge-m3를, 빠르게 비교하는 도구로 FAISS(비슷한 벡터를 빠르게 찾아주는 라이브러리)를 씁니다.
3. **혼합 검색** — 위 두 결과의 순위를 합쳐 더 안정적인 결과를 냅니다.

이 세 방식을 모두 만들어 두는 이유는, 나중에 성능 평가 단계에서 **어떤 검색 방식이
쿼리 변환과 가장 잘 어울리는지 비교**하기 위해서입니다.

### ③ 성능 평가 모듈

- "쿼리를 변환하면 정말 검색이 좋아지는가"를 숫자로 증명하는 부분입니다.
- 평가용 정답지를 만들고, 여러 검색 조합을 돌려 점수를 매기고, 통계적으로 의미 있는
  차이인지까지 확인합니다.
- **이 부분을 프로젝트에서 가장 먼저, 가장 자세히 준비합니다.** 상세 내용은
  [MODULE_SPECIFICATION.md](MODULE_SPECIFICATION.md)의 3번 모듈에 있습니다.

### ④ 웹 화면 모듈

- 사용자가 질문을 입력하면, **변환 과정(입력한 말이 어떤 전문 용어로 바뀌었는지)** 을
  단계별로 보여 주고, 찾은 논문의 제목과 초록을 카드 형태로 보여 줍니다.
- 처음에는 Streamlit(파이썬으로 웹 화면을 빠르게 만드는 도구)으로 간단히
  만들고, 시간이 되면 더 정식 웹 서비스 형태로 발전시킵니다.

## 3. 논문 모음(코퍼스)을 어떻게 마련하는가

검색을 하려면 먼저 **검색 대상이 되는 논문들의 모음**이 있어야 합니다. 이것을
'코퍼스'라고 부릅니다.

- **어디서 가져오나:** Kaggle(데이터를 공유하는 사이트)에 arXiv(전 세계 연구자들이 논문을
  올리는 공개 저장소)가 공식으로 제공하는 **논문 정보 모음 파일**이 있습니다. 제목,
  초록, 분야, 논문 번호가 들어 있는 큰 파일 하나입니다.
- **왜 이 방법인가:** arXiv에 논문을 하나씩 요청해서 받아오면, 예의상 요청 사이에
  3초씩 기다려야 해서 수만 편을 모으는 데 며칠이 걸립니다. Kaggle 파일을 쓰면 이 과정이
  한 번의 다운로드로 끝납니다.
- **얼마나:** 컴퓨터·인공지능 관련 분야(예: 자연어 처리, 컴퓨터 비전, 기계 학습,
  정보 검색)에서 최근 5~6년 논문 **1만~3만 편**을 골라 씁니다.

### 실시간 arXiv 검색도 곁들인다

위 코퍼스는 한 번 만들면 고정됩니다(그래서 평가 결과를 항상 똑같이 재현할 수 있음).
여기에 더해, 실제 서비스에서는 **arXiv에 실시간으로 검색을 요청**하는 기능도 옵션으로
둡니다. 이러면 코퍼스에 없는 최신 논문도 찾을 수 있습니다. 다만 실시간 검색은 결과가
계속 바뀌어 평가에는 부적합하므로, **성능 평가는 고정된 코퍼스로만** 합니다.

### arXiv API의 기본 성격 — "쿼리 1개 → 논문 여러 개" (코드로 확인)

실제로 `~/venvs/paper_py310` 환경에서 arXiv API를 호출해 확인한 결과입니다.

- **검색어(쿼리) 하나를 넣으면, 관련도 순으로 정렬된 논문이 여러 개 나옵니다.** "논문 하나만"이
  아닙니다. `max_results`(가져올 개수)를 10으로 하면 10개, 5로 하면 5개가 나왔습니다.
- 그동안 "쿼리 하나에 논문 하나"처럼 보였던 이유는, 지금 우리 코드(`src/arxiv_search.py`)가
  `load_max_docs=1`로 되어 있기 때문입니다. 그런데 이 값은 실제로는 **무시되고**, 결과
  개수는 `top_k_results`(기본값 3)가 정합니다. 그래서 실제로는 1개가 아니라 3개가 나오고 있었습니다.
  → `top_k_results=10`으로 지정하니 정확히 10개가 나오는 것을 확인했습니다.
- **특정 논문들을 번호로 한 번에 가져오는 기능**(`id_list`)도 있습니다. 논문 번호 2개를
  넣으면 그 2편이 정확히 옵니다. 코퍼스를 만들거나 특정 논문을 확인할 때 유용합니다.

이 성격 덕분에, 검색어 하나를 넣고 나온 여러 논문 중 정답이 상위 몇 등에 있는지를 볼 수
있어 **재현율·평균 역순위 같은 순위 평가가 가능**합니다(4절). 만약 정말 논문이 하나씩만
나왔다면 순위 평가 자체가 불가능했을 것입니다.

### 실시간 arXiv 검색에서 주의할 점 (코드로 직접 확인한 사실)

참고 코드(`reference/langchain_community/`)를 직접 뜯어보고 확인한, 놓치면 실험이 조용히
틀어지는 사항들입니다.

| 확인한 사실 | 우리 프로젝트에 주는 영향 |
|---|---|
| 결과 개수는 `top_k_results` 값이 정한다 (`load_max_docs`는 이 경로에서 안 쓰임) | 상위 10개를 평가하려면 `top_k_results=10`으로 지정해야 함. 지금 코드의 `load_max_docs=1`은 아무 효과 없는 설정 |
| 검색어는 300자에서 잘린다 | 변환 과정 전체가 아니라 **최종 검색어만** 넘겨야 함 |
| 특정 옵션을 켜면 검색어에서 `:` 와 `-` 기호를 지운다 | `ti:"..."` 같은 분야 지정 검색이 깨짐 → 그 옵션(`get_full_documents`)을 꺼 둬야 함 |
| 논문 번호 형태로 입력하면 자동으로 번호 검색으로 바뀐다 | 논문 번호로 다시 찾는 기능을 따로 안 만들어도 됨 |
| 결과의 '게재일'은 사실 '수정일'이다 | 날짜를 표시하거나 거를 때 주의 |

## 4. 성능을 무엇과, 어떻게 비교하는가 (요약)

성능 평가가 이 프로젝트의 심장이므로 방향만 여기 요약하고, **구체적인 방법은
[MODULE_SPECIFICATION.md](MODULE_SPECIFICATION.md) 3번 모듈에 매우 자세히** 적었습니다.

- **무엇과 비교하나:** 핵심은 "쿼리 변환 전 vs 변환 후"입니다. 여기에 더해, 변환 방식을
  여러 가지(변환 안 함 / 한 번에 대충 변환 / 우리의 단계별 변환 등) 두고 서로 비교해서,
  "**단계별로** 변환한 것이 정말 효과가 있었는지"까지 가려냅니다.
- **어떤 숫자로 재나:** 대표 지표는 두 가지입니다.
  - **재현율(Recall@K):** 정답 논문이 검색 결과 상위 K개 안에 들어왔는지의 비율.
    (예: 상위 10개 안에 정답이 있으면 성공)
  - **평균 역순위(MRR):** 정답이 몇 등에 나왔는지를 점수로 바꾼 것.
    1등이면 1점, 2등이면 0.5점, 3등이면 0.33점… 처럼 등수가 낮을수록 점수가 큽니다.
- **왜 이 지표들인가:** 처음 기획서에 있던 정밀도·F1·NDCG 같은 지표는, 우리처럼
  "질문 하나에 정답 논문이 딱 하나"인 상황에서는 위 두 지표와 사실상 같은 정보를
  반복하게 됩니다. 이 부분의 자세한 설명과, 그럼에도 그 지표들을 살리는 방법(관련도를
  여러 단계로 매기는 별도 평가)은 상세 문서에 적었습니다.

## 5. 현재 성능과 남은 계획 (2026-08-07 갱신)

1~4절은 프로젝트를 시작할 때의 설계다. 이 절은 **실측 결과를 반영한 현재 위치와 앞으로 할 일**이다.

### 5-1. 지금 어디까지 왔나

시험용 질문 300개 전체, 실제 서비스 경로(arXiv 실시간), 네 모델 모두 오류 0건.

| 모델 | Recall@10 | 기준선 대비 | 판정 |
|---|---|---|---|
| 변환 안 함 (기준선) | 0.167 | — | — |
| 계층 변환 (학습 전) | 0.220 | +0.053 | 불확실 (p=0.050) |
| 학습 모델 (SFT) | 0.273 | +0.107 | 확실 |
| **최종 모델 (SFT+DPO)** | **0.343** | +0.177 | 확실 (기준선의 2.05배) |

**성능이 낮은 이유를 원인별로 분해했다** (최종 모델 기준, ISSUE #16):

| 실패 원인 | 비율 | 무엇으로 고치나 |
|---|---|---|
| 성공 (1~10등) | 34.3% | — |
| 후보에는 있는데 순위가 낮음 (11~100등) | 9.3% | **재정렬** |
| 용어는 맞는데 100등 밖으로 묻힘 | 36.7% | **더 구체적인 어휘** |
| 용어가 논문에 하나도 없어 도달 불가 | 19.7% | **어휘 학습** |

즉 **어휘 문제가 56.4%로 최대 병목**이고, 재정렬로 회수할 수 있는 몫은 9.3%다.

### 5-2. 핵심 설계 변경 — 변환기와 재정렬기의 역할을 나눈다

실측에서 확인한 것: 정답 논문에만 있는 표현으로 검색하면 12/12 회수되지만,
`collaborative filtering` 같은 **진짜 학술 용어**로 검색하면 2/12뿐이다. 그런 용어를 쓰는
논문이 arXiv에 수천 편이라 특정 1편을 위로 올릴 수 없기 때문이다.

```
기존: 변환기 하나가 "정답을 1등으로 올리는 검색어"를 만든다
      → 키워드 검색으로는 구조적으로 불가능한 요구

변경: 변환기   = 정답이 후보 100편 안에 들어오게 한다   (재현율 책임)
      재정렬기 = 그중 의도에 맞는 것을 위로 올린다      (정밀도 책임)
```

이 변경으로 **변환기의 개발 지표가 Recall@10에서 Recall@100으로 바뀐다.** 순위는 재정렬기가
책임지므로, 변환기는 "후보에 넣기"만 잘하면 된다.

### 5-3. 남은 작업 (우선순위 순)

| 단계 | 기간 | 무엇을 | 왜 |
|---|---|---|---|

## 부록. 용어 사전

프로젝트에 자주 나오는 용어를 쉬운 말로 정리했습니다.

| 용어 (원어) | 쉬운 설명 |
|---|---|
| 쿼리 (query) | 사용자가 검색을 위해 입력하는 질문/검색어 |
| 코퍼스 (corpus) | 검색 대상이 되는 논문들의 모음(모아둔 데이터) |
| 큰 언어 모델 (LLM) | 사람의 말을 이해하고 만들어내는 인공지능 모델 (예: ChatGPT 같은 것) |
| 단계별 추론 (Chain of Thought) | 답을 한 번에 내지 않고, 생각 과정을 여러 단계로 나눠 차근차근 진행하게 하는 방식 |
| 계층적(단계적) 변환 | 입력한 말을 곧바로가 아니라 '입력한 말 → 중간 개념 → 전문 용어' 순서로 단계를 밟아 다듬는 것 |
| 임베딩 (embedding) | 문장을 '의미를 담은 숫자들의 목록(벡터)'으로 바꾸는 것. 의미가 비슷하면 숫자도 비슷해짐 |
| 단어 일치 기반 검색 (BM25, 희소 검색) | 검색어의 단어가 문서에 실제로 얼마나 들어 있는지로 찾는 전통적 방식 |
| 의미 기반 검색 (밀집/벡터 검색) | 임베딩(숫자 목록)이 비슷한 문서를 찾는 방식. 단어가 안 겹쳐도 뜻이 통하면 찾음 |
| 혼합 검색 (Hybrid) | 위 두 검색의 순위를 합쳐 더 안정적인 결과를 내는 방식 |
| 순위 합치기 (RRF) | 여러 검색 결과의 등수를 정해진 공식으로 합쳐 하나의 순위로 만드는 방법 |
| Elasticsearch | 단어 일치 기반 검색을 해주는 검색 엔진 소프트웨어 |
| FAISS | 숫자 목록(벡터)들 사이에서 비슷한 것을 빠르게 찾아주는 라이브러리 |
| Ollama | 큰 언어 모델을 내 컴퓨터에서 쉽게 실행하게 해주는 프로그램 |
| Qwen3-4B | Alibaba가 무료로 공개한, 40억 개 값으로 이루어진 작은 언어 모델 |
| 재현율 (Recall@K) | 정답 논문이 검색 결과 상위 K개 안에 들어온 비율. 높을수록 좋음 |
| 정밀도 (Precision@K) | 검색 결과 상위 K개 중 실제 정답인 것의 비율 |
| 평균 역순위 (MRR) | 정답이 몇 등에 나왔는지를 점수화(1등=1점, 2등=0.5점…)해 평균낸 값 |
| NDCG | 결과의 순위와 각 결과의 관련도(얼마나 관련 있는지 등급)를 함께 반영하는 점수 |
| 개발용/시험용 분할 | 데이터를 두 묶음으로 나눔. 개발용은 만들면서 계속 보고, 시험용은 마지막 성적 측정 때만 봄(미리 보면 성적을 부풀리는 셈이라 안 됨) |
| 미세조정 (fine-tuning) | 이미 만들어진 언어 모델을, 우리 목적에 맞게 추가로 조금 더 학습시키는 것 |
| arXiv | 전 세계 연구자들이 논문을 무료로 올리고 받는 공개 저장소 |
| arXiv API | arXiv에 프로그램으로 검색을 요청하는 통로. 검색어 하나에 관련 논문 여러 개를 순위대로 돌려줌(하나만이 아님). 논문 번호로 특정 논문을 한 번에 가져오는 기능도 있음 |
| Kaggle | 데이터를 공유·다운로드하는 사이트. arXiv 논문 정보 모음 파일을 여기서 받음 |
