### 파일을 나누는 규칙

**디렉터리마다 코드 파일은 4개를 넘지 않는다.** 기능마다 파일을 새로 만들면 곧
"뭐가 뭔지 모르는" 상태가 된다. 새 기능은 **되도록 기존 파일 안에** 넣고, 파일을 늘려야만
한다면 무엇을 합칠 수 있는지 먼저 본다.

**버전 접미사(`_v2`)로 파일을 늘리지 않는다.** 새 방식이 옛 방식을 대체하면 옛 코드를
지우고, 왜 바꿨는지를 ISSUE.md 와 코드 설명글에 남긴다.

### 서비스 경로와 실험 경로를 구분할 것

`app.py` 가 실제로 쓰는 것만이 서비스 성능이다. 비교군(passthrough·hierarchical·hyde,
임베딩 유사도 재정렬)은 평가에서만 쓴다. **실험 경로 숫자를 서비스 성능이라고 말하면 안 된다**
(로컬 평가 0.74 대 실제 서비스 0.15 를 겪은 적이 있다 — ISSUE #10).

## 모듈 ① 쿼리 변환 — `src/rewriter/`

### 담당하는 일

사용자가 입력한 말을, 검색기가 실제로 찾을 수 있는 검색어로 바꾼다.
**가장 중요한 일은 한국어를 영어 학술 용어로 건너게 하는 것**이다(arXiv 는 한글을 색인하지
않아 한국어를 그대로 넣으면 88.2% 가 0건이다).

### 약속 (인터페이스)

모든 변환기는 이 하나를 만족한다.

```python
class Rewriter(Protocol):
    name: str
    def rewrite(self, raw_query: str) -> RewriteResult: ...
```

`RewriteResult` (`src/schemas.py`) 가 담는 것:

| 필드 | 무엇 |
|---|---|
| `raw_query` | 사용자가 친 원본 |
| `intent` | 사용자가 진짜 찾고 싶은 것 한 문장 |
| `concepts` | 핵심 개념 2~4개 |
| `academic_terms` | 정확한 영어 학술 용어 3~5개 |
| `queries` | **검색 방식별 최종 검색어** — `sparse` / `dense` / `arxiv` |
| `parse_ok` | 변환이 제대로 됐는가 (실패율 자체가 품질 지표다) |

### 최종 검색어를 방식별로 나누는 이유

검색기마다 잘 먹는 입력이 다르다.

| 키 | 쓰는 곳 | 좋은 모양 |
|---|---|---|
| `dense` | 로컬 의미 검색 | 찾는 내용을 설명하는 **자연스러운 영어 문장 하나** |
| `arxiv` | arXiv 실시간 | `all:"원본" OR abs:"용어1" OR abs:"용어2"` — **따옴표 구**의 나열 |
| `sparse` | (지금은 안 씀) | 영어 용어를 공백으로 나열 |

`arxiv` 검색어는 **언어 모델이 아니라 코드가 만든다**(`baselines.build_arxiv_query`).
arXiv 문법 구성을 불안정한 모델에 맡기지 않기 위해서다. 따옴표 없이 넓은 단어를 나열하면
수천 편에 묻히고, 용어를 하나만 쓰면 0건이 되기도 한다. 그래서 **각 용어를 따옴표 구로 만들어
전부 OR 로** 잇는다.

### 변환기 종류

| 이름 | 파일 | 무엇 | 상태 |
|---|---|---|---|
| `passthrough` | `base.py` | 변환 안 함 | **기준선. 모든 평가에 반드시 포함** |
| `hierarchical` | `baselines.py` | 의도→개념→용어→검색어 4단계 | 비교군 + 학습 데이터 생성용 |
| `single_step` | `baselines.py` | "학술 검색어로 바꿔줘" 한 번 | 비교군 (계층 구조의 기여를 가려낸다) |
| `hyde` | `baselines.py` | 가상 초록을 지어내 의미 검색어로 | 비교군 (알려진 다른 방법) |
| `finetuned` | `finetuned.py` | SFT 까지 학습 | 학습 전/후 비교용 |
| **`dpo`** | `finetuned.py` | SFT + 선호 학습 | **서비스가 쓰는 것** |

`build_rewriter(name)` 하나로 전부 만든다. 무거운 패키지는 그 이름을 부를 때만 늦게 가져온다.

### 특별한 것 둘

**`finetuned.py` 가 `generate_json` 을 갖고 있다.** 추천 에이전트가 같은 Qwen3-4B 를 또
올리지 않도록, **이미 올라와 있는 모델을 빌려주는** 창구다. 이때 LoRA 어댑터는 잠깐 끈다
(어댑터는 '검색어 변환' 한 가지만 하도록 학습돼 있어 다른 일에 쓰면 편향이 낀다).
이 장치가 없으면 모델 두 벌(12.2GB)이 GPU 16GB 를 넘겨 **추천 모델이 조용히 CPU 로 밀려나**
한 번에 229.6초가 걸린다.

**`paper_resolver.py` 는 "그 논문" 요청을 따로 처리한다.** "트랜스포머 최초 논문" 처럼 특정
논문을 지목하는 요청은 주제 검색과 다른 능력이다(ISSUE #6). 언어 모델의 지식으로 후보를
떠올린 뒤 **arXiv 에서 실제로 존재하는지 검증**해 할루시네이션을 막는다.

## 모듈 ② 검색 — `src/retrieval/`

### 담당하는 일

검색어를 받아 관련 논문을 점수순으로 돌려준다. 채널이 둘이고, 그 결과를 합쳐 다시 줄 세운다.

### 약속 (인터페이스)

모든 검색 채널은 이 하나를 만족한다.

```python
def search(self, query: str, k: int) -> list[ScoredPaper]: ...
```

`ScoredPaper` = `paper_id` · `score` · `rank` · `title` · `abstract`.
모양을 맞춰 두었기 때문에 평가 하네스가 채널을 갈아 끼우며 비교할 수 있다.

### 채널 둘

**채널 A — arXiv 실시간 (`arxiv_live.py`)**
- 서비스가 최신 논문과 색인 밖 분야를 커버하는 통로. **역할은 정확도가 아니라 최신성·범위다.**
- 3초 간격·단일 연결(정책 준수), 429/503 지수 백오프, 디스크 캐싱.
- arXiv 는 관련도 점수를 주지 않아서 우리가 `1/순위` 를 점수 자리에 채운다.

**채널 B — 로컬 의미 검색 (`local_index.py`)** ← 정확도의 대부분
- 논문 716,183편 임베딩(bge-m3, 2.93GB)과 내적으로 뜻이 가까운 논문을 찾는다.
- 시스템 메모리 15GB 에서 돌리려고 세 가지를 다르게 만들었다:
  ⓐ **본문을 메모리에 안 올린다** — 파일 안 위치만 기록해 두고 필요할 때 꺼내 읽는다
  ⓑ **FAISS 를 안 쓴다** — 벡터 복사본이 한 벌 더 필요해진다
  ⓒ **임베딩을 조각으로 계산해 바로 디스크에 쓴다** — 중간에 끊겨도 이어서 한다
- **색인과 코퍼스의 짝을 반드시 확인한다.** 짝이 안 맞으면 `seek` 이 엉뚱한 줄에 떨어지는데
  **JSON 파싱은 그대로 성공한다.** 오류도 안 나고 결과도 그럴듯해 보이는 채로 다른 논문의
  제목·초록이 나온다(ISSUE #28). 크기 지문 + 표본 대조로 막고 단위 테스트로 못박았다.

### 합치기와 재정렬 (`ranking.py`)

**RRF — 점수가 아니라 등수를 더한다.** arXiv 채널 점수는 1등이 1.0 인데 의미 검색 점수는
코사인 유사도라 0.4~0.8 에 몰려 있다. 그대로 더하면 **어느 채널이 옳은가가 아니라 점수 눈금이
큰 쪽이 이긴다.** 등수만 쓰면 눈금 맞추기가 필요 없고 조정할 값이 완충 상수 k 하나뿐이다.

**교차 인코더 재정렬** — `BAAI/bge-reranker-v2-m3`(568M, 다국어). 질문과 논문을 **함께** 읽어
관련도를 직접 예측한다. 재정렬에 넣는 질문은 **변환된 검색어가 아니라 원본 질문**이다 —
목적이 '사용자 의도와 맞는가'를 보는 것이기 때문이다.

**재정렬의 한계를 알고 쓸 것**: 정답이 1차 검색에서 1~30등이면 95% 를 살리지만, 201~300등이면
12.5% 밖에 못 살린다. **이미 위에 있는 정답만 지킨다. 깊은 곳에서 끌어올리지 못한다.**

### 논문 번호 정규화 (`corpus.normalize_paper_id`)

arXiv 실시간은 `2103.00020v2`, 로컬 색인은 `2103.00020` 으로 같은 논문을 다르게 표기한다.
통일하지 않으면 **두 채널이 합의한 논문일수록 점수가 반으로 쪼개진다.** 오류를 내지 않고
성능만 조용히 깎는 종류의 버그다.

떼어낼 때 `split("v")[0]` 을 쓰면 **안 된다** — `solv-int/9611001v1` 이 `sol` 로 잘린다
(ISSUE #27). 끝에 붙은 `v숫자` 만 정규식으로 뗀다.

## 모듈 ③ 성능 평가 — `evaluation/`

### 담당하는 일

"변환하면 정말 좋아지는가"를 숫자로 재고, 그 숫자를 **믿어도 되는지까지** 판정한다.

### 3-1. 평가셋 (`dataset.py`)

```
generate ──> split ──> pool ──> grade        audit (언제든)
   유료        무료      무료      유료
```

**정답지를 어떻게 만드나**: 논문을 하나 골라 **초록만** 모델에게 주고, "이 논문을 아직 못 찾은
사람"이 칠 법한 검색어를 만들게 한다. 그 논문이 그 질문의 정답이 된다(거꾸로 만들기).

**옛 평가셋이 실패한 이유와 지금의 대책**

| 옛 결함 | 지금 |
|---|---|
| 난이도 축이 "제목과 표현이 얼마나 다른가" 였다 → 의미 검색에는 **뒤집혀** 있었다 (#32) | 축을 **"묻는 사람이 얼마나 아는가"** 로 재정의. 검색 방식과 무관하다 |
| 제목을 주고 "어순만 바꿔라"라고 시켰다 → 정답을 적어 준 셈 | **제목을 아예 주지 않는다.** 초록만 준다 |
| 한국어 문항은 검사기가 영어 낱말만 세서 **검사한 적이 없었다** | 한국어·영어를 **한 번에** 만들어 짝(`pair_id`)으로 묶는다. 감사는 한국어를 영어로 옮긴 뒤 비교한다 |
| 등급 정답지를 **질문 만든 그 모델이 채점**했다 (#34) | 생성기(gpt-5.4)와 심판(gpt-4.1-mini)을 다른 계열로 고정 |

**난이도 = 묻는 사람의 전문성**

| 층 | 누가 | 어떻게 쓰나 |
|---|---|---|
| `easy` | 대학원생 | 정확한 학술 용어로 짧게 |
| `medium` | 학부 연구생 | 범용 전문어와 일상어가 섞인다 |
| `hard` | 1~2학년 | 전문 용어 없이 일상어로 두루뭉술하게 |
| `known_item` | 논문을 아는 사람 | 특정 논문을 지목 (**다른 층과 섞지 않고 따로 본다**) |

**거르는 것과 기록만 하는 것**
- 거른다: 초록을 5낱말 이상 그대로 옮긴 문항, 짝이 깨진 문항
- **기록만 한다**: 제목 겹침. 대학원생이 정확한 용어로 물으면 겹치는 것이 정상이다.
  여기서 임계값을 정하면 나중에 유리한 값을 고르고 싶은 유혹이 생긴다.
  대신 분포를 남기고 **성능을 겹침 구간별로 층화 보고**한다.

**분할은 논문 단위로.** 같은 논문의 질문이 개발용과 시험용에 흩어지면 시험지를 미리 본 셈이 된다.

### 3-2. 평가 데이터 파일 넷

| 파일 | 무엇 | 크기 |
|---|---|---|
| `data/eval/dev.jsonl` | **개발용** 질문. 탐색은 전부 여기서 | 348문항 / 174짝 |
| `data/eval/test.jsonl` | **시험용** 질문. 확정 판정 전용 | 342문항 / 171짝 |
| `data/eval/grades_dev.jsonl` | 개발용 등급 정답지 (후보 20편에 0~3) | 174짝 |
| `data/eval/grades_test.jsonl` | 시험용 등급 정답지 | 171짝 |

질문 파일 한 줄: `query_id` · `text` · `gold_id` · `lang` · `difficulty` · `pair_id` ·
`title_overlap`(기록용) · `abstract_copy_words`(기록용) · `_title`(감사용).

**중간 산출물(질문 원본·후보 풀)은 `runs/` 에 둔다.** 평가 폴더에 중간 파일이 쌓이면
무엇이 진짜 시험지인지 알 수 없게 된다.

### 3-3. 점수 매기기 (`metrics.py`)

| 지표 | 뜻 |
|---|---|
| Recall@K | 상위 K편 안에 정답이 들어온 비율 |
| MRR@K | 정답이 몇 등인지까지 반영 (1등=1, 2등=1/2 …) |
| nDCG@K | 등급을 이득으로 써서 "좋은 논문을 위에 올렸나" |
| 부트스트랩 신뢰구간 | "0.35" 하나만으로는 못 보는 **표본 크기의 무게**를 보여 준다 |
| 짝지은 부트스트랩 검정 | 같은 질문끼리 짝지어 "이 차이가 우연인가"를 잰다 |

지표는 외부 라이브러리 대신 numpy 로 직접 구현했다(투명성 + 설치 부담 없음).

### 3-4. 실행 (`pipeline_eval.py`)

**핵심 설계: 채널별 검색 결과 논문 번호를 전부 따로 저장한다.**

```json
{"channels": {"arxiv": ["...100편..."], "local_dense": ["...100편..."]}}
```

그래서 융합 상수·채널 가중치·재정렬 방식을 바꿔 가며 실험할 때 **검색을 다시 하지 않는다.**
arXiv 는 3초 제한이 있어 300문항 재검색에 15분 이상 걸리는데 그 비용을 한 번만 치른다.

**실패를 세는 방식**: 오류·결과 0건 문항을 **제외하지 않고 실패(0점)로 센다.** 분모는 항상
전체 문항 수다. 제외하면 기준선이 부풀려진다 — 같은 실행을 그렇게 재면 passthrough 가
0.257 대신 0.467 로 보인다(ISSUE #23).

**상한을 어느 집합으로 재는가** (두 번 틀린 자리 — ISSUE #26, #31): '채널 합집합'과
'재정렬이 실제로 본 후보'는 다른 집합이다. 융합이 후보를 줄이기 때문이다. 합집합을 상한이라
부르면 **융합이 흘린 몫까지 재정렬 탓으로 넘어가** 처방이 뒤바뀐다. 그래서 보고서가
① 채널 합집합 ② 재정렬이 실제로 본 후보 ③ 최종값을 **셋 다** 찍고, 파일에 새겨진 재정렬
깊이를 명령줄 기본값보다 우선한다.

**응답 시간 실측**(`--bench-service`): 정확도가 아니라 시간을 잰다. 한 번의 검색에 언어 모델을
세 번 부르고(논문 지목 확인·쿼리 변환·추천 이유) 그 사이에 arXiv 호출과 재정렬이 끼어 있다.
사람은 30초를 넘으면 떠난다.

### 3-5. 보고 (`report.py`)

`--run` 을 하나 주면 자세한 보고(전체 · 난이도별 · 언어별 · 제목 겹침 구간별),
둘 이상 주면 **공통 문항만 추려** 비교하고 첫 번째를 기준으로 짝지은 검정을 돌린다.

**반드시 지킬 것 셋**
1. **기준선(passthrough)을 항상 첫 번째로 둔다.** 없으면 프로젝트의 주장이 검증되지 않는다.
2. **탐색은 개발용에서만.** 시험용을 보면서 설정을 고르면 시험지가 탄다(ISSUE #25).
3. **p > 0.05 는 "차이가 없다"가 아니라 "있는지 없는지 모른다".**

### 3-6. 이 평가 데이터의 한계 — 점수를 읽을 때 반드시 함께 볼 것

- **단일 정답 지표에는 이론적 상한이 있다**(ISSUE #14). 한 질문에 맞는 논문이 실제로 여러
  편이라, 완벽한 검색기도 특정 1편을 상위 10에 못 올릴 수 있다. 그래서 nDCG 를 함께 본다.
- **로컬 색인 평가는 "색인 밖 논문을 못 찾는다"는 약점을 구조적으로 못 잰다.** 평가셋 정답
  논문이 전부 색인 안에 있기 때문이다.
- **자동 생성 질문은 실제 검색어와 형태가 다르다.** 실사용자 질문 수집은 미착수.

사용자가 검색어를 넣고, 변환 과정과 결과를 보고, 추천 이유를 읽는다. Streamlit 한 파일.

### 지금 화면 흐름

```
검색어 입력
  └→ [특정 논문 지목?] → 🎯 배너로 그 논문을 먼저 보여준다
  └→ 변환 과정 (의도 → 개념 → 학술 용어)
```

## 추천 에이전트 — `src/recommend_agent/recommender.py`

검색된 논문 10편(제목 + 초록)을 사용자 의도와 대조해 **관련도 · 이유 · 종합 요약**을 JSON 으로
만든다. 초록에 근거해서만 쓰도록 강제하고, 맞는 논문이 하나도 없으면 그렇게 말하게 한다
(할루시네이션 방지).

**모델은 새로 올리지 않고 쿼리 변환기가 이미 올린 것을 빌려 쓴다**(위 GPU 예산 참고).
빌려 쓸 때 4B 모델이 **내용은 제대로 채우면서 키 이름을 자기 마음대로 바꾸는** 함정이 있어,
스키마의 필수 키 이름을 프롬프트에 못박고 빠지면 다시 시도한다.

## 학습 — `training/`

| 파일 | 무엇 |
|---|---|
| `build_training_data.py` | 후보 검색어를 N개 만들어 **실제 arXiv 검색으로 채점** → 정답 논문을 찾아낸 것을 라벨로, 못 찾은 것을 선호쌍의 rejected 로 |
| `train.py` | `sft` (지도 미세조정) → `dpo` (선호 학습). **순서가 중요하다** |

**핵심 아이디어**: 라벨을 사람이 "좋아 보이는" 기준으로 고르지 않고 **검색 성공을 신호로**
삼는다. 그러면 라벨이 "학술적으로 그럴싸한 표현"이 아니라 **"진짜 찾아내는 표현"** 이 된다.

**분할은 논문 단위로.** 같은 논문에서 나온 질문들은 라벨이 거의 같아서, 질문 단위로 나누면
검증 손실이 실제보다 좋게 나오고 과적합 시작점을 놓친다.
