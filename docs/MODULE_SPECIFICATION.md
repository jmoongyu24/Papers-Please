## 모듈 ① 쿼리 변환 — `src/rewriter/`

사용자가 입력한 말을 검색기가 찾을 수 있는 검색어로 바꿈.

### 약속

```python
class Rewriter(Protocol):
    name: str
    def rewrite(self, raw_query: str) -> RewriteResult: ...
```

`RewriteResult` (`src/schemas.py`): `raw_query` · `intent` · `concepts` · `academic_terms` ·
`queries`(검색 방식별 최종 검색어) · `parse_ok`(변환 실패율 자체가 품질 지표임).

### 검색어를 방식별로 나누는 이유

| 키 | 쓰는 곳 | 좋은 모양 |
|---|---|---|
| `dense` | 로컬 의미 검색 | 찾는 내용을 설명하는 자연스러운 영어 문장 하나 |
| `arxiv` | arXiv 실시간 | `all:"원본" OR abs:"용어1" OR abs:"용어2"` 형태의 따옴표 구 나열 |
| `sparse` | 지금은 안 씀 | 영어 용어를 공백으로 나열 |

`arxiv` 검색어는 **언어 모델이 아니라 코드가 만듦**(`baselines.build_arxiv_query`).
검색 문법 구성을 불안정한 모델에 맡기지 않기 위해서임.

### 변환기 종류

| 이름 | 파일 | 무엇 | 상태 |
|---|---|---|---|
| `passthrough` | `base.py` | 변환 안 함 | 기준선. 모든 평가에 포함 |
| `translate` | `baselines.py` | 한국어만 영어로 옮김 | **유일하게 이득이 확정된 변환기** |
| `hierarchical` | `baselines.py` | 의도→개념→용어→검색어 4단계 | 비교군 + 학습 데이터 생성용 |
| `single_step` | `baselines.py` | 한 번에 학술 검색어로 | 비교군 |
| `hyde` | `baselines.py` | 가상 초록을 지어내 의미 검색어로 | 비교군. **로컬 채널에 넣어 시험한 적 없음** |
| `finetuned` / `dpo` | `finetuned.py` | SFT / SFT+선호 학습 | 지금 구조에서 기여 판정 불가(#37) |

`build_rewriter(name)` 하나로 전부 만듦. 무거운 패키지는 그 이름을 부를 때만 늦게 가져옴.

### 특별한 것 둘

- **`finetuned.py` 의 `generate_json`** — 추천 이유 생성기가 같은 Qwen3-4B 를 또 올리지 않도록
  이미 올라온 모델을 빌려주는 창구임. 빌려줄 때 LoRA 어댑터는 잠깐 끔(어댑터가 검색어 변환
  한 가지만 하도록 학습돼 있어 다른 일에 쓰면 편향이 낌).
- **`paper_resolver.py`** — "트랜스포머 최초 논문" 같은 특정 논문 지목 요청을 따로 처리함.
  언어 모델 지식으로 후보를 떠올린 뒤 **arXiv 에서 실제 존재를 검증**해 없는 논문을 지어내는
  것을 막음(#6).

## 모듈 ② 검색 — `src/retrieval/`

### 약속

```python
def search(self, query: str, k: int) -> list[ScoredPaper]: ...
```

`ScoredPaper` = `paper_id` · `score` · `rank` · `title` · `abstract`.
모양이 같아서 평가 하네스가 채널을 갈아 끼우며 비교할 수 있음.

### 채널 둘

**채널 B — 로컬 의미 검색 (`local_index.py`)** ← 정확도의 대부분
- 논문 716,183편 임베딩(bge-m3)과 내적으로 뜻이 가까운 논문을 찾음.
- 메모리 15GB 에서 돌리려고 세 가지를 다르게 만들었음:
  ⓐ 본문을 메모리에 안 올리고 파일 안 위치만 기록 ⓑ FAISS 미사용(벡터 복사본이 한 벌 더
  필요해짐) ⓒ 임베딩을 조각으로 계산해 바로 디스크에 씀(중간에 끊겨도 이어서 함).
- **색인과 코퍼스의 짝을 반드시 확인함.** 짝이 안 맞으면 파일 위치가 엉뚱한 줄에 떨어지는데
  **JSON 해석은 그대로 성공함.** 오류 없이 다른 논문의 제목·초록이 나옴(#28).

**채널 A — arXiv 실시간 (`arxiv_live.py`)**
- 최신 논문과 색인 밖 분야를 담당함. **역할은 정확도가 아니라 최신성·범위임.**
- 3초 간격, 단일 연결, 429/503 지수 백오프, 소켓 시간 제한 90초, 디스크 캐싱.
- arXiv 는 관련도 점수를 주지 않아서 `1/순위` 를 점수 자리에 채움.

### 합치기와 재정렬 (`ranking.py`)

**순위 합치기(RRF)** — 점수가 아니라 등수를 더함. arXiv 채널 점수는 1등이 1.0 인데 의미 검색
점수는 0.4~0.8 에 몰려 있어서, 그대로 더하면 **어느 채널이 옳은가가 아니라 점수 눈금이 큰
쪽이 이김.** 등수만 쓰면 눈금을 맞출 필요가 없음.

**교차 인코더 재정렬** — `BAAI/bge-reranker-v2-m3`(568M, 다국어). 질문과 논문을 함께 읽어
관련도를 직접 예측함. 넣는 질문은 변환된 검색어가 아니라 **원본 질문**임(사용자 의도와 맞는지를
보는 단계이므로).

**재정렬의 한계를 알고 쓸 것** (시험용, 번역 구성 실측):

| 정답의 1차 등수 | 1~10등 | 11~30등 | 31~100등 |
|---|---|---|---|
| 상위 10편에 살린 비율 | 0.953 | 0.600 | 0.683 |

**이미 위에 있는 정답을 지키는 데는 강하고, 깊은 곳에서 끌어올리는 데는 약함.**

### 논문 번호 정규화 (`corpus.normalize_paper_id`)

arXiv 실시간은 `2103.00020v2`, 로컬 색인은 `2103.00020` 으로 같은 논문을 다르게 표기함.
통일하지 않으면 **두 채널이 함께 찾아낸 논문일수록 중복으로 남아 손해를 봄.**
떼어낼 때 `split("v")[0]` 을 쓰면 안 됨 — `solv-int/9611001v1` 이 `sol` 로 잘림(#27).
끝에 붙은 `v숫자` 만 정규식으로 뗌.

## 모듈 ③ 성능 평가 — `evaluation/`

### 평가셋 (`dataset.py`)

```
generate ──> split ──> pool ──> grade        audit (언제든)
  유료        무료      무료     유료
```

논문을 하나 골라 **초록만** 모델에게 주고, 그 논문을 아직 못 찾은 사람이 칠 법한 검색어를
만들게 함. 그 논문이 그 질문의 정답이 됨.

**옛 평가셋이 실패한 이유와 지금의 대책**

| 옛 결함 | 지금 |
|---|---|
| 난이도 축이 "제목과 표현이 얼마나 다른가" 였음 → 의미 검색에는 뒤집혀 있었음(#32) | 축을 **"묻는 사람이 얼마나 아는가"** 로 재정의. 검색 방식과 무관함 |
| 제목을 주고 어순만 바꾸게 시켰음 | **제목을 아예 주지 않음.** 초록만 줌 |
| 한국어 문항은 감사기가 영어 낱말만 세서 검사한 적이 없었음 | 한국어·영어를 한 번에 만들어 짝으로 묶고, 한국어를 영어로 옮긴 뒤 감사함 |
| 등급 정답지를 질문 만든 그 모델이 채점했음(#34) | 생성기 gpt-5.4, 심판 gpt-4.1-mini 로 계열을 가름 |

**난이도 = 묻는 사람의 전문성**: `easy`(대학원생, 정확한 학술어) · `medium`(학부 연구생) ·
`hard`(1~2학년, 일상어) · `known_item`(특정 논문 지목, 다른 층과 섞지 않음).

**거르는 것**: 초록을 5낱말 이상 그대로 옮긴 문항, 짝이 깨진 문항.
**기록만 하는 것**: 제목 겹침. 임계값으로 자르지 않고 겹침 구간별로 층화 보고함
(임계값을 정하면 나중에 유리한 값을 고르고 싶은 유혹이 생김).

**분할은 논문 단위로 함.** 같은 논문의 질문이 개발용과 시험용에 흩어지면 시험지를 미리 본 셈임.

### 평가 데이터 파일 넷

| 파일 | 무엇 | 크기 |
|---|---|---|
| `data/eval/dev.jsonl` | 개발용 질문. 탐색은 전부 여기서 | 348문항 / 174짝 |
| `data/eval/test.jsonl` | 시험용 질문. 확정 판정 전용 | 342문항 / 171짝 |
| `data/eval/grades_dev.jsonl` | 개발용 등급 정답지(후보 20편에 0~3) | 174짝 |
| `data/eval/grades_test.jsonl` | 시험용 등급 정답지 | 171짝 |

두 파일 모두 한국어와 영어가 정확히 절반씩이고, 난이도 세 층도 정확히 균등함.
중간 산출물(질문 원본·후보 풀)은 `runs/` 에 둠.

### 지표 (`metrics.py`)

Recall@K · MRR@K · nDCG@K · 부트스트랩 신뢰구간 · 짝지은 부트스트랩 검정.
외부 라이브러리 대신 numpy 로 직접 구현했음(투명성 + 설치 부담 없음).

### 실행 (`pipeline_eval.py`)

**핵심 설계: 채널별 검색 결과 논문 번호를 전부 따로 저장함.**

```json
{"channels": {"arxiv": ["...100편..."], "local_dense": ["...100편..."]}}
```

그래서 융합 상수·채널 가중치·재정렬 방식을 바꿔 실험할 때 **검색을 다시 하지 않음.**

**실패를 세는 방식**: 오류·결과 0건 문항을 제외하지 않고 실패(0점)로 셈. 분모는 항상 전체
문항 수임. 제외하면 기준선이 부풀려짐(#23).

**상한을 어느 집합으로 재는가**(두 번 틀린 자리 — #26, #31): '채널 합집합'과 '재정렬이 실제로
본 후보'는 다른 집합임. 보고서가 ① 채널 합집합 ② 재정렬이 본 후보 ③ 최종값을 셋 다 찍음.

**주요 인자와 기본값**: `--k 100`(채널마다 가져올 수) · `--rerank-depth`(재정렬 후보 수) ·
`--local-query raw`(로컬 채널에 원본 질문) · `--rerank-query raw` · `--fuse-top-n 200`.
**이 값들이 서비스와 다르면 잰 값이 서비스를 설명하지 못함**(#40).

### 보고 (`report.py`)

`--run` 하나면 자세한 보고(전체·난이도별·언어별·제목 겹침 구간별), 둘 이상이면 공통 문항만
추려 비교하고 첫 번째를 기준으로 짝지은 검정을 돌림.

지킬 것 셋: ① 기준선을 항상 첫 번째로 둠 ② 탐색은 개발용에서만 ③ p > 0.05 는 "차이가 없다"가
아니라 "있는지 없는지 모른다".

### 이 평가 데이터의 한계

- 단일 정답 지표에는 이론적 상한이 있음(#14). 한 질문에 맞는 논문이 여러 편이라 완벽한
  검색기도 특정 1편을 상위 10에 못 올릴 수 있음. 그래서 nDCG 를 함께 봄.
- **색인 밖 논문을 못 찾는 약점은 구조적으로 못 잼.** 평가셋 정답 논문이 전부 색인 안에 있음.
- 자동 생성 질문은 실사용자 검색어와 형태가 다를 수 있음. 실사용자 질문 수집은 미착수.

## 모듈 ④ 웹 화면 — `app.py`

### 화면 흐름 (2026-08-16 구조)

```
검색어 입력
  -> [특정 논문 지목?] 그 논문을 먼저 짚어 보여 줌
  -> 검색어 1: 원본 (한국어면 영어로 옮김)
     검색어 2: 질문에 답할 법한 가상 초록
  -> 각각 로컬 의미 검색 100편 -> 순위 합치기(RRF) -> 재정렬 -> 결과 카드 10편
  -> 관련도(high/med/low)·이유·종합 요약
  -> [arXiv 켜짐] "최신 논문" 칸을 결과 아래에 따로 보여 줌
```

무거운 부품은 전부 `st.cache_resource` 로 한 번만 올림. 실행: `streamlit run app.py`.

|---|---|
| 후보 깊이 100 (300 아님) | 깊게 가져오면 상한은 오르지만 만족도가 떨어짐(−0.036, p<0.001). ISSUE #40 |
| arXiv 를 재정렬 목록에 안 섞음 | 어떤 비율로 섞어도 만족도가 떨어짐(1대1 −0.041 · 2대1 −0.040 · 3대1 −0.034). ISSUE #39 |
| 검색어 2개를 합침 (대체 아님) | 가상 초록으로 대체하면 hard 만 좋아지고 나머지가 나빠짐 |
| dpo 변환기는 arXiv 켤 때만 | 결과물이 arXiv 검색어뿐이라 로컬 검색에 쓸 곳이 없음. 끄면 GPU 8.64GB 를 아낌 |

**평가도 같은 조건으로 잴 것**: `--k 100`, `--rerank-depth 100`. 서비스와 평가의 깊이가
어긋나면 잰 값이 서비스를 설명하지 못함(#10, #13, #40 이 전부 같은 사고임).

### 반드시 지킬 것 — GPU 예산

GPU 16GB 에 여러 모델이 들어가야 함. 순진하게 올리면 넘침.

| 부품 | 순진하게 | 지금 |
|---|---|---|
| 쿼리 변환기 (Qwen3-4B + LoRA) | 8.64GB | 8.64GB |
| 추천 이유 생성기 (Qwen3-4B) | +3.54GB | **0 — 변환기 모델을 빌려 씀** |
| 임베더 (bge-m3) | 2.14GB | **1.07GB (fp16)** |
| 재정렬 (bge-reranker-v2-m3) | 3.06GB | **1.53GB (fp16)** |

**모자라면 오류가 나는 게 아니라 조용히 CPU 로 밀려남.** 그러면 추천 한 번이 10.5초에서
229.6초가 됨(실측).

### "못 찾았다"고 말하기

로컬 의미 검색은 아무리 무관한 질문이어도 항상 상위 10편을 채워 돌려줌. 그래서 최소 관련도
기준선 `MIN_RERANK_SCORE = 0.002` 를 둠. 등급 정답지 7,112쌍으로 실측해 정한 값임
(무관 43.8% 걸러냄, 만족 7.7% 잘못 버림). 기준선 아래 논문은 지우지 않고 접어 둠.
**재정렬 모델을 바꾸면 점수 눈금이 달라지므로 반드시 다시 재야 함.**

## 추천 이유 생성 — `src/recommend_agent/recommender.py`

검색된 논문 10편(제목 + 초록)을 사용자 의도와 대조해 관련도·이유·종합 요약을 JSON 으로 만듦.
초록에 근거해서만 쓰도록 강제하고, 맞는 논문이 하나도 없으면 그렇게 말하게 함.
모델은 쿼리 변환기가 이미 올린 것을 빌려 씀. 4B 모델이 **내용은 채우면서 키 이름을 마음대로
바꾸는** 문제가 있어 필수 키 이름을 프롬프트에 못박고 빠지면 다시 시도함.

## 학습 — `training/`

| 파일 | 무엇 |
|---|---|
| `build_training_data.py` | 후보 검색어를 여러 개 만들어 **실제 arXiv 검색으로 채점** → 정답 논문을 찾아낸 것을 라벨로, 못 찾은 것을 선호쌍의 거절 쪽으로 |
| `train.py` | `sft`(지도 미세조정) → `dpo`(선호 학습). 순서가 중요함 |

**핵심 아이디어**: 라벨을 사람이 "좋아 보이는" 기준으로 고르지 않고 **검색 성공을 신호로** 삼음.
**분할은 논문 단위로 함** — 같은 논문에서 나온 질문은 라벨이 거의 같아서, 질문 단위로 나누면
검증 손실이 실제보다 좋게 나오고 과적합 시작점을 놓침.

**한계 기록**: 이 방식은 "정답 논문이 몇 등인가"만 보상으로 삼았음. 그래서 Recall 은 조금
올랐고 만족도(nDCG)는 떨어졌음(#37). 다시 학습한다면 보상에 만족도를 넣어야 함.
