## 모듈 ① 쿼리 변환 모듈

### 담당하는 일

사용자가 입력한 검색어를 받아, **입력한 말 → 중간 개념 → 전문 학술 용어 → 최종 검색어**의
단계를 거쳐 검색에 쓸 전문 검색어로 다듬습니다. 입력은 완전한 일상어일 수도 있고, 이미
전문 용어가 섞여 있지만 논문이 실제로 쓰는 정확한 용어와는 어긋난 경우(대학원생)일 수도
있습니다. 두 경우 모두를 더 정확한 용어로 보정합니다. 이 프로젝트의 핵심 아이디어가 담긴 부분입니다.

### 구조와 코드

```
src/rewriter/
├── llm_client.py     # 언어 모델(Qwen3-4B)을 Ollama로 불러와 질문을 던지고 답을 받음
├── hierarchical.py   # 단계별 변환의 실제 로직 (아래 설명)
└── baselines.py      # 성능 비교를 위한 다른 변환 방식들
```

변환기는 모두 아래처럼 **똑같은 모양의 함수**를 갖도록 만듭니다. 이렇게 모양을 맞춰야,
나중에 성능 평가에서 변환 방식만 바꿔 끼우며 비교할 수 있습니다.

```python
# 입력: 사용자가 입력한 검색어 (문자열, 일상어이거나 전문 용어가 섞여 있을 수 있음)
# 출력: 변환 결과 (단계별 내용 + 최종 검색어들)
def rewrite(raw_query: str) -> RewriteResult
```

### 단계별 변환이 실제로 하는 일

언어 모델에게 아래 4단계를 순서대로 생각하게 시킵니다. 이렇게 생각 과정을 단계로
나누는 방식을 '단계별 추론(Chain of Thought)'이라고 합니다.

```
입력: "사진 보고 글로 설명해주는 AI는 요즘 어떻게 만들어?"

1단계 [의도 파악]   이미지를 입력받아 자연어 설명을 만들어내는 기술의 원리를 알고 싶어함
2단계 [핵심 개념]   이미지 이해 + 글 생성 + 두 가지를 합치는 것
3단계 [전문 용어]   image captioning, vision-language model, multimodal learning
4단계 [최종 검색어]  검색 방식별로 알맞은 형태로 만듦 (아래 표)
```

1~3단계의 결과는 나중에 웹 화면에서 "당신의 질문이 이렇게 전문 용어로 바뀌었어요"라고
사용자에게 보여 주는 데도 그대로 씁니다.

### 최종 검색어를 검색 방식별로 나눠 만드는 이유

검색 방식마다 잘 통하는 검색어의 형태가 다릅니다. 그래서 최종 검색어를 한 종류가 아니라
**세 종류로** 만듭니다.

| 어떤 검색용 | 검색어 형태 | 이유 |
|---|---|---|
| 단어 일치 기반 검색용 | 전문 용어를 나열 (예: `image captioning vision-language model`) | 단어가 겹쳐야 찾으므로 핵심 단어를 죽 나열 |
| 의미 기반 검색용 | 자연스러운 영어 문장 한 개 | 의미 검색은 문장 단위 뜻을 잘 잡음 |
| 실시간 arXiv 검색용 | arXiv 검색 문법 사용 (예: `abs:"image captioning" AND cat:cs.CV`), 300자 이하 | arXiv가 요구하는 문법이 따로 있음 |

### 변환기 종류 — 모두 같은 약속(`rewrite(질문) -> 변환결과`)을 따른다

평가 하네스에서 `--rewriter <이름>`으로 갈아 끼울 수 있다.

| 이름 | 파일 | 무엇을 하나 | 역할 |
|---|---|---|---|
| `passthrough` | `base.py` | 원본 질문을 그대로 검색 | **기준선.** 모든 비교에 반드시 포함 |
| `hierarchical` | `hierarchical.py` | Qwen3-4B로 의도→개념→학술용어를 한 번에 생성 | 학습 전 상태 |
| `single_step` | `baselines.py` | "학술 검색어로 바꿔줘"만 한 번 시킴 | 계층 구조의 이득을 가려내는 대조군 |
| `hyde` | `baselines.py` | 가짜 초록을 지어내 의미 검색에 씀 | 알려진 다른 방법과 비교 |
| `finetuned` | `finetuned.py` | 검색 성공을 보상으로 학습(SFT)한 모델 | — |
| `dpo` | `finetuned.py` | 위에 선호 학습까지 얹은 모델 | **현재 최고 성능** |

**중요한 구조 차이:** `hierarchical`은 학술 용어 목록만 내고 arXiv 검색 문법은
`build_arxiv_query()`라는 파이썬 함수가 조립한다. 언어 모델에게 문법을 맡겼더니 `AND`를
남발해 결과가 0건이 되는 문제가 있었기 때문이다(ISSUE #5). 반면 `finetuned`/`dpo`는
완성된 검색어 문자열을 통째로 생성하며, **의도·개념 같은 계층 출력을 하지 않는다.**
즉 **현재 가장 성능이 좋은 모델은 계층 변환기가 아니다.**

조립 규칙:
```
all:"사용자 원본 검색어" OR abs:"학술용어1" OR abs:"학술용어2" ...   (300자 이내)
```

## 모듈 ② 검색 모듈

### 담당하는 일

변환된 전문 검색어를 받아, 논문 모음(코퍼스)에서 관련 논문을 찾아 순위를 매겨 돌려줍니다.
결과로는 각 논문의 **제목과 초록**을 함께 줍니다(이번 프로젝트의 최종 출력).

### 구조와 코드

```
src/retrieval/
├── corpus.py       # 논문 모음 파일을 불러오고 원하는 분야만 거름
├── sparse.py       # 단어 일치 기반 검색
├── dense.py        # 의미 기반 검색
├── hybrid.py       # 두 검색 결과를 합침
└── arxiv_live.py   # 실시간 arXiv 검색 (옵션)
```

검색기도 변환기처럼 **똑같은 모양의 함수**로 맞춥니다.

```python
# 입력: 검색어(방식별로 준비된 것), 몇 개까지 가져올지(k)
# 출력: 점수 매겨진 논문 목록 (제목, 초록, 논문번호, 점수)
def search(queries, k: int) -> list[ScoredPaper]
```

### 세 가지 검색 방식 쉽게 설명

1. **단어 일치 기반 검색** (`sparse.py`)
   - 검색어의 단어가 논문 제목·초록에 실제로 얼마나 들어 있는지로 점수를 매깁니다.
     흔한 단어(the, model 등)는 점수를 적게, 드문 단어는 점수를 많이 줍니다.
   - 도구: **Elasticsearch**(검색 엔진 소프트웨어). 개발·검사 단계에서 이것을 켜기 번거로울
     때를 대비해, 똑같은 방식을 순수 파이썬으로 하는 가벼운 대체품(`bm25s`)도 함께 둡니다.

2. **의미 기반 검색** (`dense.py`)
   - 문장을 '의미를 담은 숫자 목록(임베딩)'으로 바꾸고, 숫자가 비슷한 논문을 찾습니다.
     단어가 정확히 안 겹쳐도 뜻이 비슷하면 찾아냅니다.
   - 숫자로 바꾸는 모델: **bge-m3** (여러 언어를 다뤄서, 한국어 질문으로 영어 초록을
     찾는 것도 가능).
   - 비슷한 숫자를 빠르게 찾는 도구: **FAISS**. 논문 3만 편 정도는 전부 하나씩 정확히
     비교해도 충분히 빠르므로, 복잡한 근사 방법 없이 정확 비교 방식을 씁니다.

3. **혼합 검색** (`hybrid.py`)
   - 위 두 검색은 각각 잘하는 상황이 다릅니다. 그래서 두 결과의 **순위를 합쳐** 더
     안정적인 결과를 냅니다.
   - 합치는 방법: **순위 합치기(RRF)**. 각 논문이 두 검색에서 각각 몇 등을 했는지만 보고
     정해진 공식으로 합칩니다. 두 검색의 점수 크기를 억지로 맞출 필요가 없어 다루기 쉽습니다.

### 실시간 arXiv 검색 (`arxiv_live.py`)

- 고정된 논문 모음에 없는 **최신 논문**까지 찾고 싶을 때 쓰는 옵션입니다.
- 이미 동작을 확인했지만(기존 `src/arxiv_search.py`), 정비가 필요합니다. 특히:
  - 결과 개수를 정하는 값은 `top_k_results`입니다. 지금 코드의 `load_max_docs=1`은
    **효과가 없는 설정**이라 상위 10개를 못 가져옵니다 → `top_k_results=10`으로 고쳐야 함.
  - 검색어에서 `:` `-` 기호를 지우는 옵션은 꺼 둬야 arXiv 문법 검색이 안 깨집니다.
- 자세한 주의사항은 [PLAN.md 3절](PLAN.md#실시간-arxiv-검색에서-주의할-점-코드로-직접-확인한-사실)과
  `reference/langchain_community/README.md`에 정리돼 있습니다.

## 모듈 ③ 성능 평가 모듈

### 담당하는 일

"쿼리를 변환하면 검색이 정말 좋아지는가"를 **주관이 아니라 숫자로** 보여 줍니다.
이를 위해 세 가지를 만듭니다.

1. **평가용 정답지** — 어떤 일상어 질문에 어떤 논문이 정답인지 모아둔 데이터.
2. **점수 계산 방법** — 검색 결과가 얼마나 좋은지 숫자로 매기는 방법.
3. **실험 실행 도구** — 여러 검색 조합을 돌려 점수를 내고 비교표를 만드는 코드.

---

### 3-1. 평가용 정답지를 어떻게 만드나

#### 왜 필요한가

검색 시스템이 좋은지 나쁜지 판단하려면, "이 질문에는 이 논문이 정답"이라는 **정답지**가
있어야 합니다. 문제는, 이런 정답지를 사람이 손으로 수백~수천 개 만들기가 매우 힘들다는
것입니다.

#### 기본 아이디어 — 거꾸로 만들기

보통은 '질문 → 정답 논문'을 찾지만, 우리는 순서를 뒤집습니다.

> **정답 논문을 먼저 고른 뒤, 그 논문을 찾고 싶어할 만한 일상어 질문을 만들어낸다.**

방법은 이렇습니다. 논문 한 편의 **제목과 초록**을 언어 모델에게 보여 주고 이렇게
시킵니다: *"이 분야를 잘 모르는 학부생이 이 논문을 찾고 싶을 때, 평소 말로 어떻게
검색할까? 그 질문을 만들어줘."* 그러면 **(일상어 질문, 정답 논문)** 한 쌍이 자동으로
생깁니다. 이걸 여러 논문에 대해 반복하면 정답지가 완성됩니다.

이 방식(논문에서 질문을 거꾸로 만들어내기)은 검색 연구에서 이미 널리 쓰이는 방법입니다.

#### 만드는 절차 (차례대로)

**1) 논문 뽑기** — 논문 모음(코퍼스)에서 여러 편을 무작위로 뽑습니다. 이때 분야가
한쪽으로 치우치지 않게 분야별로 골고루 뽑습니다.

**2) 질문 만들기** (`generate_queries.py`) — 뽑은 논문마다 언어 모델(이 단계에서는
품질 좋은 유료 모델을 잠깐 씀)에게 검색 질문을 만들게 합니다. 우리 사용자는 학부생부터
대학원생까지 넓으므로(0절), 질문도 그 폭을 담아야 합니다. 다양성을 위해:

- **어려움 3단계**: 실제 사용자층을 반영해 세 종류로 만듭니다.
  - 완전 일상어 — 예: "사진 보고 설명해주는 인공지능" (그 분야를 모르는 학부생)
  - 어설픈 전문어 — 예: "이미지 설명 생성 모델" (조금 아는 사람. **전문 용어를 쓰지만
    논문이 실제로 쓰는 정확한 용어와는 어긋남**)
  - 정확한 전문어에 가까움 — 예: "image captioning model" (대학원생 수준. 이런 입력에도
    변환이 도움이 되는지, 오히려 방해가 되지는 않는지 확인하는 용도)
- **언어 2가지**: 한국어 / 영어
- 동시에, 그 질문을 전문 용어로 바꾸는 **단계별 변환 예시**도 같이 만들게 해 둡니다.
  나중에 변환기의 예시(프롬프트)나 미세조정 재료로 재활용할 수 있습니다.

각 질문은 아래 형태로 저장합니다.

```json
{
  "query_id": "q00001",
  "arxiv_id": "2103.00020",          // 정답 논문 번호
  "lay_query": "사진 보고 설명 만들어주는 AI 어떻게 만들어?",
  "lang": "ko",                      // 언어
}
```

**3) 품질 나쁜 질문 걸러내기** (`filter_queries.py`) — 이 단계가 **평가 신뢰도를
좌우하는 가장 중요한 부분**입니다. 왜냐하면 언어 모델이 질문을 만들 때, 초록에 있는
전문 용어를 그대로 베껴서 질문에 넣어버리는 일이 자주 있기 때문입니다. 그러면
"일상어 질문"이 아니라 사실상 정답을 미리 알려주는 질문이 되어, 평가가 너무 쉬워지고
결과를 믿을 수 없게 됩니다. 그래서 아래 4가지로 거릅니다.

| 거르는 방법 | 무엇을 걸러내나 | 쉬운 설명 |
|---|---|---|
| 전문 용어 베끼기 검사 | 질문이 정답 논문의 드문 전문 용어를 그대로 담고 있으면 버림 | 질문과 정답 논문 제목·초록에서 **드물게 쓰이는 단어**가 겹치는지 봄. 겹치면 "일상어인 척 정답을 베낀 것"으로 보고 제외 |
| 자연스러움 검사 | 비전문가 질문 같지 않으면 버림 | 질문 만든 모델과 **다른** 모델에게 "이게 진짜 비전문가가 할 만한 질문인가?" 판정시킴 |
| 중복 제거 | 사실상 같은 질문이 여러 개면 하나만 남김 | 질문들을 숫자로 바꿔 서로 너무 비슷한 것끼리 하나만 남김 |
| 사람이 직접 검수 | 위 자동 검사가 놓친 것 | 무작위 100개를 직접 읽어보고 합격률을 기록(보고서에 씀) |

> '드물게 쓰이는 단어'를 찾는 원리: 모든 논문에 흔히 나오는 단어(model, method 등)는
> 신경 쓸 필요가 없고, 특정 논문에만 나오는 드문 전문 용어가 질문에 그대로 들어 있으면
> 베낀 것으로 봅니다. 이 '흔한 정도'를 계산하는 방식을 IDF라고 부릅니다.

**4) 개발용/시험용으로 나누고 고정하기** (`build_splits.py`) — 걸러낸 질문을 두 묶음으로
나눕니다.

- **개발용(200개)**: 만드는 동안 계속 보면서 변환기·검색기를 다듬는 데 씁니다.
- **시험용(300개)**: 마지막에 최종 성적을 잴 때 **딱 한 번만** 봅니다.

두 묶음을 나누는 이유는, 개발하면서 시험 문제를 미리 보고 맞추면 성적이 부풀려지기
때문입니다(마치 시험 전에 답을 외우는 것과 같음). 한 번 나눈 뒤에는 파일을 고정하고
버전을 붙여(`eval-v1`) 이후 바꾸지 않습니다. 그래야 실험 결과를 언제 돌려도 똑같이
재현됩니다.

#### 규모와 비용

- 개발용 200개 + 시험용 300개 (걸러낸 뒤 기준). 실사용자 수집은 이번엔 하지 않음.
- 질문 생성에 쓰는 유료 모델 비용은 저렴한 모델 기준 몇 달러 수준. 전체를 만들기 전에
  100개만 먼저 만들어 방식을 확정한 뒤 나머지를 만듭니다.

### 3-1-2. 실제로 구축된 데이터셋 스펙 (v1, 2026-07-17)

위 방법으로 실제 구축한 결과다. gpt-4o-mini로 생성, `corpus-v1`(논문 3만 편) 기반.

**만든 과정**: 논문 220편(6개 분야 균형 추출, 3번 배치에 나눠 생성) × 난이도 3개 =
질문 660개 생성 → 용어 누수 필터로 6개 탈락 → **654개** → 논문 단위로 train 300 / test 300
분할(양쪽 동시 분야 균형, 목표 개수를 맞추느라 54개 제외).

**파일** (`data/eval/`): `queries.raw.jsonl`(660, 생성 원본) →
`queries.filtered.jsonl`(654, 필터 통과) → `train.jsonl`(300, 개발용) +
`test.jsonl`(300, 시험용).

**총량**

| 파일 | 질문 수 | 논문 수 | 용도 |
|---|---|---|---|
| `train.jsonl` | 300 | 100 | 개발용 — 다듬는 동안 계속 봄 |
| `test.jsonl` | 300 | 100 | 시험용 — 최종 측정 때 한 번만 봄 |

- train과 test는 **정답 논문이 0편 겹침**(논문 단위 분할 → 정보 누수 없음).
- 질문은 논문 1편당 3개(easy/mid/hard). 양쪽 다 3개짜리 논문 100편으로 정확히 300씩.

**구성 (3개 축) — 양쪽 모두 균형**

| 축 | train (300) | test (300) |
|---|---|---|
| 난이도 | easy 100 / mid 100 / hard 100 | easy 100 / mid 100 / hard 100 |
| 언어 | en 156 / ko 144 | ko 153 / en 147 |
| 분야 | 6개 분야 각 48~51개 | 6개 분야 각 48~51개 |

train과 test 모두 세 축이 고르게 짜여, 어느 축으로 나눠 분석해도 양쪽에서 표본이 충분하다.
(분할 함수 `split_stratified`가 각 분야를 양쪽에 반씩 배정하도록 개선함.)

**핵심 특징 — "용어 격차"가 데이터에 실제로 담겨 있다**

질문이 정답 논문의 단어와 얼마나 겹치는지(질문 단어 중 논문 제목+초록에 실제 등장하는
비율). 낮을수록 사용자 말과 논문 용어의 격차가 크다 = 이 프로젝트가 풀려는 문제.

| (test 기준) | easy | mid | hard |
|---|---|---|---|
| 영어 질문 | 0.45 | 0.59 | 0.77 |
| 한국어 질문 | 0.01 | 0.01 | 0.03 |

(train도 거의 동일: 영어 0.49/0.63/0.77, 한국어 0.00/0.00/0.02)

여기서 서로 다른 두 '격차'가 드러난다.

- **영어 질문 = 용어 격차 축.** easy → mid → hard로 겹침이 0.46 → 0.63 → 0.77로 오른다.
  난이도가 "사용자가 논문의 정확한 용어에서 얼마나 멀리 있는가"를 실제로 조절한다.
  easy는 단어 일치 검색(BM25)에 불리해 **변환이 가장 도움이 될 지점**, hard는 이미 많이
  겹쳐 변환 없이도 잘 찾힐 지점.
- **한국어 질문 = 언어 격차 축.** 난이도와 무관하게 겹침이 거의 0. 한국어 단어는 영어
  초록과 애초에 글자가 안 겹치기 때문. 즉 한국어 질문은 **BM25가 사실상 무력**하고,
  (a) 영어 전문 용어로의 변환 또는 (b) 다국어 의미 기반 검색(bge-m3)만이 논문을 찾는다.

→ 이 두 축이 한 데이터셋에 함께 들어 있어, "변환이 용어 격차를 메우는가"와 "변환이
언어 격차를 메우는가"를 동시에 측정할 수 있다.

**한계**: ① 질문당 정답 1편(known-item)이라 재현율·MRR은 맞지만 정밀도·NDCG는 축퇴됨.
② 합성 데이터(실사용자 아님) — 현실성은 프롬프트 품질과 누수 필터에 의존. ③ 규모는
중간(질문 654 / 논문 220).

#### 정답지를 만들 때 arXiv API를 쓰나?

- **정답지 자체는 arXiv API 없이 만듭니다.** 정답 논문은 고정된 논문 모음(코퍼스, Kaggle
  파일에서 받은 것) 안에서 고르고, 질문은 유료 언어 모델이 만듭니다. 즉 "정답 논문 →
  질문"을 만드는 데는 API 호출이 필요 없습니다.
- arXiv API가 관여하는 곳은 두 군데입니다. ① 실시간 검색 트랙(3-3의 보조 비교)에서 실제로
  검색을 요청할 때, ② (선택) 만든 질문이 정말 정답 논문을 찾아내는지 arXiv에서 한번
  확인해 볼 때입니다.
- 이때 중요한 성격: **arXiv API는 검색어 하나에 논문을 여러 개(순위대로) 돌려줍니다**
  (코드로 확인, [PLAN.md 3절](PLAN.md#arxiv-api의-기본-성격--쿼리-1개--논문-여러-개-코드로-확인)).
  덕분에 "정답이 상위 몇 등에 있나"를 볼 수 있어 재현율·평균 역순위 평가가 가능합니다.
  또 논문 번호로 여러 편을 한 번에 가져오는 기능(`id_list`)이 있어, 특정 논문을 확인할 때
  편리합니다.

### 3-2. 점수를 어떻게 매기나 (평가 방법)

#### 무엇을 재는가 — 흔한 오해 바로잡기

**변환된 쿼리의 '텍스트'를 평가셋 쿼리와 비교하는 것이 아닙니다.** 쿼리끼리 글자를
견주는 부분은 코드 어디에도 없습니다. 재는 것은 검색 결과입니다:

```
평가셋 = (원본 질문, 정답 논문 ID)
  → 변환기가 질문을 검색어로 바꿈
  → 그 검색어로 코퍼스를 검색 → 논문 순위 목록
  → 채점: 미리 정한 정답 논문이 상위 K개 안에 몇 등으로 나왔나?
```

한 문장으로: **"변환 쿼리로 검색했을 때 정답 논문이 얼마나 위쪽에 나오는가"** 를 잽니다.
(known-item retrieval: 특정 논문 되찾기)

#### 대표 지표 두 가지

우리 정답지는 "질문 하나에 정답 논문이 딱 하나"인 구조입니다. 이 구조에 가장 잘 맞는
지표는 다음 둘입니다.

**① 재현율 (Recall@K)** — 정답 논문이 검색 결과 **상위 K개 안에** 들어왔으면 성공으로
칩니다. 여러 질문에서 성공한 비율이 재현율입니다.

- 예: `Recall@10 = 0.8`이면, 질문 100개 중 80개에서 정답이 상위 10개 안에 있었다는 뜻.
- K는 1, 5, 10, 20로 여러 개 봅니다. K=1은 "정답을 1등으로 맞혔나", K=10은 "상위 10개
  안에 있나"를 뜻합니다.

**② 평균 역순위 (MRR)** — 정답이 **몇 등**에 나왔는지까지 반영합니다. 정답이 1등이면
1점, 2등이면 0.5점(=1/2), 3등이면 약 0.33점(=1/3)을 주고, 이를 모든 질문에 대해 평균냅니다.

- 재현율은 "상위 10개 안에 있나/없나"만 보지만, MRR은 같은 '있음'이라도 1등인지 8등인지를
  구분합니다. 그래서 순위 품질을 더 세밀하게 봅니다.

#### 기획서의 정밀도·F1·NDCG는 왜 대표로 안 쓰나

처음 기획서에는 정밀도(Precision@K), F1, NDCG도 있었습니다. 그런데 "질문 하나에 정답이
딱 하나"인 상황에서는 이 지표들이 위 두 지표와 **사실상 같은 정보를 반복**하게 됩니다.

- 정답이 하나뿐이면 정밀도는 재현율을 K로 나눈 값이 되어 새 정보가 없습니다.
- F1은 그 둘을 섞은 것이라 역시 새 정보가 없습니다.
- 정답이 하나뿐인 NDCG는 결국 MRR과 거의 같아집니다.

이 점을 보고서에 정직하게 밝히면 오히려 평가 설계를 제대로 이해했다는 근거가 됩니다.

#### 정밀도·NDCG를 살리고 싶다면 (선택 확장)

정밀도와 NDCG가 진짜 의미를 가지려면 "정답이 여러 개이고, 각 논문의 관련도가 등급으로
매겨진" 정답지가 필요합니다. 이를 위해 시험용 질문 중 100개 정도를 골라:

1. 비교하는 모든 검색 방식의 상위 결과를 한데 모읍니다(질문당 수십 편).
2. 각 논문이 그 질문에 얼마나 관련 있는지 0/1/2 등급을 매깁니다. 등급은 질문을 만든
   모델과 **다른** 모델에게 매기게 하고, 일부는 사람이 직접 확인합니다.

이렇게 하면 정밀도·NDCG가 비로소 의미를 갖습니다. 시간이 없으면 생략하고, 있으면
보고서의 신뢰도를 크게 올려 줍니다. (이 여러 결과를 모아 등급 매기는 방식을 '풀링'이라
부릅니다.)

#### 시스템 자체에 대한 지표

성능(정확도) 외에, 실제 서비스로서의 품질도 잽니다.

- 변환에 걸리는 시간 (그래픽카드 있을 때 / 없을 때 각각)
- 질문 입력부터 결과까지 걸리는 전체 시간
- 변환 결과 형식이 깨진 비율

### 3-3. 무엇과 무엇을 비교하나

성능 비교의 뼈대는 **"변환 방식" × "검색 방식"의 모든 조합**입니다. 아래 표의 각 칸에
재현율·평균 역순위 점수가 채워집니다.

| 변환 방식 ↓ / 검색 방식 → | 단어 일치 검색 | 의미 기반 검색 | 혼합 검색 |
|---|---|---|---|
| 변환 안 함 (원본 질문 그대로) | | | |
| 한 번에 변환 | | | |
| 가상 답변 검색 (HyDE) | | | |
| **단계별 변환 (우리 방식)** | | | |

이 표에서 답을 얻는 질문들:

- **가장 중요한 질문:** 맨 윗줄(변환 안 함)과 맨 아랫줄(단계별 변환)을 비교 → "변환이
  효과가 있는가?"
- **차별점 질문:** 둘째 줄(한 번에 변환)과 맨 아랫줄(단계별 변환)을 비교 → "굳이
  **단계별로** 나눈 게 효과가 있는가?" (이게 있어야 우리 방식의 고유한 가치가 증명됨)
- **검색 방식 질문:** 각 줄에서 세 검색 방식을 비교 → "혼합 검색이 더 나은가?"

여기에 더해, 실시간 arXiv 검색으로 "기존 arXiv 검색창에 원본을 넣던 사용자 vs 변환
검색어를 넣는 경우"도 보조로 비교합니다(실제 서비스 개선 이야기).

### 3-4. 실험을 어떻게 돌리나 (`run_experiments.py`, `report.py`)

- **모든 결과를 파일로 저장(캐싱)합니다.** 변환 결과와 검색 결과를 파일로 남겨 두면,
  같은 실험을 다시 돌릴 때 시간을 아끼고, 언제 봐도 같은 결과가 나옵니다.
- **통계적으로 의미 있는 차이인지 확인합니다.** 점수가 조금 올랐다고 다 의미 있는 건
  아닙니다. 같은 질문들에 대한 두 방식의 점수 차이가 **우연이 아닌지**를 통계 검정으로
  확인합니다. 방법은 '부트스트랩'(질문을 무작위로 다시 뽑아 차이 분포를 보는 것)으로,
  p값과 95% 신뢰구간을 냅니다. → `metrics.py::paired_bootstrap`.
  - **지표 계산은 numpy로 직접 구현했습니다**(원래 계획의 `ranx` 라이브러리 대신).
    이유: 재현율·평균 역순위는 공식이 단순해 직접 구현이 더 투명하고, 추가 설치 없이
    어디서나 돌아갑니다. 나중에 원하면 ranx로 교차 검증만 덧붙일 수 있습니다.
- **첫 목표(달성):** 데모(`python -m evaluation.run_experiments --demo`)에서 "변환 전 vs
  임시 변환 × BM25" 비교표가 나옵니다. 진짜 변환기·검색기를 꽂으면 그대로 본 실험이 됩니다.

### 3-5. 평가 재정의 (2026-07-18) — '계단식 개선'을 핵심 평가로

지금까지의 평가에는 두 가지 논리적 한계가 있어, 사용자 구상('계층 변환 = 쿼리에 대한
CoT, 단계별로 검색 성능이 점점 높아짐')에 맞춰 평가를 확장한다.

**한계 A — 정답 1편(known-item)이 '만족도'와 어긋난다.** 질문을 특정 논문 1편에서 거꾸로
만들었기에 그 1편만 정답으로 친다. 그러나 실제로는 관련 논문이 여러 편이다. 검색기가 다른
좋은 논문을 상위에 올려도 '실패'로 채점되어, 지금 점수는 실제 검색 품질을 과소평가하거나
노이즈가 낀다. → 이것이 지표(Recall/MRR)의 문제가 아니라 **정답지(질문당 관련 1편)**의
문제라는 점이 핵심. 지표를 아무리 늘려도(Precision·NDCG·MAP) 정답 1편에서는 같은 정보로
붕괴한다(3-2 참조). **만족도를 재려면 정답지를 '관련 여러 편 + 관련도 등급'으로 확장한 뒤
NDCG 등을 써야 한다.**

**한계 B (핵심) — 지금은 '최종 쿼리'만 평가한다.** 사용자 구상의 본질은 "의도 → 개념 →
전문 용어로 단계를 밟으며 **검색 성능이 계단처럼 올라간다**"인데, 지금 평가는 계층의 마지막
결과물 하나만 검색에 쓴다. 즉 계단을 만들어놓고 맨 윗칸만 재고 있었다. (어제 "계층 vs
한번에 차이 없음" 결과도 이 관점에서 재해석 필요.)

**→ 계단식 평가(stage-wise) 도입.** 각 단계의 산출물을 검색어로 만들어 **단계마다 재현율을
측정**한다: 원본 → 의도 → 개념 → 전문 용어 순으로 Recall@10이 오르는지 본다. 이것이
사용자 가설을 직접 검증하는 실험이며, 그대로 웹 화면(모듈 ④)의 단계별 시각화 소재가 된다.
코드: `evaluation/stagewise_eval.py`.

**다음 계획(우선순위):**
1. **계단식 평가** — 단계별 검색 성능이 오르는지 검증(캐시 재사용, 저비용). ← 지금
2. **만족도 지표** — 정답지를 관련도 등급으로 확장(풀링+LLM 저지) → NDCG·Precision·MAP로
   만족도 측정. (지표는 이때 비로소 의미. 3-2의 '선택 확장'과 연결)
3. **변환기 재설계** — 각 단계가 검색용 쿼리를 명시적으로 내도록. dense 과잉 일반화(ISSUE #2)도 함께.
4. **웹 화면** — 단계별 변환 과정 + 최종 검색 결과 시각화.

### 3-6. 평가 하네스 재구축 (2026-08-07) — 지금의 공식 평가 방법

3-1~3-5는 로컬 논문 모음 위에서 재는 방식이었다. 그런데 그 점수(0.74)가 실제 서비스
성능(0.15)을 전혀 예측하지 못했다(ISSUE #10). 지금의 **공식 기준은 `arxiv_eval.py`** 이고,
서비스가 실제로 밟는 경로를 그대로 잰다.

```
질문 → 변환기 → arxiv 검색어 필드 → arXiv 실시간 검색 → 정답 논문이 몇 등인가
```

**설계상 중요한 결정 네 가지**

1. **검색된 논문 번호를 순위대로 전부 저장한다.**
   예전에는 "정답이 몇 등"만 남겨서, 깊이 30으로 돌린 결과로는 Recall@100을 알 방법이 없었고
   다시 재려면 arXiv를 처음부터 다시 불러야 했다. 이제 **한 번 돌린 결과로 어떤 깊이든
   재검색 없이 다시 계산**한다(`--report-only`).
2. **이어하기(resume).** 300문항 평가는 모델당 30~60분이라 중간에 끊기기 쉽다. 결과 파일에
   이미 있는 질문은 건너뛴다. **지금까지 40문항만 평가해 온 실질적 이유가 이것이었다.**
3. **부트스트랩 95% 신뢰구간을 함께 출력한다.** "Recall@10 = 0.35"만으로는 40문항짜리인지
   300문항짜리인지 알 수 없다.
4. **오류와 '결과 0건'을 엄격히 구분하고, 오류는 지표에서 뺀다.** 이 설계 덕분에
   arXiv 오류로 17.5%가 유실되던 것을 발견했다(ISSUE #8, #12).

**세 도구의 역할 분담**

| 도구 | 하는 일 |
|---|---|
| `arxiv_eval.py` | 모델 하나를 실제 서비스 경로로 평가 → 질문별 결과 저장 |
| `compare_runs.py` | 결과 파일 여러 개를 **공통으로 성공한 문항만 추려** 비교 + 짝지은 검정. 모델마다 오류 문항이 달라 그냥 평균을 비교하면 불공정하다(ISSUE #12). **기준선(변환 안 함)이 빠지면 경고한다** |
| `audit_dataset.py` | 평가 데이터 자체를 감사 — 분할 건전성 / 정답 누수 / 질문 현실성 / 지표 적합성 |

```bash
# 모델 하나 평가 (이어하기 자동)
python -m evaluation.arxiv_eval --queries data/eval/test.jsonl \
    --rewriter dpo --k 100 --out runs/test300_dpo.jsonl

# 저장된 결과만 다시 집계 (arXiv 호출 없음)
python -m evaluation.arxiv_eval --report-only results/test300_dpo.jsonl

# 모델 비교 — 기준선을 반드시 포함할 것
python -m evaluation.compare_runs results/test300_passthrough.jsonl \
    results/test300_hierarchical.jsonl results/test300_dpo.jsonl --k 10 --depth-table

# 데이터셋 감사
python -m evaluation.audit_dataset
```

### 3-7. 이 평가 데이터의 한계 — 점수를 읽을 때 반드시 함께 볼 것

`audit_dataset.py`가 자동으로 재는 항목이다. 분할 건전성(논문 겹침 0)과 정답 라벨
신뢰도(원출처가 전부 최고 등급)는 문제가 없지만, 다음 두 가지는 **점수 해석을 바꾼다.**

**① 난이도별로 도달 가능한 최대 점수가 다르다 (ISSUE #14)**

질문 하나에 정답 논문 1편만 세는데, 실제로는 사용자가 만족할 논문이 여러 편이다.
사람이 검증한 등급 정답지로 계산한 **완벽한 검색기의 이론적 상한**:

| 난이도 | 사용자가 만족할 논문 수(중앙값) | 단일정답 Recall@10 상한 |
|---|---|---|
| easy | 20편 | **0.61** |
| mid | 12편 | 0.79 |
| hard | 6편 | 0.90 |

→ **난이도 사이의 점수를 서로 비교하면 안 된다.** 같은 난이도 안에서 모델끼리만 비교한다.
easy의 낮은 점수는 시스템 성능이 아니라 과제 설계의 한계다.

**② hard 난이도에 정답 누수가 있다 (ISSUE #15)**

| 난이도 | 제목 내용어 겹침 평균 | 겹침 50% 이상 | 논문 고유 방법명 포함 |
|---|---|---|---|
| easy | 0.07 | 2% | 2% |
| mid | 0.12 | 6% | 2% |
| **hard** | **0.28** | **30%** | **14%** |

`SequenceMatch`, `CODER` 같은 **논문이 제안한 방법 이름이 질문에 그대로** 들어간 경우가 있다.
변환을 안 한 기준선조차 hard에서 0.400이 나오는 이유가 이것이다.

**③ 질문의 90~95%가 물음표로 끝나는 대화체다.** 실제 검색창 입력은 명사 나열형이라,
이 데이터의 점수가 실사용 성능을 덜 대표한다. 실사용자 질문 수집이 필요한 이유다.

## 모듈 ④ 웹 화면 모듈

### 담당하는 일

사용자가 질문을 입력하면, 변환 과정과 검색 결과를 보기 좋게 화면에 보여 줍니다.
"당신의 일상어가 이런 전문 용어로 바뀌었다"를 보여 주는 것이 이 시스템의 특징이자
발표 데모의 핵심입니다.

### 구조와 화면 구성 (1단계: Streamlit)

Streamlit(파이썬으로 웹 화면을 빠르게 만드는 도구)으로 먼저 만듭니다.

| 화면 요소 | 내용 |
|---|---|
| 질문 입력창 | 일상어 질문 입력 + 예시 질문 버튼 |
| 변환 과정 보기 | 1단계 의도 → 2단계 개념 → 3단계 전문 용어 → 4단계 최종 검색어를 차례로 표시 |
| 결과 카드 | 논문 제목, 초록(접기/펼치기), 분야, 날짜, arXiv 링크. 검색어와 겹친 단어를 강조 |
| 변환 전/후 비교 탭 | 원본으로 검색한 결과 vs 변환해서 검색한 결과를 나란히 → 개선을 즉석에서 보여줌 |
| 옵션 | 검색 방식 선택, 실시간 arXiv 검색 켜기/끄기 |
| 좋아요/싫어요 | 결과에 대한 사용자 반응을 저장 → 나중에 실사용자 평가 재료로 |

### 구현해야 할 것

- [ ] Streamlit 화면 (`app.py`) — 위 요소들
- [ ] 전체를 명령어 한 줄로 실행하는 배포 설정 (`docker-compose.yml`: 검색엔진 + 언어 모델 + 화면)
- [ ] (여유 시) 더 정식 웹 서비스 형태로 발전

## 공통 부품

각 모듈이 함께 쓰는 것들입니다.

- `src/config.py` — 모델 이름, 파일 경로, 검색 개수(K) 같은 설정값을 한곳에 모아 둠.

- `pyproject.toml` — 프로그램이 필요로 하는 다른 프로그램(라이브러리) 목록 정리.
  지금 `requirements.txt`에는 이 프로젝트와 무관한 것들과, 이름만 같고 실제로는 가짜인
  위험한 항목(`fitz 0.0.1.dev2`)이 섞여 있어 새로 정리 필요.
- `tests/` — 각 부품이 잘 도는지 확인하는 간단한 검사 코드.
