## 1. 지금 상태

### 시험용 342문항 성능 (2026-08-14 측정, 2026-08-16 재집계로 확인)

| 구성 | Recall@10 | nDCG@10 |
|---|---|---|
| **한국어를 영어로 옮겨 로컬 의미 검색** ← 가장 좋음 | **0.608** | **0.512** |
| 변환기(dpo) + 두 채널 | 0.570 | 0.442 |
| 로컬 의미 검색 단독 (번역 없음) | 0.553 | 0.484 |
| 변환기 없음 + 두 채널 | 0.553 | 0.458 |
| arXiv 단독 | 0.389 | 0.251 |

로컬 단독을 기준으로 짝지은 부트스트랩 검정:

| 비교 | Recall@10 | nDCG@10 |
|---|---|---|
| 번역 추가 | **+0.056 (p=0.001)** | **+0.027 (p<0.001)** |
| 변환기(dpo) + arXiv 채널 추가 | +0.018 (p=0.101, 판정 불가) | **−0.043 (p<0.001, 나빠짐)** |

목표는 Recall@10 0.70 이고 지금 0.608 임.

### 가장 좋은 구성의 층별 성능

| 구간 | Recall@10 | nDCG@10 | 후보 상한(깊이 100) | 회수율 |
|---|---|---|---|---|
| 전체 342문항 | 0.608 | 0.512 | 0.705 | 0.863 |
| easy (대학원생, 정확한 학술어) | 0.904 | 0.671 | 0.956 | 0.945 |
| medium (학부 연구생) | 0.658 | 0.539 | 0.772 | 0.852 |
| **hard (1~2학년, 일상어)** | **0.263** | 0.325 | **0.386** | 0.682 |
| 한국어 | 0.567 | 0.455 | 0.673 | 0.843 |
| 영어 | 0.649 | 0.568 | 0.737 | 0.881 |

난이도가 설계 의도대로 단조롭게 나옴(easy > medium > hard). 옛 평가셋은 이것이 뒤집혀 있어서
폐기했음(ISSUE #32). 새 평가셋의 숫자는 믿고 쓸 수 있음.

### 확정된 것

| 내용 | 근거 |
|---|---|
| 로컬 의미 색인 71만 편이 성능의 대부분을 만듦 | 옛 평가셋에서 +0.243, p<0.0001 |
| 교차 인코더 재정렬이 효과 있음 | 옛 평가셋에서 0.343 → 0.427, p<0.001 |
| 한국어를 영어로 옮겨 넣으면 좋아짐 | 시험용 한국어 Recall +0.111(p=0.001), 영어 대조군 +0.000 |
| 난이도 축이 제대로 작동함 | easy 0.904 > medium 0.658 > hard 0.263 |

### 반증된 것 (졸업작품 보고서에 그대로 실을 것)

| 내용 | 근거 |
|---|---|
| 계층 변환(의도→개념→용어)이 단계마다 검색을 좋게 함 | 세 번 측정해 세 번 반증 |
| 학습한 변환기(dpo)가 지금 구조에서 기여함 | Recall +0.018(판정 불가), nDCG −0.016(나빠짐) |
| 두 채널을 합치면 좋아짐 | Recall +0.018(판정 불가), nDCG −0.043(나빠짐), 옛 평가셋에서도 같은 결론 |

## 2. 지금 막고 있는 문제 (2026-08-16 직접 확인)

### 문제 1 — hard 층은 재정렬이 아니라 1차 검색에서 막힘

개발용 348문항에서 정답 논문이 71만 편 중 몇 등인지 끝까지 계산했음(깊이를 잘라 보지 않고
전 구간을 봄). 로컬 의미 검색 한 채널, 한국어는 번역문 사용.

| 깊이 | 10 | 100 | 300 | 1000 | 3000 | 10000 |
|---|---|---|---|---|---|---|
| 전체 | 0.466 | 0.635 | 0.721 | 0.782 | 0.845 | 0.894 |
| easy | 0.784 | 0.914 | 0.957 | 0.974 | 0.983 | 1.000 |
| medium | 0.491 | 0.707 | 0.802 | 0.853 | 0.931 | 0.948 |
| **hard** | 0.121 | **0.284** | 0.405 | 0.517 | 0.621 | 0.733 |

hard 층 116문항의 정답 등수 분포: 1~10등 14편 · 11~100등 19편 · 101~1000등 27편 ·
1001~10000등 25편 · **1만등 밖 31편**.

즉 hard 층 실패의 주된 원인은 순위를 못 올린 것이 아니라 **후보에 아예 없는 것**임.
재정렬 모델은 깊은 곳에서 끌어올리지 못함(아래 표).

| 정답의 1차 등수 | 1~10등 | 11~30등 | 31~100등 |
|---|---|---|---|
| 재정렬이 상위 10편에 살린 비율 | 0.953 (162/170) | 0.600 (18/30) | 0.683 (28/41) |

### 문제 2 — 서비스가 실제로 하는 일이 문서·평가와 다름 (ISSUE #39, #40)

`app.py` 를 읽고 실제로 실행해 확인한 사실임.

| | 문서가 말하는 것 | 코드가 실제로 하는 것 |
|---|---|---|
| 후보 합치기 | 순위 합치기(RRF) 로 두 채널을 합침 | **RRF 를 부르지 않음.** 로컬 결과를 앞에 놓고 이어 붙인 뒤 앞에서 300편만 자름 |
| arXiv 채널 | 최신성과 범위를 담당 | 로컬이 이미 300편을 채우므로 **arXiv 후보가 한 편도 재정렬에 못 들어감** (300편 중 0편) |
| 쿼리 변환기(dpo) | 서비스가 쓰는 변환기 | 결과물이 arXiv 검색어뿐이라 **결과에 영향 0.** 그래도 매 검색마다 호출되고 GPU 8.64GB 를 차지함 |
| 로컬 후보 깊이 | — | 서비스 300편, 평가 100편으로 **서로 다름** |

결과로 두 가지 문제가 생김.

1. **보고된 "서비스 성능 0.570" 은 서비스의 성능이 아님.** 실제 서비스는 번역 + 로컬 단독에
   가깝고, 그 구성은 시험용에서 0.608 이었음. 로컬 깊이도 300이라 후보 상한이 더 높음
   (개발용 기준 깊이 100 에서 0.635, 300 에서 0.721).
2. **arXiv 호출과 변환기 호출은 비용만 내고 결과에 기여하지 않음.** 응답 시간 약 5.1초와
   GPU 8.64GB 가 여기에 들어감.

같은 종류의 어긋남을 이미 두 번 겪었음(ISSUE #10, #13). 세 번째임.

### 문제 3 — 응답 시간이 기준을 넘음

| 단계 | 첫 질문 | 두 번째부터 |
|---|---|---|
| 논문 지목 확인 | 4.1초 | 0.4초 |
| 쿼리 변환 | 20.0초 | 3.5초 |
| 로컬 의미 검색 | 14.6초 | 0.2초 |
| arXiv 검색 | 1.5초 | 1.2초 |
| 재정렬 | 6.8초 | 1.3초 |
| 추천 이유 생성 | 26.1초 | 14.6초 |
| **합계** | **73.0초** | **21.1초** |

기준은 30초임. 질문 2개로만 잰 값이라 표본이 작음. 가장 큰 단계는 추천 이유 생성이고,
그다음이 arXiv 채널에 딸린 단계(논문 지목 확인 + 쿼리 변환 + arXiv 검색 = 5.1초)임.
문제 2 때문에 이 5.1초는 결과에 아무 영향도 주지 않으면서 소모되고 있음.

## 4. 다음 우선순위

### 1순위 — 서비스 구성을 확정하고 그 구성으로 다시 재기 (반나절)

**왜 먼저인가:** 지금 보고할 수 있는 서비스 성능 숫자가 없음. 문서의 0.570 은 실제 서비스와
다른 구성의 값임(문제 2). 이것을 고치지 않으면 이후 모든 실험이 "무엇을 개선한 것인지"
말할 수 없게 됨.

할 일: ⓐ `app.py` 의 후보 합치기를 정하기(arXiv 채널을 쓸 것이면 RRF 로 합치고, 안 쓸 것이면
호출 자체를 옵션으로 내림) ⓑ 로컬 후보 깊이를 서비스와 평가에서 같은 값으로 맞추기
ⓒ 그 구성으로 개발용에서 확인한 뒤 시험용에서 한 번만 확정 측정.

### 2순위 — 후보 깊이를 올렸을 때 실제 이득 측정 (개발용, 반나절)

**왜:** 깊이 100 에서 300 으로 늘리면 후보 상한이 0.635 에서 0.721 로 오름(위 표). 다만
재정렬이 31~100등에서 68%, 11~30등에서 60% 만 살리므로 상한이 오른 만큼 최종값이 오르지는
않음. **이득이 얼마인지는 재 봐야 알 수 있고, 로컬 검색은 호출 제한이 없어 비용이 거의 없음.**
재정렬 시간만 후보 수에 비례해 늘어나므로 응답 시간도 함께 잼.

### 3순위 — hard 층 대책 실험 (개발용, 하루)

**왜:** 미회수분이 가장 크고(0.263 대 상한 0.386), 이 프로젝트가 돕겠다고 한 사용자층임.
문제 1 에서 원인이 1차 검색으로 좁혀졌으므로 처방도 1차 검색 쪽이어야 함.

- 가장 싼 것부터: 일상어 질문을 **학술 문장으로 다시 쓴 뒤 로컬 의미 검색에 넣기**.
  번역이 통한 것과 같은 원리이고 학습이 필요 없음. HyDE 변환기가 이미 있으나 **로컬 채널에
  넣어 시험한 적은 없음**(지금까지 변환 결과는 전부 arXiv 채널로만 갔음).
- 그다음: 질문 하나로 검색어 여러 개를 만들어 각각 검색하고 합치기.
- 마지막: 임베딩 모델 미세조정. 비용이 가장 크므로 앞의 둘이 실패한 뒤에 판단.

### 4순위 — 서비스 마무리

응답 시간 재측정(질문 20개 이상), 추천 이유 생성 14.6초 줄이기, 좋아요/싫어요 적재,
`pyproject.toml`, 라이선스, docker 배포, 영문 README.
