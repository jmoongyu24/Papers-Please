## #36 파일이 중구난방으로 늘어나 유지 관리가 안 됐다 🟢

- **발생:** 2026-08-14, 사용자가 "뭐가 뭔지 모르겠다"고 지적
- **문제점:** 코드 파일이 **63개**, `data/eval/` 이 **17개** 까지 늘어 있었다. 원인은 셋이다.

  1. **기능마다 새 파일을 만들었다.** `evaluation/` 한 곳에 25개가 쌓였다.
     이름만 봐서는 무엇이 지금 쓰는 것이고 무엇이 죽은 것인지 알 수 없었다.
  2. **버전 접미사로 옛 코드를 남겨 뒀다.** `generate_queries.py` 와
     `generate_queries_v2.py`, `report.py` 와 `report_v2.py` 가 나란히 있었다.
     둘 중 어느 쪽이 진짜인지 파일만 봐서는 모른다.
  3. **폐기 판정을 받은 코드를 지우지 않았다.** 어휘 조회(#22), 용어 손질(#33),
     3만 편 시절 검색기가 전부 남아 있었다. **`build_rewriter` 가 아직 그것들을 부르고
     있어서**, 모르고 쓰면 조용히 성능이 깎이는 상태였다.
- **왜 위험한가:** 파일이 많은 것 자체보다, **어느 것이 진짜인지 알 수 없는 것**이 위험하다.
  실제로 평가셋에 `train.jsonl`(v1, 폐기) 과 `dev2.jsonl`(v2, 현행) 이 같이 있어서
  기본값을 잘못 잡으면 **폐기된 시험지로 재고도 알아채지 못한다.**
- **해결:** 디렉터리마다 코드 파일을 4개 이하로 통합하고, 폐기 판정 코드를 실제로 지웠다.

  | 위치 | 전 | 후 | 남긴 것 |
  |---|---|---|---|
  | `evaluation/` | 25 | **4** | `dataset` · `pipeline_eval` · `metrics` · `report` |
  | `src/retrieval/` | 12 | **4** | `corpus` · `local_index` · `arxiv_live` · `ranking` |
  | `src/rewriter/` | 11 | **4** | `base` · `baselines` · `finetuned` · `paper_resolver` |
  | `training/` | 5 | **2** | `build_training_data` · `train` |
  | `tests/` | 4 | **2** | `test_retrieval` · `test_evaluation` |
  | `data/eval/` | 17 | **4** | `dev` · `test` · `grades_dev` · `grades_test` |

  - 평가셋 이름에서 버전 표기를 뗐다: `dev2 → dev`, `test2 → test`,
    `qrels_v2_* → grades_*`. `qrels` 는 정보검색 용어라 직관적이지 않아 `grades` 로 바꿨다.
  - 중간 산출물(질문 원본·후보 풀)은 `data/eval/` 이 아니라 `runs/` 에 두기로 했다.
    **평가 폴더에는 실제로 평가에 쓰는 것만 둔다.**
  - 옛 실험 결과(`runs/` 28MB, `results/` 4MB)와 옛 질의 캐시(390MB)를 비웠다.
    전부 폐기된 v1 평가셋 기준이라 재사용할 수 없다.
- **검증:** 단위 테스트 37개 통과, 전 모듈 import 확인, 모든 명령줄 도구 동작 확인.
- **재발 방지 (규칙으로 남긴다):**
  1. **디렉터리마다 코드 파일 4개 이하.** 새 기능은 되도록 기존 파일 안에 넣는다.
  2. **`_v2` 같은 버전 접미사로 파일을 늘리지 않는다.** 새 방식이 옛 방식을 대체하면
     옛 코드를 지우고, 왜 바꿨는지를 여기와 코드 설명글에 남긴다.
  3. **폐기 판정을 내렸으면 그날 코드를 지운다.** 판정만 하고 남겨 두면 다음 사람이
     (또는 다음 세션의 내가) 그것을 살아 있는 선택지로 착각한다.

- **발생:** 2026-08-13, 후보 풀을 만들려다 `ModuleNotFoundError` 로 발견

  | `trl`, `datasets`, `accelerate` | 재학습 |

  알 수 없고, 무거운 실행을 시작해 몇 분 뒤에야 실패한다. 더 나쁜 경우는 일부만 빠져
  있어서 **조용히 다른 경로로 우회하는 것**이다.
- **해결:** 전부 설치해 복구했다(`sentence-transformers 5.7.0`, `transformers 5.15.0`,
  `torch 2.10.0+cu128`, CUDA 사용 가능).
- **재발 방지:** 무거운 실행을 시작하기 전에 의존성을 먼저 확인한다. `requirements.txt` 의
  각 줄을 실제로 `import` 해 보는 한 줄 점검이 몇 초면 끝난다.
- **부수 효과 하나:** 누수 재감사 도구(`audit_leakage_bilingual.py`)를 만들 때 `ollama`
  패키지 대신 HTTP API 를 직접 부르게 한 것이, 결과적으로 이 문제와 무관하게 돌아가는
  이유가 됐다. **감사 도구는 의존성이 적을수록 좋다**는 원칙이 실제로 값을 했다.

## #34 등급 정답지를 '질문을 만든 그 모델'이 채점했다 🔴

- **발생:** 2026-08-13, 평가 검증 담당이 평가셋 제작 파이프라인을 되짚다가 발견
- **문제점:** `evaluation/judge_relevance.py` 는 자기 파일 첫머리(11행)에 이렇게 적어 놓았다.

  > "**생성 모델과 다른 판정자**를 쓴다(자기 질문을 자기가 후하게 채점하는 편향 방지)."

  그런데 정작 `--model` 의 **기본값이 `gpt-4o-mini`**(105행)이고, 도움말은 "생성 모델
  (gpt-4o-mini)과 다른/강한 모델 권장"이라고 **자기가 위반하고 있음을 그대로 적어 두었다.**
  문서의 실행 예시(20행)도 `--model gpt-4o-mini` 다.
  질문 생성기는 `src/config.py:33` 의 `QUERY_GEN_MODEL = "gpt-4o-mini"` 이고,
  `data/eval/train.jsonl` 각 문항에 `gen_model=gpt-4o-mini` 로 기록돼 있다.
  → **지금 등급 정답지 90문항은 자기가 만든 질문을 자기가 채점한 것이다.**
- **영향:** 판정 품질 자체가 나쁘다는 뜻은 아니다. 사람 32건 블라인드 검증에서 가중 카파
  0.860 이 나왔다. 문제는 **편향의 방향이 검증되지 않았다**는 것이다. 자기가 만든 질문에
  후한 점수를 주면 → 만족스러운 논문 수가 과대평가되고 → **이론적 상한(#14)이 과소평가**된다.
  이 상한은 "목표 0.70 이 상한의 91%" 같은 핵심 서술의 근거이므로 영향이 작지 않다.
- **조치:** 새 평가셋을 만들 때 **생성기와 판정기를 서로 다른 계열로 고정**한다. 지금 예산
  계획(생성 gpt-5.4 계열 · 판정 gpt-4.1-mini)이면 추가 비용 없이 해결된다. 옛 등급 정답지
  90문항으로 계산한 상한값은 **"자기채점 조건에서 나온 값"** 이라고 표기해 인용한다.

## #33 검색어 용어 손질(term_repair)은 성능을 깎았다 — 폐기 ⚪

- **발생:** 2026-08-10 구현, 2026-08-13 판정
- **무엇이었나:** 변환기가 만든 검색어 중 **arXiv 에 아예 존재하지 않는 구**(예:
  `compact agent context compression` 0편, `architecture explanation` 1편)를 빼고, 실재하는
  더 짧은 부분 구로 바꾸는 모듈. 실사용 사례 두 건에서 착안한 것이라 문제의식은 옳았다.
- **실측 (시험용 300문항, 같은 조건):**

  | 지표 | dpo | repaired:dpo | 차이 |
  |---|---|---|---|
  | Recall@1 | 0.187 | 0.170 | −0.017 |
  | **Recall@10** | **0.343** | **0.320** | **−0.023** |
  | Recall@100 | 0.437 | 0.423 | −0.013 |

  **모든 K 에서 나빠졌다.** 검색어가 실제로 바뀐 85문항만 보면 0.424 → 0.341(−0.082) 로
  손해가 더 크다. 짝지어 세면 **새로 성공 3건, 새로 실패 10건**(부호검정 p=0.09 — 유의하진
  않지만 방향이 일관되게 나쁘다).
- **폐기 이유 셋:**
  1. 위 실측에서 **한 번도 이득이 없었다.**
  2. **실시간 서비스에서 쓸 수 없다.** 처음 보는 구의 문서 빈도를 세려면 코퍼스를 한 번
     훑어야 하고(310만 편, 약 4분) 그래서 모르는 구는 손대지 않고 넘기게 만들어져 있다.
  3. 붙는 자리가 arXiv 채널인데, 두 채널 구조에서 **arXiv 채널 전체의 기여가 +0.003** 이다
     (#29). 이 채널의 검색어를 다듬는 데 시간을 쓸 이유가 없다.
- **조치:** 코드는 비교군으로 남기되(`repaired:<바탕변환기>` 이름으로만 호출됨) **기본 실행
  경로에서 뺀다.** 같은 아이디어를 나중에 다시 시도하지 않도록 이 기록을 남긴다.
  아이디어가 짚은 문제(존재하지 않는 표현을 만들어내는 것)는 진짜였지만, **로컬 의미 검색이
  이미 우회했다** — 뜻으로 찾는 검색에는 문자열이 실재하는지가 상관없기 때문이다.
- ⚠️ 이 측정은 **시험용 300문항에서 돌아갔다.** 규칙 위반이 이미 일어난 상태다(#25).
  결론이 "버린다"라 오염 영향은 작지만, **앞으로의 탐색은 학습용에서만** 한다.

## #32 hard 난이도 0.970 은 실력이 아니라 설계상 누수다 🔴

- **발생:** 2026-08-13, 세 담당(총괄·검색 개발·평가 검증)의 교차 점검
- **문제점:** 시험용 300문항에서 난이도별 Recall@10 이 easy 0.390 · mid 0.680 · **hard 0.970**
  으로, 어려울수록 잘 맞히는 뒤집힌 모양이 나왔다. 원인은 데이터 생성 프롬프트에 있다.

  `evaluation/generate_queries.py` 의 hard 지시문:
  > "…**제목의 자구와 완전히 일치하지 않도록 단어 순서를 바꾸거나 동의어를 결합**하여
  > 전문적인 검색어로 구성한다."

  즉 hard = **논문 제목을 어순만 바꾼 것**이다. 이것은 글자 일치를 요구하는 arXiv 키워드
  검색에는 어렵지만, **뜻으로 찾는 의미 검색에는 가장 쉬운 형태**다. 난이도 축이 옛 검색기
  기준으로 설계돼 있어서 **새 검색기에 대해서는 뒤집혀 있다.**
- **증거 둘 — 이론적 상한을 넘었다.** #14 의 등급 정답지로 다시 계산한 상한과 실측:

  | 난이도 | 이론적 상한 [95% 신뢰구간] | 실측 |
  |---|---|---|
  | easy | 0.612 [0.504, 0.722] | 0.390 |
  | mid | 0.791 [0.708, 0.868] | 0.680 |
  | **hard** | **0.897 [0.821, 0.963]** | **0.970 ← 상한 초과** |

  완벽한 검색기도 못 넘는 값을 넘었다. 질문 안에 원출처를 특정하는 정보가 있다는 뜻이다.
- **증거 셋 — 누수 감사 도구에 한국어 사각지대가 있다.** `evaluation/audit_dataset.py:48` 의
  `content_words()` 가 `[A-Za-z][A-Za-z0-9\-]+` 정규식이라 **한글을 한 글자도 세지 않는다.**
  그래서 아래 같은 문항이 "겹침 0.024, 깨끗함"으로 통과했다.

  | 한국어 hard 질문 | 정답 논문 제목 |
  |---|---|
  | "직접 음성 번역을 위한 순환 피드백을 활용한…" | *Cascaded Models With **Cyclic Feedback** For **Direct Speech Translation*** |

  **제목의 완전한 한국어 번역**이다. 다국어 임베딩 모델(bge-m3)은 번역을 그대로 꿰뚫는다.
  → **#15 의 "hard 30% 누수"는 영어 문항만 센 과소 집계다.**
- **영향:** 전체값 0.680 = (0.390 + 0.680 + 0.970) / 3 이므로 hard 층 하나가 전체를 **0.048**
  끌어올린다. **hard 를 뺀 정직한 값은 0.535** 이고, 목표 0.70 까지 0.020 이 아니라 **0.165**
  남았다. "목표에 근접했다"는 서술은 철회한다.
- **조치(미완료):** ⓐ 헤드라인 수치에 hard 를 넣을 때는 반드시 "hard 제외 0.535" 를 함께
  적는다. ⓑ `content_words()` 를 한국어까지 세도록 고친다. ⓒ 한국어 문항을 영어로 번역해
  겹침을 다시 재고, **임계값 하나로 자르지 말고 겹침 구간별로 층화 보고**한다.
  ⓓ 새 평가셋을 만들 때 난이도 축을 검색 방식과 무관하게 다시 정의한다.

## #31 상한 계산이 실제 재정렬 입력과 어긋났다 — #26 의 재발 🟢

- **발생:** 2026-08-13, 검색 개발 담당과 평가 검증 담당이 **서로 모르는 채 같은 결함을 발견**
- **문제점:** `evaluation/pipeline_eval.py` 가 상한과 재정렬 입력을 **다른 방식으로** 만들었다.

  | | 어떻게 만드나 | 값 |
  |---|---|---|
  | 보고된 "상한" | 채널마다 상위 300편을 모은 **합집합** (`union_rank`) | 0.823 |
  | **실제 재정렬 입력** | 그것을 RRF 로 합쳐 **상위 300편만** (`fused_ids_of`) | **0.797** |

  융합이 정답 8편을 300등 밖으로 밀어냈다. 그 0.026 은 **융합 탓인데 재정렬 탓으로** 넘어가
  있었다. 회수율이 82.6% 로 보였지만 실제로는 **85.4%** 다.
- **왜 위험한가:** 지표 값은 맞는데 **처방이 뒤바뀐다.** 손실이 재정렬 탓이면 재정렬을 고쳐야
  하고, 융합 탓이면 융합을 없애야 한다. 정반대 작업이다.
  (재정렬기는 후보의 **순서를 보지 않고 어떤 논문이 들어 있는지만** 본다. 그렇다면 후보 수를
  줄이는 융합을 재정렬 앞에 둘 이유가 없다 — 손해만 된다.)
- **#26 과 무엇이 다른가:** #26 은 '깊이'가 어긋난 것이었고 이번은 '집합을 만드는 방식'이
  어긋난 것이다. **같은 종류의 실수가 다른 자리에서 되살아났다.**
- **해결:** ⓐ `rerank_pool_rank()` 를 새로 만들어 **재정렬이 실제로 본 후보**로 상한을 잰다.
  ⓑ 보고를 세 줄로 나눠 **① 채널 합집합 → ② 재정렬 입력 → ③ 최종** 을 각각 찍고, 손실을
  **융합 몫과 재정렬 몫으로 갈라서** 보여준다. ⓒ 재정렬할 때 깊이를 문항에 새겨(`rerank_depth`),
  나중에 재집계할 때 명령줄 기본값으로 상한을 재는 세 번째 재발을 막았다.
  ⓓ 세 경우를 단위 테스트로 못박았다(`tests/test_pipeline_eval.py`).

## #29 "하이브리드로 올랐다"는 잘못된 공로 배분이었다 🟡

## #28 서비스용 검색기에 색인·코퍼스 짝 확인이 없었다 🟢

- **문제점:** 줄 위치표는 **그 코퍼스 파일 전용**이다. 다른 파일에 갖다 쓰면 `seek` 이 엉뚱한

  | `evaluation/pipeline_eval.py` `TextLookup` | 했다 | 다만 **파일 이름만** 비교 |

  - 지문이 우연히 같아도 내용이 밀린 경우까지 잡도록 **표본 대조**를 생성자에 넣었다.

## #26 재정렬 깊이와 상한 계산 깊이가 어긋나 회수율이 부풀려졌다 🟢

## #25 학습용 300문항이 이미 변환기 학습에 소모돼 있었다 🟡

  그러면 깨끗한 시험지가 시험용 300 하나뿐인데, 시험용은 이미 재정렬 방식 선택과 깊이

- **대응:** 71만 편 코퍼스에서 개발용 질문을 새로 만든다. 이때 **평가용 정답 논문 200편에서는
  질문을 만들지 않는다**(만들면 평가 질문과 학습 질문이 같은 초록에서 나온 쌍둥이가 된다).

## #24 후보 확보율이 천장이었다 — 검색 경로를 둘로 늘려 해결 🟢

| 어휘 조회 평가에서 **정답 논문을 조회 대상에서 안 뺐다** | 시스템이 정답 논문의 초록을 그대로 베껴 용어를 만듦 | 조회 이득을 **2배 부풀림**(성공률 24%→49%), 최종 성능 +0.073 과대평가 |
| 전제 확인 실험에서도 **같은 실수 반복** | "1차 검색이 잘 된다(81.3%)"는 결론이 부풀려짐 | 코퍼스 확장 판단의 근거가 오염 |
| 스모크 스크립트가 **LLM 을 두 번 로드** | GPU 메모리 부족 → 임베더가 CPU 로 밀려남 | 검색 품질이 떨어진 상태로 **"결과가 나쁘다"고 잘못 보고** |
| 상용구 필터를 **잘못된 순서로 구현** | 거른 자리를 다음 순위로 채워, 더 넓고 엉뚱한 용어가 들어옴 | 스모크에서 8/10 → 5/10 악화 (발견 후 수정) |
| 대리 지표를 **개입과 무관한 축으로 설계** | '좋은 용어가 있는가'만 재는 지표로 '잡음이 적은가'를 판단하려 함 | 넓은 절 쳐내기 실험이 무의미해짐 |

**앞으로 실험 전에 반드시 확인할 것:**

1. **정답이 시스템에 새어들어가지 않는가.** 평가셋의 정답 논문은 `corpus-v1` 에 전부 들어
   있다. 로컬 코퍼스를 쓰는 모든 부품(어휘 조회·재정렬 후보·학습 라벨)은 **정답 논문을
   제외했는지** 명시적으로 확인한다. 실사용에서 사용자가 찾는 논문이 우리 3만 편에 있을
   확률은 arXiv cs 의 2.3% 뿐이다.
2. **측정 지표가 개입과 같은 축인가.** "무엇을 바꿨는데 무엇이 변할 것으로 기대하는가"를
   먼저 적고, 그 변화를 잡아내는 지표인지 확인한다.
3. **비교 대상의 문항 집합이 같은가.** 결과 0건·오류로 빠진 문항을 실패로 세지 않으면
   기준선이 부풀려진다(passthrough 를 그렇게 재면 0.257 이 0.467 로 보인다).
4. **자원이 충분한가.** GPU 메모리가 모자라면 모델이 조용히 CPU 로 오프로드되어 품질이
   떨어진다. 실행 로그에 `meta device` / `offloaded` 경고가 없는지 확인한다.
5. **개수를 억지로 채우지 않는가.** 라벨 생성·어휘 조회 양쪽에서 "k개를 채우려다 쓰레기가
   들어오는" 문제를 겪었다. 자격 미달이면 개수가 줄어드는 것이 맞다.
6. **결과가 예상과 맞으면 더 의심한다.** 오늘 부풀려진 두 수치는 모두 '기대한 방향'이라
   그냥 믿었다. 반대로 예상과 어긋난 결과(넓은 절이 무해함)는 재확인해서 진짜였다.

## #22 어휘 조회 평가에 정답 논문이 새어들어감 🟢

- **발생:** 2026-08-10, 어휘 조회 코드를 다시 읽다가 발견
- **문제점:** `GroundedRewriter.rewrite()` 가 `lookup(raw_query, k=6)` 을 부를 때
  **정답 논문을 제외하지 않는다.** 그런데
  - test 정답 논문 100편은 **전부 `corpus-v1`(조회 코퍼스)에 들어 있다** — 거기서 만들었으므로
  - 1차 의미 검색이 정답 논문을 상위 20에 넣는 비율이 **81.3%**

  즉 어휘 조회가 **정답 논문 자신의 초록에서 용어를 그대로 베껴오고** 있었다. 실제 서비스에서
  사용자가 찾는 논문이 우리 3만 편에 있을 확률은 낮으므로(arXiv cs 의 2.3%) 비현실적 조건이다.
- **편향의 크기 (test 앞 150문항, 둘 다 깊이 200 + 재정렬):**

  | 조건 | Recall@1 | Recall@10 |
  |---|---|---|
  | 정답 논문 포함 (기존 측정) | 0.440 | **0.540** |
  | 정답 논문 제외 (실사용 조건) | 0.387 | **0.467** |
  | 차이 | −0.053 | **−0.073** [−0.120, −0.027], p=0.001 |

  조회 성공률 자체도 **49.3% → 24.0%** 로 반토막이었다.
- **편향을 걷어낸 뒤 어휘 조회의 진짜 순 기여:**

  | | Recall@10 |
  |---|---|
  | dpo + 재정렬 (조회 없음, 깊이 100) | 0.427 |
  | 조회 + 상용구필터 + 깊이200 (편향 제거) | 0.467 |
  | 차이 | **+0.020** [−0.027, +0.073], **p=0.508** |

  **어휘 조회·상용구 필터·깊이 2배를 전부 합쳐도 순 기여가 노이즈와 구분되지 않는다.**
- **판정:** #19(어휘 조회)와 상용구 필터의 "효과 있음" 결론을 **철회한다.** 다만 스모크
  테스트에서 `object goal navigation`·`depth separation` 같은 좋은 용어를 실제로 가져온 것은
  사실이므로, **known-item 지표로는 판단이 안 되는 것일 수 있다.** 만족도 평가(NDCG)를
  arXiv 경로에 적용한 뒤 다시 판단한다. 그때까지 서비스 적용 여부는 보류.

## #21 규모를 키우는 접근이 전부 막힘 ⚪

성능을 올리려고 시도한 '규모 확대' 여섯 가지의 결과를 한곳에 남긴다. **전부 수확 체감이거나
무효였고, 원인이 하나로 수렴한다.**

| 시도 | 결과 |
|---|---|
| **후보 깊이 100 → 200** | 천장 0.513 → 0.540. 최종 R@10 0.493 → 0.517 (p=0.017). 호출 1회→2회. 150은 200과 호출 수가 같아(`page_size=100`) 선택할 이유가 없다 |
| **조회 코퍼스 확대** | 대리 실험(코퍼스를 줄여가며 측정)에서 **2만 편에서 포화**: 5천 17.3% · 1만 20.7% · 2만 24.7% · 3만 24.0%. 128만 편으로 43배 늘려도 기대 이득이 거의 없어 **보류** |
| **이웃 논문 수 20 → 100** | 24.0% → 28.7%, 용어는 오히려 넓어짐(159편 → 328편) |
| **검색어 분리(multi-query)** | 최종 실패 문항 중 96/145 가 이미 정답에 걸리는 용어를 가졌으나, 그 용어 **하나만으로 검색해도 상위 10 회수 5.0%**. OR 희석이 원인이 아니었다 |
| **정답 논문 라벨로 재학습** | 매칭률 0.79 → 0.22~0.33 **악화** (#17) |
| **어휘 조회 + 상용구 필터** | 편향 제거 후 p=0.508 (#22) |

**수렴하는 원인:** 정답 논문이 `anomaly detection` 대신 `anomaly segmentation` 을 골랐다는
사실은 **질문만 보고 알 수 없다.** 실패 용어의 63%가 이런 '거의 맞음'이다. 모델을 키우거나
데이터를 늘리거나 후보를 더 가져와도 이 벽은 그대로다.

**남은 길로 보이는 것:** 지표를 바꾸는 것. 지금은 "질문 하나에 정답 논문 1편"을 세는데,
사람이 검증한 등급 정답지 기준 이론적 상한이 easy 0.61 / mid 0.79 / hard 0.90 이다(#14).
사용자가 원하는 것이 '관련 논문 10편 추천'이라면 **그것을 재는 지표(NDCG)를 아직 안 쓰고 있다.**

## #18 재정렬 계층 도입 — 순위 문제를 직접 해결 🟢

- **발생:** 2026-08-09
- **문제점:** 최종 모델의 Recall@100 = 0.490 인데 Recall@10 = 0.343 이었다. 즉 **정답의
  14.7%가 이미 후보 100편 안에 들어와 있는데 순위가 낮아 사용자 눈에 안 띈다.** arXiv 는
  키워드 일치도로 순위를 매기므로 '사용자가 무엇을 원하는지'를 모른다.
- **해결:** `src/retrieval/rerank.py` 를 **교차 인코더**(`BAAI/bge-reranker-v2-m3`, 568M,
  다국어)로 다시 구현하고, 후보 100편을 **원본 질문**과의 관련도로 다시 줄 세운다.
  변환된 검색어가 아니라 원본 질문을 쓰는 이유는, 재정렬의 목적이 '사용자 의도와 맞는가'를
  보는 것이기 때문이다.
- **측정 방법(중요):** `evaluation/rerank_eval.py` 신설. 평가 결과에 저장해 둔 논문 번호와
  arXiv 검색 캐시(제목·초록 포함)를 합쳐 후보를 복원하므로, **재정렬 방식을 바꿔 가며 몇 번을
  실험해도 arXiv 요청이 한 건도 발생하지 않는다.**
- **결과 (test 300문항, 최종 모델 위에서):**

  | K | 재정렬 전 | 재정렬 후 | 변화 | p값 |
  |---|---|---|---|---|
  | 1 | 0.173 | **0.393** | +0.220 | <0.001 |
  | 5 | 0.277 | 0.457 | +0.180 | <0.001 |
  | **10** | 0.343 | **0.467** | **+0.123** | **<0.001** |
  | 30 | 0.420 | 0.477 | +0.057 | <0.001 |

  재정렬의 상한은 그 실행의 Recall@100(0.490)이다. **0.467 은 회수 가능한 몫의 95%다.**

- **교차 인코더 vs 임베딩 유사도 (같은 조건 비교):**

  | K | 교차 인코더 | 임베딩 유사도 |
  |---|---|---|
  | 1 | **0.393** | 0.303 |
  | 10 | **0.467** | 0.450 |

  질문과 논문을 함께 넣어 판단하는 교차 인코더가 낫고, **상위 순위일수록 차이가 크다.**
  임베딩 방식은 두 글을 따로 인코딩해 내적만 재므로 미세한 적합성 판단이 약하다.

- **네 변환기 전부에 적용한 결과 (전체 300문항 기준):**

  | 변환기 | 재정렬 전 | 재정렬 후 | 변화 |
  |---|---|---|---|
  | 변환 안 함 | 0.167 | 0.257 | +0.090 |
  | 계층 변환 | 0.220 | 0.350 | +0.130 |
  | 검색보상 학습(dpo) | 0.343 | 0.427 | +0.083 |
  | **+ 어휘 조회(최종)** | 0.343 | **0.467** | +0.123 |

  **① 재정렬은 모든 변환기에서 유의미하게 이득이다**(전부 p<0.001).
  **② 그러나 재정렬이 변환을 대체하지는 못한다.** 변환 안 함에 재정렬만 붙이면 0.257 이고,
  변환까지 있으면 0.467 이다(+0.210, p<0.001). 두 층은 서로 다른 일을 한다.
  **③ 측정 함정 하나:** `passthrough` 는 한국어에서 결과 0건이 45%라 후보 자체가 없다.
  그 문항을 빼고 재면 재정렬 후 0.467 로 보이지만, **전체 300문항 기준으로는 0.257**이다.
  결과가 없는 문항을 실패로 세지 않으면 기준선이 부풀려진다.

## #17 정답 논문에서 라벨을 뽑아 학습시키기 — 시도와 실패 🔴

- **발생:** 2026-08-08~09
- **의도:** 학습 데이터 생성을 arXiv API 에서 로컬 스냅샷으로 옮기고(정책 취지 + 속도),
  **정답 논문에서 좋은 용어를 직접 뽑아 라벨로** 삼는다. 기존 방식(변환기가 후보를 만들고
  arXiv 로 채점)은 라벨 확보율이 28%였고 1회 생성에 arXiv 를 1,147회 불렀다.
- **만든 것:**
  - `src/retrieval/phrase_stats.py` — 구가 arXiv 몇 편에 등장하는지 세는 도구.
    코퍼스를 한 번만 훑으며 수천 개를 동시에 세고 디스크에 보관한다.
  - `data/corpus/corpus-full.jsonl` — arXiv **전체 310만 편**(문서 빈도를 arXiv 와 비슷한
    규모로 재기 위함). `corpus.py` 에 분야 제한 없는 구축 기능 추가.
  - `training/make_labels.py` — 정답 논문의 2~4단어 구 중 (a) 문장 조각이 아니고
    (b) 문서 빈도가 목표 구간이며 (c) 제목·반복으로 뒷받침되고 (d) 질문과 의미가 가까운 것을 고른다.
- **중간 성과:** 라벨 확보율 28% → **100%**, arXiv 호출 1,147회 → **0회**.
  라벨 자체를 arXiv 로 검증하니 Recall@10 = 0.656 / Recall@100 = 0.833 이었다(90문항).
- **그런데 학습은 실패했다:**

  | 체크포인트 | 출력 길이 | 용어 수 | 정답 논문에 걸린 비율 |
  |---|---|---|---|
  | 에폭1 | 609자 | 16.1 | 형식 미학습(무한 반복, 300자 상한의 2배) |
  | 에폭2~8 | 97~156자 | 2.8~4.0 | **0.22~0.33** |
  | *기존 dpo* | *126자* | *3.8* | ***0.79*** |

- **왜 실패했나 (근본 원인):** 라벨은 **그 논문 고유의 좁은 용어**(문서 빈도 중앙값 102편)를
  가르친다. 학습 논문에서는 외우지만, **처음 보는 논문의 고유 용어는 질문만 보고 알 수 없다.**
  학습이 진행될수록 학습 논문에 특화되고 일반화는 나빠졌다. 논문 단위로 검증셋을 나눈 뒤에는
  **검증 손실이 1에폭부터 계속 상승**했다.
- **부수 발견 — 검증 누수:** 기존 `train_lora.py` 가 **질문 단위로** 검증셋을 나누고 있었다.
  같은 논문에서 나온 세 질문은 라벨이 거의 같아 검증 손실이 실제보다 좋게 나온다.
  → 논문 단위 분할로 고쳤다(`split_by_paper`). **이전의 "3에폭이 최적"이라는 판단도
  이 누수 때문에 낙관적이었을 가능성이 있다.**
- **결정적 단서 (다음 방향으로 이어짐):** 실패한 용어 684개를 뜯어보니 **63%가 '거의 맞음'**
  이었다. `covid-19 dataset`(논문에는 `covid-19 data`), `anomaly detection`(논문에는
  `anomaly segmentation`) 처럼 의미는 맞는데 **문자열이 달랐다.** arXiv 의 `abs:"구"` 는
  정확한 문자열 매칭이라 한 글자만 달라도 걸리지 않는다.
  → **생성 모델에게 '실재하는 정확한 문자열'을 맞히라고 요구하는 것 자체가 무리다.**
- **상태:** 🔴 이 노선은 현재 데이터 규모(논문 100편)에서 막다른 길로 판단. 대신 #19 로 전환.
  (학습 자산은 보존: `data/training/labels_train.jsonl` 300개, `models/qwen3-4b-query-lora-v2`)

- **발생:** 2026-08-09, #17 의 실패 진단에서 도출
- **착안:** 모델이 좁은 용어를 못 만든다면, **실제 논문에서 가져오면 된다.** 조회한 구는
  arXiv 에 실재하는 문자열임이 보장되므로 '거의 맞음' 실패가 원천적으로 사라진다.
- **구현:** `src/rewriter/vocab_lookup.py` + `src/rewriter/grounded.py`

  ```
  질문 → 로컬 코퍼스 의미 검색(bge-m3, 다국어) → 주제가 비슷한 논문 20편
       → 그 논문들의 구 추출 → 문서 빈도 20~1,000편만 → 여러 논문에서 공통인 것 우선
       → 모델이 만든 용어와 **합쳐** arXiv 검색어 조립 (좁은 것을 앞에 두어 300자 제한에서 살림)
  ```

- **1차 검색 방식이 결정적이었다:**

  | 1차 검색 | 조회한 구가 정답 논문에 있는 비율 |
  |---|---|
  | BM25 | 0.192 (한국어에서 0건이라 무너진다) |
  | **의미 검색(bge-m3)** | **0.350** |

- **왜 '대체'가 아니라 '보태기'인가:** 모델 용어는 정답에 걸리는 비율이 0.793 이지만 넓고
  (중앙값 3,191편), 조회 용어는 0.350 이지만 좁다(20~1,000편). 서로 보완적이다.
- **결과:**

  | 지표 | dpo | + 어휘 조회 | p값 |
  |---|---|---|---|
  | **Recall@100** (후보 확보) | 0.437 | **0.490** | **0.044 유의미** |
  | Recall@10 (재정렬 후) | 0.427 | 0.467 | 0.122 불확실 |

  영어에서 Recall@100 이 0.449 → **0.503** 으로, **처음으로 기준선(0.483)을 넘었다**
  (#13 에서 "영어에서는 변환이 이득이 없다"고 기록한 문제가 완화됨).
- **정직한 판정(당시):** 후보 확보(Recall@100)는 유의미하게 개선했으나 최종 Recall@10 은
  미확정(+0.040, p=0.122).
- **최종 판정(2026-08-10):** **철회.** 위 이득의 상당 부분이 정답 논문을 조회에 포함시킨
  편향이었다(#22). 편향 제거 후 조회+필터+깊이200 을 전부 합쳐도 +0.020 (p=0.508).
- **한계:** 조회 코퍼스가 3만 편이라 주제 범위가 제한적이다. 1차 의미 검색이 주제를 못 맞히면
  어휘도 얻지 못한다(닭과 달걀). 그래서 모델 용어를 빼면 안 된다.

## #20 폐기된 가설 두 개 (실측으로 반증) ⚪

기록으로 남긴다. 둘 다 그럴듯했지만 데이터가 반대였다.

**① "넓은 절이 정답을 파묻는다 → 넓은 절을 쳐내야 한다"**

검색어 전체의 합집합 크기(모든 절의 문서 빈도 합)와 성공률 사이에 **단조 관계가 없었다.**

| 합집합 크기 | 0~5천 | 5천~2만 | 2만~5만 | 5만~15만 | 15만+ |
|---|---|---|---|---|---|
| 실제 성공률 | 0.411 | 0.263 | 0.360 | 0.293 | 0.397 |

오히려 좋은 용어를 가진 문항만 보면 **성공 문항의 합집합이 더 컸다**(25,473편 vs 6,540편).
arXiv 는 여러 절에 동시에 걸리는 논문을 위로 올리므로, 넓은 절은 아래쪽에 논문을 더할 뿐
정답을 밀어내지 않는다. → **절은 줄이면 안 되고 늘려야 한다.** 라벨 실험도 같은 방향이었다
(절 4.0개 R@10 0.933 / 2.92개 0.656 / 2.0개 0.467).

**② "3만 편 코퍼스로 검색어를 채점하면 arXiv 채점을 대신할 수 있다"**

로컬에서 정답을 1등으로 올린 검색어 30개를 실제 arXiv 로 확인하니 **29개가 100등 밖**이었다.
원인은 채점 방식이 아니라 **코퍼스 크기**다. 3만 편에서는 구 대부분이 0~5편에만 걸려
합집합이 너무 작고, 그래서 정답이 자동으로 1등이 된다. → 문서 빈도를 재려면 arXiv 와
비슷한 규모(310만 편)가 필요하다.

## #16 "변환기에 arXiv 어휘를 학습시킨다"는 방향의 유효 범위 검증 🟡

- **발생:** 2026-08-07, 사용자 제안 — "쿼리 변환기를 arXiv 논문의 용어 표현에 익숙해지게
  학습시키면 사용자 쿼리를 그에 맞게 변환할 수 있을 것"
- **왜 검증이 필요한가:** 방향이 맞다면 남은 기간을 전부 여기 써야 하고, 틀리다면 이전
  진단(재정렬·로컬 색인)으로 돌아가야 한다. 이전에 "재정렬이 가장 큰 한 방"이라고 진단했다가
  300문항 재측정에서 틀린 적이 있으므로(#13), 이번에는 실측으로 먼저 가른다.

### 검증 1 — 실패를 원인별로 분해 (dpo 모델, test 300문항)

정답 논문 본문(제목+초록)을 놓고, 모델이 생성한 `abs:"..."` 용어가 **그 논문에 실제로
등장하는지**로 갈랐다. 등장하지 않으면 그 쿼리는 논문에 원천적으로 닿을 수 없다.

| 구분 | 건수 | 비율 | 성격 |
|---|---|---|---|
| ① 성공 (1~10등) | 103 | 34.3% | — |
| ② 후보에 있으나 낮은 순위 (11~100등) | 28 | 9.3% | **재정렬로 회수 가능** |
| ③ 용어는 맞는데 100등 밖으로 묻힘 | 110 | 36.7% | 용어가 너무 흔해 합집합에 파묻힘 |
| ④ 용어가 논문에 하나도 없음 → 도달 불가 | 59 | 19.7% | **순수 어휘 문제** |

- 생성 용어가 정답 논문 본문에 등장하는 비율: **성공 0.61 vs 실패 0.28**.
  실패의 30%는 생성 용어가 **하나도** 논문에 없다.
- 성공/실패를 가르는 것은 **용어의 구체성**이다. 정답 논문에 매칭된 용어 중 가장 희귀한
  것의 문서 빈도(30,000편 기준) 중앙값:

  | 구분 | 문서 빈도 중앙값 | 1,000편 초과 비율 |
  |---|---|---|
  | ① 성공 | **5편** | 5% |
  | ② 11~100등 | 8편 | 0% |
  | ③ 묻힘 | **226편** | 34% |

  성공한 쿼리는 그 논문 근처에만 있는 좁은 표현을 썼고, 묻힌 쿼리는 수백~수천 편에 걸리는
  넓은 표현만 만들었다. **45배 차이.**

→ 여기까지는 사용자 제안을 강하게 뒷받침한다. ③+④ = **56.4%** 가 어휘의 사정권이고,
재정렬의 사정권(② 9.3%)보다 6배 크다. **이전 진단("재정렬이 가장 큰 한 방")은 틀렸다.**

### 검증 2 — 실제 논문 어휘로 검색하면 회수되는가 (arXiv 호출 24회, 3초 간격 준수)

실패 문항 12개를 뽑아, 정답 논문에서 뽑은 구로 직접 검색해 봤다.

| 검색에 쓴 용어 | 예시 | 상위 10등 회수 |
|---|---|---|
| 초록의 **초희귀 구** (문서 빈도 2편) | `through three key components`, `overhead on top` | **12/12 (100%)** |
| 제목의 **진짜 학술 용어** (문서 빈도 5~300편) | `collaborative filtering`, `retrieval-augmented generation` | **2/12 (17%)** |

- **위 줄이 뜻하는 것:** arXiv의 색인·순위는 문제가 아니다. 충분히 구별력 있는 구를 주면
  100% 1등으로 찾아준다. 즉 병목은 전적으로 **쿼리 쪽 어휘**다. (이 자체가 중요한 결론 —
  arXiv API를 버릴 이유가 없다는 뜻이다.)
- **아래 줄이 뜻하는 것 (더 중요):** 정확한 학술 용어를 **알아도** 특정 1편을 상위 10에
  못 올린다. `collaborative filtering`을 쓰는 논문이 arXiv에 수천 편이기 때문이다.
  상위 10에 올리려면 사실상 그 논문에만 있는 표현이 필요한데, 그건 사용자 질문에서
  유추할 수 없다.

### 결론 — 방향은 맞다. 단, 단독으로는 목표에 못 미친다

- **맞는 부분:** 어휘가 최대 병목이라는 진단은 데이터로 확인됐다(56.4%). 어휘 학습으로
  ④(도달 불가 19.7%)는 후보 집합에 들어오게 되고, ③의 일부도 좁은 용어로 개선된다.
- **한계:** 어휘만 정확해져도 **순위**는 해결되지 않는다. 키워드 OR 검색으로 known-item을
  1등에 올리는 것은 구조적으로 불가능에 가깝다.
- **따라서 역할을 나눠야 한다:**
  - **변환기(어휘 학습)** = 정답이 후보 100편 **안에 들어오게** 하는 책임 (재현율)
  - **재정렬기** = 그 후보 중 사용자 의도에 맞는 것을 **위로 올리는** 책임 (정밀도)
  - 어느 하나만으로는 안 되고, 두 개선은 곱해진다.
- **결합 상한 추정:** 현재 R@100 = 0.437. ④(19.7%)가 어휘 학습으로 후보에 들어오면
  R@100 ≈ 0.63. 그 후보를 완벽히 재정렬하면 R@10 = 0.63. 현재 0.343 대비 **약 1.8배**.
  참고로 이 값은 데이터셋의 이론적 상한(#14, easy 0.61)에 근접하므로, 사실상 **이 지표로
  달성 가능한 최대치**에 해당한다.

### 정책이 방향을 지지한다 (docs/ARXIV_API_POLICY.md)

- 메타데이터(제목·초록·저자·ID·분류)는 **CC0**이며 "retrieve, store, transform, and share"가
  명시적으로 권장 항목이다. Kaggle 스냅샷도 CC0. **학습에 쓰는 데 제약이 없다.**
- legacy API는 **3초당 1회·단일 연결** 제한이고, 한도를 넘겨야 하는 용도는 지원팀에 문의하라고
  되어 있다. 그런데 **현재 학습 데이터 생성 방식은 arXiv API로 채점한다** — 후보 쿼리
  하나마다 검색을 1회 하므로, 지난 1회 생성에서 **실측 1,147회**를 호출했다
  (`data/training/candidates.jsonl` 기준: 질문 300개 × 질문당 후보 평균 3.82개).
  데이터를 늘리면 수만 회가 된다. 이건 벌크 수집에 API를 쓰는
  패턴이라 정책 정신에 어긋난다. arXiv는 이 용도로 **벌크 데이터(Kaggle 스냅샷)를 따로 제공**한다.
  → **학습 데이터 생성·채점을 로컬 스냅샷으로 옮기는 것이 정책 준수이자 성능 개선이다.**
- 그 외 준수 현황: PDF·소스 파일을 저장·서빙하지 않음(초록은 CC0 메타데이터라 해당 없음),
  결과에서 arXiv 초록 페이지로 링크함, 후원·보증을 표방하지 않음 — 모두 이미 지켜지고 있다.
  다만 README에 **출처 표기와 비후원 문구**를 넣어야 한다(미조치).

- **상태:** 🟡 방향 확정, 구현 미착수. 단계별 계획은 [PLAN.md 5-3](PLAN.md) 참고.

## #13 프로젝트의 핵심 주장이 서비스 경로에서 한 번도 검증되지 않았음 🟢

- **발생:** 2026-08-07, 코드·결과 전수 점검 중 발견
- **문제점:** 이 프로젝트의 핵심 주장은 **"쿼리를 변환하면 검색이 좋아진다"**인데,
  `runs/`의 arXiv 실시간 평가 결과는 `hierarchical`·`finetuned`·`dpo` 셋뿐이고
  **변환을 안 한 `passthrough` 기준선이 없었다.** 즉 지금까지 증명한 것은
  "학습된 변환 > 계층 변환"(0.15 → 0.35)뿐이고, 주장 자체는 미검증 상태였다.
  로컬 코퍼스에서는 증명했지만(BM25 0.41→0.71) 그건 다른 시스템이라고 스스로 결론 냈다(#10).
- **부수 문제:** test 300문항을 갖고 있으면서 `--sample 40`으로만 쟀다. 40문항 기준
  Recall@10의 95% 신뢰구간은 ±0.15에 달해, "2.33배 향상"이 매우 넓은 오차막대 위에 있었다.
  40개로 제한한 실질적 이유는 arXiv 호출 제한이 아니라 **중단되면 처음부터 다시 해야 했기
  때문**이었다(이어하기 미지원).
- **해결(2026-08-07):** 평가 하네스를 재구축하고 **test 전체 300문항으로 네 모델을 재측정**했다.
  - 검색 결과 논문 ID를 순위대로 전부 저장 → arXiv 재호출 없이 어떤 K로든 재계산 가능
  - 이어하기 + 중간 저장 → 300문항 완주 가능 (모델당 30~60분)
  - 부트스트랩 95% 신뢰구간 출력
  - `evaluation/compare_runs.py` 신설 — 공통 성공 문항 교집합 + 짝지은 유의성 검정
- **결과 (test 300문항 전체, k=100, 네 모델 모두 오류 0건):**

  | 모델 | Recall@10 (95% CI) | MRR@10 | 기준선 대비 | p값 |
  |---|---|---|---|---|
  | **passthrough (기준선)** | **0.167** [0.127, 0.210] | 0.087 | — | — |
  | hierarchical (학습 전) | 0.220 [0.173, 0.267] | 0.132 | +0.053 | **0.050 (불확실)** |
  | finetuned (SFT) | 0.273 [0.223, 0.323] | 0.178 | +0.107 | <0.001 유의미 |
  | **dpo (SFT+DPO, 최종)** | **0.343** [0.290, 0.397] | 0.236 | **+0.177** | **<0.001 유의미** |

  **① 주장은 검증됐다 — 단, 학습한 모델에 한해서다.** 최종 모델은 기준선의 2.05배(p<0.001).
  그러나 **학습 전 계층 변환기는 기준선 대비 p=0.050으로 불확실**하다. 즉
  "계층적으로 변환하면 검색이 좋아진다"는 서비스 경로에서 여전히 증명되지 않았고,
  **검색 보상으로 학습을 시켜야만 유의미한 이득이 생긴다.**

  **② 변환의 가치는 전적으로 한국어에서 나온다 (언어별 짝지은 검정):**

  | 구간 | passthrough | hierarchical | finetuned | dpo |
  |---|---|---|---|---|
  | 영어 (n=147) | **0.327** | 0.259 (p=0.120) | 0.293 (p=0.428) | 0.354 (p=0.543) |
  | 한국어 (n=153) | **0.013** | 0.183 (p<0.001) | 0.255 (p<0.001) | 0.333 (p<0.001) |

  - 한국어는 원본 그대로 던지면 **결과 0건 비율이 88.2%** 다(arXiv가 한글을 색인하지 않음).
    변환이 이 구멍을 메운다: 0.013 → 0.333 (**25배**, p<0.001).
  - **영어에서는 어떤 변환기도 기준선을 유의미하게 넘지 못한다.** 학습 전 계층 변환기는
    오히려 -0.068로 악화 방향이다(p=0.120이라 확정은 못 하지만 이득이 없는 것은 분명).
    영어 질문은 이미 논문 어휘와 겹치므로 변환이 신호를 흐리기 때문이다(#2와 같은 현상).
  - **함의:** 이 시스템의 검증된 가치는 "비전문가 쿼리 개선"이 아니라 **"다국어(한국어)
    쿼리를 arXiv가 검색 가능한 영어 학술 용어로 건너게 하는 것"** 에 있다. 정직하게
    이렇게 서술해야 한다.

  **③ 표본을 늘리자 DPO에 대한 결론이 뒤집혔다.** 40문항에서 SFT→DPO 추가 이득은
  +0.050 (p=0.444) 로 "노이즈와 구분 안 됨"이었으나, 300문항에서는 **+0.070 (p<0.001)
  유의미**로 바뀌었다. 작은 표본이 실제 효과를 놓치고 있었다(2종 오류).
  → **표본 크기가 결론을 바꾼 실례.** 앞으로 모든 판정은 300문항 전체로 한다.

  **④ 난이도별 (기준선 대비 dpo):** easy 0.010→0.150 · mid 0.090→0.230 · hard 0.400→0.650.
  모두 유의미. 단 easy의 낮은 절대값은 시스템 성능이 아니라 과제 한계다(아래 #14).

- **참고:** 결과 원본 `results/test300_*.jsonl`(커밋됨, 재현 가능),
  도구 `evaluation/arxiv_eval.py` · `evaluation/compare_runs.py`.

## #14 단일정답 Recall이 사용자 만족도와 다른 것을 재고 있음 🟡

- **발생:** 2026-08-07, `evaluation/audit_dataset.py`로 평가 데이터셋 감사 중 확인
- **문제점:** 평가 데이터는 "질문 1개 = 정답 논문 1편"(known-item) 구조인데, 실제로는
  질문에 맞는 논문이 여러 편이다. 사람 검증(QWK 0.860)을 거친 등급 정답지로 계산한
  **완벽한 검색기의 이론적 상한**은 다음과 같다.

  | 난이도 | 사용자가 만족할 논문 수(등급 2+, 중앙값) | 단일정답 Recall@10 상한 |
  |---|---|---|
  | easy | **20편** | **0.61** |
  | mid | 12편 | 0.79 |
  | hard | 6편 | 0.90 |

  즉 easy 질문에서 Recall@10이 낮게 나오는 것은 **시스템이 나빠서가 아니라 지표가 원출처
  1편만 정답으로 세기 때문**이다. (게다가 이 상한은 3만 편 코퍼스 기준이고, 실제 arXiv
  250만 편에서는 더 낮다.)
- **영향:** ① 난이도 사이의 점수를 서로 비교하면 안 된다(같은 난이도 안에서 모델끼리만 비교).
  ② 사용자가 체감하는 "검색 결과가 별로다"는 만족도 문제인데, 지금 재는 것은 회수율이라
  **개선 방향을 잘못 잡을 위험**이 있다.
- **근거가 이미 있다:** #2에서 "dense 검색 성능 하락"으로 보이던 현상이 등급 정답지 + NDCG로
  재보니 사라졌다. 변환 쿼리가 원출처 대신 **다른 관련 논문**을 위에 올렸던 것이다.
  그런데 그 등급 평가는 **로컬 코퍼스 경로에서만** 했고, 지금 유일한 공식 기준인
  arXiv 실시간 경로에서는 한 번도 하지 않았다.
- **대응:** 하네스가 난이도별 지표를 낼 때 위 상한을 함께 표시하도록 했다(측정과 과제 한계를
  분리). 근본 해결은 `judge_relevance.py`를 **arXiv 실시간 결과에 적용**해 등급 정답지를
  만들고 NDCG@10을 함께 재는 것. 미착수.

## #15 평가 데이터셋의 hard 난이도에 정답 누수가 있음 🟡

- **발생:** 2026-08-07, `evaluation/audit_dataset.py` 감사
- **문제점:** hard 난이도 질문이 논문 제목을 거의 번역한 수준인 경우가 많다.

  | 난이도 | 제목 내용어 겹침 평균 | 겹침 ≥50% | 논문 고유 방법명 포함 |
  |---|---|---|---|
  | easy | 0.07 | 2% | 2% |
  | mid | 0.12 | 6% | 2% |
  | **hard** | **0.28** | **30%** | **14%** |

  실제 사례: `SequenceMatch`, `CODER`, `GTO` 같은 **논문이 제안한 방법 이름이 질문에 그대로**
  들어 있다. 이러면 '검색'이 아니라 '정답 보고 찾기'가 된다.
- **영향:** hard 난이도 점수가 실제보다 높게 나온다. 실제로 passthrough(변환 없음)조차
  hard에서 Recall@10 = 0.400 인데, 이는 질문이 이미 제목 어휘를 담고 있기 때문이다.
  기존 생성 시 걸어둔 용어 누수 필터(`filter_queries.py`)가 이 유형을 못 잡았다.
- **추가 관찰:** 질문의 90~95%가 물음표로 끝나는 대화체다("~는 무엇인가요?"). 실제 검색창
  입력은 명사 나열형이라, 이 데이터의 점수가 실사용 성능을 덜 대표한다.
- **대응 방침:** 데이터셋을 통째로 다시 만들 문제는 아니라고 판단한다. easy/mid는 누수가
  2~6%로 낮고, 분할 건전성(논문 겹침 0)과 정답 라벨 신뢰도(원출처가 전부 최고 등급)는
  확인됐다. **누수 문항을 태깅해 hard 결과를 해석할 때 함께 보고**하고, 데이터를 새로
  생성하게 될 때 필터를 강화하는 쪽이 비용 대비 효과가 크다. 미착수.

## #12 arXiv HTTPError(429/503)로 평가 문항이 무더기로 유실됨 🟢

- **발생:** 2026-07-28, DPO 평가에서 40문항 중 **7건(17.5%)** 이 오류로 제외됨 → 앞선 실험과
  직접 비교 불가
- **원인 분석(오류 메시지 실측):** 두 종류였고 **쿼리 내용·길이와는 무관**했다.
  - **HTTP 429 Too Many Requests** (4건) — 속도 제한에 걸림
  - **HTTP 503 Service Unavailable** (3건) — 서버 일시 과부하
  - 즉 순수하게 **요청 속도** 문제. 그런데 기존 백오프가 `5→10초`(총 15초)로 너무 짧아,
    arXiv가 회복하기 전에 시도를 다 소진하고 실패로 처리됐다.
- **해결(2026-07-28):** `arxiv_live.py` 백오프 강화
  1. 최대 시도 3회 → **5회**
  2. 대기 시작값 5초 → **15초**, 2배씩 증가(15→30→60→120초)
  3. **429·503이면 대기를 다시 2배**로 (기다리면 대개 풀리는 오류이므로)
  4. **무작위 지연(jitter) 추가** — 여러 요청이 같은 시점에 몰려 재시도하는 것을 방지
- **검증:** 실제로 실패했던 그 7개 쿼리를 그대로 재시도 → **7/7 전부 성공**(총 27초,
  재시도가 거의 필요 없었음). 이후 40문항 평가 재실행.
- **교훈:** 오류를 '결과 없음'으로 삼키지 않고 따로 집계하게 해둔 덕분(#8)에 이 문제를
  발견할 수 있었다. 평가 지표에서 오류를 제외하는 설계도 유지한다.

## #10 로컬 평가 결과와 실제 서비스 경험이 크게 달라 로컬 평가를 신뢰할 수 없음 🟢

- **발생:** 2026-07-23, 사용자 지적 + 미니 평가로 확인
- **문제점:** 로컬 평가에서는 Recall@10 = 0.74였는데, 실제 서비스(arXiv 실시간)에서는 정답
  논문이 상위 30개 안에 든 비율이 4/20 = 0.20이었다. 즉 **로컬 평가 점수가 서비스 성능을
  전혀 예측하지 못한다.**
- **원인:** 로컬 평가와 실제 서비스가 **서로 다른 시스템을 재고 있다.**

  | 항목 | 로컬 평가 | 실제 서비스 |
  |---|---|---|
  | 검색 대상 | 고정 코퍼스 3만 편 | arXiv 전체(약 250만 편) |
  | 검색 방식 | 단어 일치(BM25) + **의미 기반(bge-m3)** | **키워드 전용** |
  | 사용한 쿼리 | `sparse` / `dense` 필드 | `arxiv` 필드(문법이 다름) |

- **해결(2026-07-23):** 서비스와 **같은 조건**으로 재는 하네스 `evaluation/arxiv_eval.py` 추가.
  - 재는 경로: 질문 → 변환기 → **`arxiv` 쿼리 필드** → **arXiv 실시간 검색** → 정답 순위
  - 측정 항목(실패를 유형별로 나눠야 개선 방향이 보이므로): Recall@10/@30, MRR@10,
    **결과 0건 비율**(과잉 제약 실패), **오류 비율**(지표에서 제외해 측정 오염 방지, #8 교훈),
    평균 결과 수(쿼리 폭 진단), 언어별·난이도별 분해
  - 강건성: 디스크 캐싱(중단·재개 가능), 오류/0건 엄격 구분, 실제 검색어 저장, 변환기 교체 가능
- **기준선 측정 결과(test 무작위 40문항, 계층 변환기, 2026-07-23):**

  | 지표 | 값 |
  |---|---|
  | Recall@10 | **0.15** |
  | Recall@30 | 0.20 |
  | MRR@10 | 0.068 |
  | 결과 0건 비율 | 0.025 |
  | 평균 결과 수 | 28.9 |
  | 오류 비율 | 0.0 (측정 오염 없음) |

  - 언어별 Recall@10: 영어 0.20 / **한국어 0.10**
  - 난이도별 Recall@10: hard 0.385 / easy 0.083 / **mid 0.0**
  - **해석:** ① 로컬 평가 0.74와 실제 0.15의 격차가 확인됨(로컬 평가로 서비스 성능을 예측할 수
    없음). ② 오류 0건이므로 이 값은 **오염되지 않은 진짜 성능**. ③ 결과 0건은 2.5%뿐이고 평균
    28.9개가 나오므로, 실패 원인은 '검색이 안 되는 것'이 아니라 **가져온 30개 안에 정답이 없는
    것**(어휘 괴리, #7). ④ hard(정확한 전문 용어 질문)에서 가장 잘 되고 mid에서 최악 —
    변환이 어중간한 표현을 제대로 못 다룸.
- **상태:** 해결 🟢. 이 하네스가 앞으로 모든 개선(학습 포함)의 측정 기준이 된다.

## #9 한 번의 사용자 검색이 arXiv를 3회 호출해 호출 제한에 걸림 🟢

- **발생:** 2026-07-23, 상위 30개 검색 후 재정렬을 시도하자 다음 쿼리가 막힘
- **사용자 가설:** "상위 몇 개를 가져오는지(top-k)를 줄이면 호출이 줄어든다"
- **코드로 확인한 사실(가설과 다름):**
  - arxiv 패키지의 `Client`는 이미 **요청 간격을 자동으로 지킨다**(`__try_parse_feed`가 마지막
    요청 이후 `delay_seconds`(우리 설정 3초)가 안 지났으면 자동으로 대기).
  - `page_size=100`이라 **상위 30개를 가져와도 API 호출은 1회**다. 따라서 top-k를 30에서
    10으로 줄여도 **호출 수는 전혀 줄지 않는다.**
  - **진짜 원인은 한 번의 사용자 검색이 arXiv를 3회 호출하는 구조**다:
    ① 특정 논문 해결기의 제목 검증 1회 ② 변환 후 검색 1회 ③ 변환 전 검색 1회(비교용).
    여기에 3초 강제 대기와 실패 시 재시도가 겹쳐 arXiv가 일시적으로 요청을 막았다(#8과 연결).
- **해결(2026-07-23):** top-k 축소가 아니라 **호출 횟수 자체를 줄였다.**
  1. **변환 전 비교 검색을 기본 해제**(개발용 옵션으로만 남김) → 일반 검색 시 호출 1회.
  2. **특정 논문 해결기는 이미 조건부**였음(언어 모델이 제목을 추정했을 때만 arXiv 검증 호출).
     일반 주제 검색에서는 0회이므로 추가 부담 없음.
  3. **지수 백오프 재시도 도입**(`arxiv_live.py`): arxiv 패키지 자체 재시도는 끄고
     (같은 속도로 계속 두드려 차단을 악화시킴), 실패 시 5초→10초로 대기를 2배씩 늘려 arXiv에
     회복할 시간을 준다.
  4. 성공한 검색 결과만 메모리 캐싱(같은 쿼리 재호출 0초 확인).
  - **검증:** 정상 검색 5건 0.8초, 같은 쿼리 재호출 0.000초(캐시 적중), 서버 HTTP 200.
- **상태:** 해결 🟢 (표기는 아래 제목 참고)

## #8 arXiv 오류가 "검색 결과 없음"으로 가려짐 (0건 오인) 🟢

- **발생:** 2026-07-18, "트랜스포머 최초 논문" 등에서 변환 전/후 모두 "검색 결과가 없습니다"
- **문제점:** 사용자는 쿼리 최적화 문제로 오해했으나, 실측 결과 **arXiv API 오류(HTTPError)** 였다.
  같은 API에 직접 HTTP 요청하면 200 OK인데 arxiv 패키지 요청은 33~48초 후 HTTPError
  (세션 중 arXiv를 과다 호출해 일시적 throttle로 추정). `arxiv_live.py`의 `except: return []`가
  오류를 빈 목록으로 삼켜 '결과 없음'처럼 보였다.
- **영향:** UX 오인 + **recall 측정 오염**(#1 미니평가의 '없음' 중 일부가 실은 오류일 수 있음).
- **해결:** `arxiv_live.search`가 오류를 삼키지 않고 예외를 올림(성공 결과만 캐싱, 재시도 4회).
  앱은 `safe_search`로 (결과, 오류) 구분 → 오류 시 "일시적 오류, 잠시 후 재시도" 표시(결과 없음과
  구분). resolver 호출도 오류 방어. 서버 HTTP 200. (2026-07-18)
- **후속:** arXiv throttle 회복 후 **깨끗한 recall 재측정** 필요(오류 제외한 진짜 값).

## #7 쿼리 변환이 arXiv 키워드와의 괴리를 아직 충분히 못 메움 🟡

- **발생:** 2026-07-18, 여러 주제 검색에서 관찰
- **문제점:** 모델이 아는 도메인의 '특정 논문'은 정확히 짚지만(paper_resolver), **쿼리 변환으로
  얻은 검색 결과는 사용자 의도에 맞는 논문을 잘 못 준다.** arXiv는 키워드 기반이라 논문이 실제로
  쓰는 정확한 표현이 아니면 안 걸리는데, 변환 모델이 만든 학술 용어가 **실제 논문 어휘와 미묘하게
  어긋나** 재현율·정확도가 낮다. 이 프로젝트의 핵심(변환으로 어휘 격차 극복)이 아직 부족한 상태.
- **원인:** 변환 모델이 "그럴싸한" 학술 용어를 파라미터 기억에서 생성할 뿐, arXiv 색인이
  실제로 매칭하는 어휘로 최적화돼 있지 않음. 검색 성공(정답 논문 회수)이 아니라 "학술적으로
  들리는" 것에 맞춰져 있음.
- **개선 아이디어(후보, 우선순위 순):**
  1. **1차 검색 결과에서 어휘 가져오기(의사 적합성 피드백):** 1차 검색 → 상위 논문의
     실제 용어를 뽑아 그 '진짜 어휘'로 쿼리 확장·재검색. 어휘 괴리를 직접 메움. agentic RAG로 확장.
  2. **검색 보상 기반 학습(RL / best-of-N SFT):** 생성 쿼리가 정답 논문을 상위에 회수하도록
     보상(Recall/MRR)으로 학습. "학술적으로 들리는" 게 아니라 "실제로 잘 찾는" 쿼리를 학습.
     - best-of-N 자기개선: N개 쿼리 생성→정답을 가장 잘 회수한 것으로 SFT(STaR류, 저비용).
     - DPO: (더 잘 찾는 쿼리 > 못 찾는 쿼리) 선호쌍 학습.
     - PPO/GRPO: 검색 지표를 직접 보상(강력하나 복잡).
  3. **SFT on (쿼리 → 효과적 검색어) 쌍:** 정답 논문을 실제로 회수하는 검색어를 라벨로 LoRA 학습.
  4. **추론 시 best-of-N:** 학습 없이, 여러 변환 후보를 생성해 실제 검색 결과가 가장 좋은 것 선택.
  5. **의미 재정렬(re-rank):** arXiv 넓은 후보를 bge-m3 임베딩으로 의도와의 유사도로 재정렬
     (키워드 한계를 의미 층이 보정). 쿼리 변환이 아니라 검색 후처리지만 효과 큼.
  6. **arXiv 실제 어휘 사전 만들기:** 코퍼스에서 자주 쓰이는 학술 구를 뽑아 예시·제약으로 제공.
- **해결 진행(2026-07-28): 검색 보상 기반 학습으로 성능 2배 향상**
  - **데이터 생성**: best-of-N rejection sampling. 질문 300개 × 후보 5개 → 실제 arXiv 검색으로
    채점 → 정답 논문을 찾아낸 쿼리만 라벨로 채택. **SFT 84개 / DPO 99개** 확보(확보율 28%).
  - **반증된 대안**: 쿼리 '형태' 다양화(AND 좁히기·제목 검색)는 실패 질문 4건에 적용해도
    **전부 미검색**. 문제는 형태가 아니라 **용어 자체**임을 확인 → 학습의 필요성이 오히려 입증됨.
  - **학습 설정**: 16GB VRAM에 bf16이 약 9.7GB로 들어가므로 **4비트 양자화 없이** 전체 정밀도
    학습(품질 우선). LoRA r=32, 배치4×누적1, 8에폭(144스텝), 학습률 1e-4, 검증 15%.
  - **과적합 발견**: 학습 손실 0.35→0.05로 계속 하락하나 **검증 손실은 에폭3(0.513)이 최저이고
    이후 계속 상승**(에폭8: 0.725). 데이터 84개로는 필연적. → 최종본이 아닌 **checkpoint-54
    (에폭3)** 채택.
  - **결과 (test 동일 40문항, 짝지은 부트스트랩):**

    | 지표 | 학습 전 | 학습 후 | 변화 |
    |---|---|---|---|
    | **Recall@10** | 0.150 | **0.300** | **+0.150** (p=0.030, 유의미) |
    | Recall@30 | 0.20 | 0.35 | +0.15 |
    | MRR@10 | 0.068 | 0.263 | +0.195 |
    | 결과 0건 비율 | 0.025 | 0.0 | 개선 |

    - 언어별: 한국어 0.10 → **0.35**(3.5배), 영어 0.20 → 0.25
    - 난이도별: hard 0.385 → **0.615**, easy 0.083 → 0.25, mid 0.0 → 0.067
    - 개선 7문항 / 악화 1문항
  - **무엇이 달라졌나(실제 사례)**: 학습 후 모델이 논문의 실제 어휘에 더 가까운 용어를 생성.
    예) "약물 개발" → 학습 전 `drug development`(미검색) / 학습 후 `drug discovery`(1등).
    `physics-informed` → `physical laws` 등 미묘한 어휘 교정이 검색 성공으로 이어짐.
- **추가 시도 1 — 확보율 개선(실패, 미채택)**: 후보 다양성이 부족해(요청 5개 → 실제 평균 3.8개)
  확보율 28%에 머무는 문제를 프롬프트로 풀려 했으나 실패.
  - 형태 다양화(AND 좁히기·제목 검색): 실패 질문 4건에 적용 → **전부 미검색**
  - 표현 다양화(이전 후보를 보여주며 "다르게" 요구): 용어가 여전히 동일하고, 온도를 올리자
    모델이 **사고 과정을 출력 자리에 뱉는 부작용** 발생
  - **결론**: 병목은 프롬프트가 아니라 **모델이 그 주제에 대해 아는 어휘 자체**. 두 실패가
    같은 결론을 가리키며, 학습이 정답 방향임을 재확인.
- **추가 시도 2 — DPO 선호 학습(효과 미확인)**: 확보한 선호쌍 99개(고유 질문 46개)로
  SFT 어댑터 위에 이어서 학습(학습률 5e-6, 2에폭, beta 0.1).
  - 학습 자체는 양호: 선호 정확도 **93.75%**, 검증 손실 0.483→0.406(과적합 신호 없음),
    보상 마진 0.556→0.884. 모델 붕괴도 없음.
  - **그러나 검색 성능 개선은 통계적으로 확인되지 않음**(아래 표).
- **세 모델 최종 비교 (test 40문항 전체, 세 모델 모두 오류 0건 — #12 해결 후 재측정):**

  | 모델 | Recall@10 | MRR@10 |
  |---|---|---|
  | 학습 전 | 0.150 | 0.068 |
  | SFT | 0.300 | 0.263 |
  | **SFT+DPO** | **0.350** | **0.284** |

  | 비교 | 변화 | p값 | 판정 |
  |---|---|---|---|
  | 학습 전 → SFT | +0.150 | 0.030 | **유의미** |
  | **학습 전 → SFT+DPO** | **+0.200** | **0.004** | **유의미(가장 강함)** |
  | SFT → DPO | +0.050 | 0.444 | 불확실 |

  - **해석**: 최종 모델(SFT+DPO)은 학습 전 대비 **2.33배**(p=0.004로 가장 강한 유의성).
    다만 DPO 단독의 추가 이득(+0.050)은 40문항 표본에서 노이즈와 구분되지 않는다. 즉
    "DPO가 해롭지 않고 소폭 도움이 되는 듯하나, 확정하려면 더 큰 표본이 필요"가 정확한 결론.
  - 언어별(DPO): 한국어 **0.45** / 영어 0.25 — 한국어에서 특히 강함(학습 전 0.10 → 0.45)
  - 난이도별(DPO): hard **0.692** / easy 0.333 / mid 0.067(여전히 최약점)
- **평가 신뢰성**: 초기 DPO 평가에서 arXiv HTTPError 7건(17.5%)이 발생해 비교가 왜곡됐으나,
  백오프를 강화(#12)한 뒤 **오류 0건으로 40문항 전체 재측정**해 위 수치를 확보함.
- **남은 과제**: 절대 수치가 여전히 낮음(0.39). mid 난이도가 최약점(0.1). 데이터 84개/99쌍은
  둘 다 부족한 규모 → **질문 수를 늘려 데이터를 확대하는 것이 다음 후보**(확보율 개선은 실패로 확인).
- **참고**: `src/rewriter/finetuned.py`(학습 모델을 평가·서비스에 꽂는 어댑터),
  `models/qwen3-4b-query-lora/checkpoint-54`(채택 체크포인트).

## #4 만족도 판정 프로토타입 90질문이 무작위가 아니라 앞 90개 → 언어 편향 ⚪

- **발생:** 2026-07-18, 만족도 평가 프로토타입 표본 점검
- **문제점:** `judge_relevance.py --limit 90`이 `pool[:90]`으로 **앞에서부터** 자름(무작위 아님).
  그 결과 언어 구성이 전체 train(영어 156 : 한국어 144 ≈ 반반)과 달리 영어 54 : 한국어 36
  으로 영어 쪽으로 쏠림. 난이도는 우연히 30/30/30 균등.
- **영향(경미):** 핵심 결과(계층 vs 한번에 유의미)는 90개에서 이미 p<0.05로 확보되어 결론은
  유효. 다만 "한국어에서 특히 도움"이라는 언어별 세부 분석에는 표본이 다소 불리.
- **상태:** 결론에 영향 없어 지켜봄. 판정을 확장할 경우 **앞에서 자르지 말고 언어·난이도

## #5 웹 앱이 로컬 코퍼스를 검색 + 정확한 쿼리를 변환기가 뭉갬 🟢

- **발생:** 2026-07-18, "Attention is all you need" 검색 시 원 논문이 안 나옴
- **문제점(3중):**
  1. (제 설계 실수) 웹 앱이 **평가용 로컬 코퍼스(3만 편)** 를 검색. 사용자 의도는 arXiv 실시간.
  2. 로컬 코퍼스는 2021년 이후만 담아, 2017년 논문(1706.03762)은 구조적으로 없음.
  3. (더 근본) 변환기가 **이미 정확한 쿼리("Attention is all you need")를 일반 용어로
     패러프레이즈**해 원 신호를 잃음. arXiv에서 `ti:"attention is all you need"`는 원 논문을
     1등으로 찾지만, 변환된 `abs:"transformer" AND cat:cs.LG`는 엉뚱한 결과.
- **해결(1·2):** 웹 앱을 **arXiv 실시간 검색으로 교체**(`src/retrieval/arxiv_live.py`, `app.py`).
  로컬 코퍼스는 평가 전용으로 남김. 서비스는 DB 불필요. 검증: 한국어 "가짜 뉴스" 변환 전 0건
  → 변환 후 관련 논문. 서버 부팅 HTTP 200 (2026-07-18).
- **해결(3, 2026-07-18):** arXiv 검색 로직을 실측 분석해 원인·해법 확정.
  - **arXiv 성질(실측):** 따옴표 구(句) 검색이라야 정확 매칭. 넓은 단어를 여러 개 나열하면
    수천 편에 묻혀 타깃이 사라짐(예: 변환된 넓은 키워드 뭉치로는 원 논문 미검색).
  - **반증된 방안:** A(원본+넓은용어 합치기)는 실측에서 실패(희석). LLM에게 arXiv 문법을
    맡기는 프롬프트 방식도 실패(원본 보존 안 함, AND 남발로 0건).
  - **채택:** arXiv 쿼리를 **코드로** `all:"원본" OR abs:"용어1" OR abs:"용어2" ...` 형태로
    구성(`hierarchical.py::build_arxiv_query`, 300자 제한). 원본을 따옴표 구로 보존해 정확한
    제목이 잡히고, 학술 용어는 **전부 따옴표 구로 OR** 연결(각각 따옴표라 희석 없음).
    '정확한가' 감지 불필요. (※ 처음엔 용어 1개만 썼는데, 좁은 구는 arXiv에 드물어 0건이 되는
    문제가 있어(예: "진통제 효능"→"analgesic efficacy" 0건) 전 용어 OR로 바꿔 재현율 확보.)
  - **검증:** "Attention is all you need" → 원 논문(1706.03762) **2등** 검색. 일상어·한국어
    ("가짜 뉴스", "AI가 사람처럼 대화") 정상. 앱이 이 arxiv 쿼리를 쓰도록 교체, 서버 HTTP 200.
  - sparse/dense(로컬 평가용)는 그대로라 로컬 지표에 영향 없음.

## #1 계층 변환기가 입력을 무시하고 프롬프트 예시를 그대로 복사 🟢

- **발생:** 2026-07-17, 쿼리 변환 모듈(hierarchical) 첫 테스트
- **문제점:** Qwen3-4B에 few-shot 예시를 **대화 기록(user↔assistant 턴)** 으로 넣었더니,
  특정 입력("가짜 뉴스 걸러내는 방법" 등)이 실제 입력을 무시하고 첫 번째 예시(image
  captioning)를 그대로 복사해 출력했다. temperature를 0.7로 올려도 결정론적으로 같은
  오답이 나왔다. 반대로 few-shot을 아예 빼면 이 문제는 사라지지만, 가끔 필드 설명 문구를
  그대로 베끼는 다른 실패가 나왔다.
- **원인 추정:** Ollama의 JSON 스키마 강제(구조화 출력)와 문맥 속 완성형 JSON 예시가
  충돌 → 문맥에 있던 유효한 JSON을 그대로 재생성하려는 편향. (Ollama/Qwen3 내부를 확정한
  것은 아님)
- **해결:** few-shot을 대화 기록으로 넣지 않고, **예시 1개를 시스템 프롬프트 안에 설명
  형태로만** 두고("예시 — 입력이 X라면 출력은 Y"), "예시 주제나 설명 문구를 그대로 베끼지
  말라"는 안티카피 지시를 추가. 예시 주제는 평가 데이터에 거의 없는 speech recognition으로
  골라 붕괴 위험을 줄임. → **train 300개 전체 검증: parse_ok 300/300, sparse 검색어 고유
  299/300(유일 중복은 실제 유사 질문), 예시 주제 붕괴 재발 0건, academic_terms 한글 섞임
  0건.** 코드: `src/rewriter/prompts.py`.

## #2 계층 변환 후 dense(의미) 검색에서 영어 질문 성능 하락 🟢

- **발생:** 2026-07-17, train 300개 변환 전/후 비교 실험
- **문제점:** 변환 후 dense 검색에서 **영어 질문 Recall@10이 0.853 → 0.782로 하락**(영어
  156개 중 하락 11건, 개선 0건). 전체 dense 지표가 "통계적으로 불확실"(p=0.215)로 나온
  원인 — 한국어는 개선(0.618→0.750)됐으나 영어 하락이 상쇄.
- **원인 (데이터로 규명):** 하락한 질문들은 **원문이 이미 잘 쓰인 영어 문장**이었고,
  변환기의 dense 검색어는 틀리지 않았지만 더 일반적인 표현으로 바꾼 패러프레이즈였다.
  dense 검색은 원문만으로 이미 정답을 잘 찾고 있었기에(영어 baseline 0.853), 표현이 바뀌면
  임베딩이 정답에서 살짝 멀어져 놓친다. 예: 원문 "running on local devices" → 변환 "local
  hardware without cloud dependency"인데 정답 논문 제목은 "...Running on the Edge".
- **판정:** 버그가 아니라 **구조적 특성** — "변환은 baseline이 약한 곳(한국어,
  easy-영어-BM25)에서 크게 이득이고, baseline이 이미 강한 곳(영어-dense)에서는 원문의
  구체적 신호를 흐려 손해." 데이터셋 분석에서 예측한 그림과 일치.
- **규명·해결(2026-07-18):** 만족도 평가(등급 정답지 + NDCG)로 재측정하니 **하락이 사라짐**
  — dense 변환없음 NDCG 0.663 → 계층 0.681(하락 아님). 즉 "하락"은 **단일 정답(known-item)
  지표의 착시**였다: 변환 쿼리가 정확한 출처 논문 대신 **다른 관련 논문**을 상위에 올려서,
  출처 1편만 정답으로 세는 지표에서는 손해처럼 보였지만 실제 만족도로는 손해가 아니었다.
  → 별도의 dense 검색어 전략 변경(원문+변환 합치기 등) 없이도 만족도상 문제 없음.
  (관련: 만족도 지표가 단일 정답이 못 보던 변환 가치를 드러냄.)

## #3 자유 텍스트 기준선(single_step, HyDE)에서 모델 사고 과정이 출력에 새어나옴 🟢

- **발생:** 2026-07-18, single_step 기준선 배치 실행
- **문제점:** single_step 검색어로 "Okay, let's tackle this query. The user wants to
  convert the Korean phrase..."처럼 **모델의 사고 과정 전체가 검색어 자리에 그대로** 나왔다.
  이대로면 BM25 검색이 무의미해져 기준선 비교가 무효가 된다.
- **원인 (진단 완료):** Qwen3-4B는 추론 모델이라, JSON 스키마 없는 자유 텍스트 생성
  (`generate_text`)에서 최종 답 대신 사고 과정을 content로 출력한다. `think=False`로도
  안 사라졌고, `think=True`면 사고가 별도 채널로 가며 content가 빈 문자열이 됐다.
  계층 변환(hierarchical)은 JSON 스키마 강제라 이 문제가 없었다 — 문제는 스키마를 안 쓰는
  기준선(single_step, HyDE)에만 있다.
- **해결:** 후보 ①번 채택 — single_step은 `{"query":...}`, HyDE는 `{"abstract":...}`
  JSON 스키마로 출력을 강제(계층 변환과 같은 방식). 기준선 성격을 지키려 필드는 결과 1개만
  둠(계층 없음). 검증: "가짜 뉴스" → single_step "how to detect fake news"(깔끔),
  HyDE는 정상 가상 초록 생성. 사고 유출 사라짐. 코드: `src/rewriter/prompts.py`,
  `src/rewriter/baselines.py` (2026-07-18).
