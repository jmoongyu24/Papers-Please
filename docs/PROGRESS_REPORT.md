### 이 평가 지표에는 이론적 상한이 있다 (반드시 함께 읽을 것)

지금 쓰는 지표는 "질문 하나에 정답 논문 딱 1편"을 세는 방식이다. 그런데 실제로는 한 질문에
맞는 논문이 여러 편 있다. 사람이 검증한 등급 정답지로 계산한 **완벽한 검색기의 상한**은
난이도별로 easy 0.61 · mid 0.79 · hard 0.90 이고, 세 난이도를 같은 수로 섞은 지금 데이터에서는
**평균 약 0.77** 이다 (ISSUE #14).

즉 목표 0.70 은 **상한의 91% 를 회수하라는 요구**다. 매우 빡빡한 목표다.
게다가 이 상한은 3만 편 코퍼스를 기준으로 계산한 값이라, 논문 수가 71만 편으로 늘어난
지금 조건에서는 **상한이 더 내려갈 가능성이 크다**(경쟁할 관련 논문이 늘어나므로).

### 남은 격차와 무엇이 막고 있는가

- 확정값 기준 격차: 0.70 − 0.427 = **0.253**
- 오늘의 미확정값 기준 격차: 0.70 − 0.637 = **0.063**

**무엇이 막고 있었는가 (어제까지의 진단)**
정답 논문이 `anomaly detection` 대신 `anomaly segmentation` 이라는 표현을 골랐다는 사실은
질문만 봐서는 알 수 없다. 실패한 검색어의 **63% 가 이런 '거의 맞음'** 이었다. arXiv 키워드 검색은
글자가 정확히 맞아야 걸리므로 한 글자만 달라도 아무것도 안 나온다. 이 벽 때문에 규모를 키우는
여섯 가지 시도가 전부 막혔다 (ISSUE #21).

**오늘 무엇이 바뀌었는가**
글자가 정확히 맞아야 하는 검색을 **유일한 통로로 쓰지 않기로 했다.** 로컬에 논문 71만 편을
의미로 검색하는 두 번째 통로를 만들었다. 이 통로는 글자가 아니라 뜻으로 찾으므로 '거의 맞음'
문제를 그대로 통과한다. 그 결과 **쿼리 변환기를 아예 쓰지 않고 원본 질문 그대로 넣어도**
기존 전체 파이프라인보다 더 잘 찾았다(0.637 대 0.427, 다만 서로 다른 문항 묶음이라 참고값).

**지금 막고 있는 것 (오늘 이후의 진단)**
후보를 얼마나 깊이 가져오는가는 더 이상 병목이 아니다. 깊이를 1000까지 늘리면 후보 상한이
**0.877** 까지 올라가는 것을 확인했고, 로컬 검색은 arXiv 와 달리 깊이를 늘려도 호출 제한이 없다.
남은 병목은 하나다 — **깊은 후보 안에 있는 정답을 재정렬이 위로 얼마나 끌어올리느냐.**

### 날짜별 상세 (오늘 것은 3절에 따로 있다)

**2026-08-10 — 잘못된 결론을 스스로 찾아내 철회한 날**

- 어휘 조회 기능이 **정답 논문 자신의 초록에서 용어를 베껴오고** 있었다. 평가할 때 정답 논문을
  조회 대상에서 빼지 않았기 때문이다 (ISSUE #22). 편향 크기는 Recall@10 **−0.073**(p=0.001),
  조회 성공률은 49.3% 에서 **24.0%** 로 반토막이었다.
- 편향을 걷어내니 어휘 조회 + 상용구 필터 + 깊이 2배를 다 합쳐도 순 기여가 **+0.020, p=0.508**
  로 노이즈와 구분되지 않았다. → **"효과 있음" 결론을 철회했다.**
- 후보 깊이 100 → 200 은 실제 이득이 있었다(0.493 → 0.517, p=0.017). 다만 arXiv 호출이 2배가 된다.
- 조회 코퍼스 확대는 **2만 편에서 포화**함을 대리 실험으로 확인해 보류했다.
- 이틀 동안 방법론 실수를 다섯 번 저질렀고 둘은 잘못된 보고까지 갔다. 재발 방지 점검표 6개를
  ISSUE #23 에 남겼다.
- **정정된 확정 성능: Recall@10 = 0.427** (기준선의 2.7배).

**2026-08-09 — 재정렬 도입, 그리고 결정적 진단**

- 학습으로 좋은 검색어를 뽑아내는 노선이 실패했다(ISSUE #17). 처음 보는 논문의 고유 용어는
  질문만 보고 유추할 수 없어 매칭률이 0.79 에서 0.22~0.33 으로 **악화**했다. 과정에서
  검증셋을 질문 단위로 나누던 누수를 발견해 논문 단위로 고쳤다.
- **결정적 진단**: 실패한 검색어의 63% 가 '거의 맞음'이다(`covid-19 dataset` 대 실제 `covid-19 data`).
  arXiv 는 글자가 정확히 맞아야 하므로 한 글자 차이로도 못 찾는다.
- **교차 인코더 재정렬 도입**(ISSUE #18) — 후보 100편을 원본 질문과의 관련도로 다시 줄 세운다.
  Recall@10 0.343 → 0.467, Recall@1 0.173 → 0.393 (둘 다 p<0.001). **이 기법은 지금도 유효하다.**
- 어휘 조회 부분의 결론은 다음 날 철회됐다.

**2026-08-07 — 프로젝트의 핵심 주장을 처음으로 검증한 날**

- 평가 문항이 무더기로 유실되던 원인을 규명했다. arXiv 서버의 요청 과다·과부하 응답이었고,
  대기 시간을 늘려 해결했다(ISSUE #12). 이후 오류 0건.

**2026-07-23 — 서비스와 같은 조건으로 재는 평가 하네스**

**2026-07-18 — 변환 모듈 완성 · 만족도 평가 기반 · 웹 화면**

  단계에서, 그것도 한국어 질문에서만 일어났다(0.028 → 0.660).
  → 프로젝트를 "비전문가 표현을 학술 용어로 옮기는 것(성능) + 변환 과정을 보여주는 것(사용 경험)"

  사람 32건 블라인드 검증에서 인접 일치 100%, 가중 카파 0.860 으로 판정 신뢰도를 확보했다.

### 3-1. 총괄이 한 일

**① 진단: 여섯 가지 실패가 아니라 하나의 문제였다**

문서 네 개와 소스 58개를 전부 읽고 내린 진단은 이렇다. 성능이 0.45 에서 멈춘 원인은
막힌 시도가 여섯 가지여서가 아니다. **후보를 확보하는 능력 자체가 천장에 닿았기 때문**이다.
arXiv 키워드 검색은 글자가 정확히 맞아야 걸리는데, 실패한 검색어의 63% 가 '거의 맞음'으로
빗나간다. 통로가 하나뿐이면 이 통로가 막힐 때 방법이 없다.

**② 해법 설계: 검색 통로를 둘로 늘린다**

```
질문
 ├─ 채널 A : 쿼리 변환기 → arXiv 키워드 검색   (지금까지 쓰던 길, 글자 일치)
 └─ 채널 B : 로컬 의미 검색 71만 편            (새로 만든 길, 뜻으로 찾기)
        ↓
   순위 합치기 (RRF)
        ↓
   교차 인코더 재정렬
        ↓
   사용자에게 보여줄 10편
```

**③ 논문 71만 편 코퍼스 구축**

- Kaggle arXiv 스냅샷에서 "컴퓨터과학·통계 기계학습·전기전자 계열 + 2021년 이후" 조건으로
  해당하는 논문을 **전부** 뽑았다. **716,183편**, `data/corpus/corpus-cs2021.jsonl`, 1.03GB.
- 평가용 정답 논문 **200편이 전부 이 안에 들어 있음을 확인**했다(200/200).
- **이 71만 편이 정당한 이유**: 기존 평가용 3만 편(`corpus-v1`)이 바로 이 716,183편 모집단에서
  뽑은 표본이다. 표본이 아니라 모집단 전체를 색인하면, 표본을 어떻게 뽑았는지에 따른 왜곡 없이
  실력을 잰다. 건초더미를 24배 크게 만든 것이므로 **더 어려운 조건에서 재는 것**이다.

**④ 큰 색인을 다루는 코드 작성 — `src/retrieval/large_index.py`**

시스템 메모리가 15GB 뿐이라 평범하게 만들면 돌아가지 않는다. 세 가지를 다르게 만들었다.

1. **논문 본문을 메모리에 올리지 않는다.** 파일 안에서 몇 번째 글자에 있는지(위치)만 기록해 두고,
   필요한 논문만 그때 꺼내 읽는다.
2. **FAISS 를 쓰지 않는다.** FAISS 는 벡터 복사본을 따로 만들기 때문에 2.93GB 가 한 벌 더 필요해진다.
   대신 저장된 벡터 파일을 그대로 읽어 계산한다.
3. **임베딩을 조각으로 나눠 계산하고 바로 디스크에 쓴다.** 중간에 끊겨도 이어서 할 수 있다.

**⑤ 임베딩 계산 완료**

- 71만 편 전부 완료. 초당 73편, **163.5분** 소요, 결과 파일 2.93GB.
- `data/embeddings/cs2021.emb.npy` · `cs2021.ids.txt` · `cs2021.offsets.npy`

### 3-2. 검색 개발 담당이 한 일

**① 순위 합치기 부품 — `src/retrieval/fusion.py`**

채널별 결과를 순위 기준으로 합친다. **점수를 그대로 더하면 안 되는 이유**를 코드에 남겼다.
arXiv 채널의 점수는 1÷순위 방식이라 1등이 1.0 인데, 의미 검색의 점수는 코사인 유사도라
0.4~0.8 사이에 몰려 있다. 그대로 더하면 **어느 채널이 옳은가가 아니라 점수 눈금이 큰 쪽이
이기게 된다.** 그래서 점수 대신 순위를 쓴다.

**② 조용한 버그를 하나 잡았다 (중요)**

논문 번호에서 버전 표기를 뗄 때 기존 코드는 `paper_id.split("v")[0]` 을 쓰고 있었다.
이러면 옛날 형식 번호 `solv-int/9611001v1` 이 **`sol` 로 잘린다.**

- 이 방식을 쓰는 기존 코드: `evaluation/arxiv_eval.py:68`, `evaluation/rerank_eval.py:51`
- 새 코드는 끝에 붙은 `v숫자`만 정규식으로 뗀다: `src/retrieval/fusion.py:41-49`

**왜 이게 위험한가**: 이걸 놓치면 arXiv 결과와 로컬 결과가 같은 논문을 서로 다른 논문으로
취급한다. 그러면 **두 채널이 함께 찾아낸 논문일수록 점수가 반으로 쪼개진다.** 가장 확실한
정답이 가장 손해를 보는, 알아채기 어려운 고장이다.

**③ 다채널 평가 하네스 — `evaluation/pipeline_eval.py`**

- **채널별 검색 결과를 따로 전부 저장한다.** 그래서 합치는 방식이나 재정렬 방식을 바꿔도
  검색을 다시 하지 않고 다시 계산만 하면 된다.
- **오류가 난 문항과 결과 0건 문항을 실패(0점)로 세고, 분모는 전체 문항 수로 잡는다.**
  기존 하네스(`arxiv_eval.py`)는 오류 문항을 제외했다. 제외하면 기준선이 부풀려진다.
  **따라서 이 하네스의 숫자와 기존 하네스의 숫자를 직접 비교하면 안 된다.**
- 단위 테스트 작성: `tests/test_fusion.py`, `tests/test_pipeline_eval.py`

**④ 스모크 테스트**

3만 편 색인으로 학습용 앞 10문항을 돌려 코드가 도는 것만 확인했다.
**3만 편 수치는 건초더미가 24배 작으므로 성능으로 읽으면 안 된다**고 로그에 명시했다.

**⑤ 세션 한도로 중간에 끊김**

끊길 때 남긴 말: **색인과 코퍼스가 짝이 맞지 않으면 엉뚱한 논문 본문을 조용히 읽어오는 문제**를
발견해 고치는 중이었다. (스모크 로그에 `경고: 줄 위치 색인은 'corpus-cs2021.jsonl' 용인데
코퍼스로 'corpus-v1.jsonl' 를 받았다` 가 남아 있다.) **이 작업은 미완료다.**

### 3-3. 평가·검증 담당이 한 일

평가 설계가 정당한지 독립적으로 검증하는 임무를 받았고, **세션 한도로 중간에 끊겼다.**
그러나 끊기기 전에 **결정적인 사실을 하나 찾아냈다.** 총괄이 직접 다시 확인해 사실로 확정했다.

**학습용 300문항은 이미 쿼리 변환기 학습에 소모된 데이터다.**

| 확인 항목 | 결과 |
|---|---|
| `data/training/candidates.jsonl` 질문 300개 ∩ `data/eval/train.jsonl` 300문항 | **300 / 300 전부 일치** |
| `data/training/labels_train.jsonl` 질문 300개 ∩ `data/eval/train.jsonl` | **300 / 300 전부 일치** |
| 위 두 파일 ∩ `data/eval/test.jsonl` 300문항 | **0 건 (겹침 없음)** |

**이 사실이 주는 제약**

- 학습용 300문항에서 잰 **채널 A(쿼리 변환기 + arXiv)** 수치는 **부풀려진다.** 변환기가 바로
  그 질문들로 학습했기 때문이다.
- 다만 **채널 B(로컬 의미 검색)** 는 학습이 전혀 개입하지 않은 사전학습 모델을 그대로 쓰므로,
  학습용 300문항에서 재도 편향이 없다. **오늘 잰 0.637 은 채널 B 단독 수치라 이 편향과 무관하다.**
- 시험용 300문항은 변환기 학습에 쓰이지 않았으므로 **최종 판정에는 시험용 300문항을 쓴다.**

**미완료**: `docs/EVAL_PROTOCOL.md` 작성은 **끝내지 못했다.** 아직 파일이 없다.

### 3-4. 오늘의 측정 결과

**조건**: 학습용 300문항 · 채널 B 단독 · 쿼리 변환기 없이 **원본 질문 그대로** · 71만 편 색인

| 조건 | Recall@1 | Recall@10 | 후보 상한 |
|---|---|---|---|
| 의미 검색만, 재정렬 없음 | 0.373 | 0.540 | 0.687 (깊이 100) |
| 의미 검색 + 교차 인코더 재정렬 | 0.513 | **0.637** | 0.687 (상한의 **92.7%** 회수) |

비교: 기존 전체 파이프라인(변환기 + arXiv + 재정렬)은 시험용 300문항에서 Recall@10 = 0.427.
→ **쿼리 변환기 없이도 더 잘 찾는 경로가 생겼다.**
(다만 문항 묶음이 서로 달라 직접 비교는 아니다. 두 묶음의 난이도·언어 구성은 같게 맞춰져 있다.)

**언어별 (재정렬 후)**

| 언어 | 문항 수 | Recall@10 | 후보 상한 |
|---|---|---|---|
| 영어 | 156 | 0.731 | 0.808 |
| 한국어 | 144 | 0.535 | 0.556 |

한국어는 **상한 0.556 의 96% 를 이미 회수했다.** 한국어를 더 올리려면 재정렬이 아니라
**후보를 더 깊이 가져와 상한 자체를 올려야 한다.**

**난이도별 (재정렬 후)**

| 난이도 | Recall@10 | 후보 상한 |
|---|---|---|
| easy | 0.380 | 0.470 |
| mid | 0.610 | 0.670 |
| hard | 0.920 | 0.920 |

hard 가 0.920 인 것을 그대로 믿으면 안 된다. hard 질문의 30% 는 논문 제목과 절반 이상
겹치는 누수가 있다(ISSUE #15). easy 가 낮은 것도 시스템이 나빠서가 아니라 easy 질문에
맞는 논문이 원래 여러 편이기 때문이다(ISSUE #14).

**후보 깊이를 늘렸을 때의 상한 곡선 (의미 검색 단독, 학습용 300문항)**

| 깊이 | 100 | 200 | 300 | 500 | 1000 |

| 후보 상한 | 0.687 | 0.753 | 0.793 | 0.820 | **0.877** |

로컬 색인은 arXiv 와 달리 **깊이를 늘려도 호출 제한이 없고 비용이 거의 들지 않는다.**
질문 300개를 깊이 1000 으로 검색하는 데 1.1분 걸렸다(깊이 100 은 0.8분).

## 5. 다음 우선순위 세 개

### 1순위 — 깊이를 늘린 재정렬의 효과 확인, 그리고 **시험용 300문항에서 재측정**

**무엇을**: 지금 돌고 있는 깊이 300 재정렬 결과를 확인하고, 가장 좋은 깊이를 고른 뒤,
같은 조건을 **시험용 300문항**에서 다시 잰다. 검증 담당의 확인까지 받아 0.637 을 확정으로 바꾼다.

**왜 1순위인가**
지금 가장 좋은 숫자가 **미확정**이다. 이 상태에서 다음 단계를 쌓으면 흔들리는 바닥 위에
집을 짓는 셈이다. 이 프로젝트는 이미 두 번 그렇게 했다가 결론을 철회했다.
게다가 이 작업은 **가장 싸다** — 로컬 검색은 300문항에 1분이고 arXiv 호출이 0회다.
후보 상한이 깊이 1000에서 0.877 까지 확인됐으므로, 남은 질문은 오직 "재정렬이 깊은 후보에서
얼마나 건져 올리느냐" 하나다. 그 답을 확정 없이 추측할 이유가 없다.

**주의**: 깊이를 늘리면 상한은 오르지만 재정렬이 봐야 할 논문도 늘어난다. 상한이 올라도
최종 값이 같이 오르지 않을 수 있다. **상한과 최종 값을 반드시 함께 본다.**

### 2순위 — 두 채널을 합치는 것이 실제로 이득인지 판정한다 (시험용 300문항에서)

**무엇을**: 채널 A 단독 · 채널 B 단독 · 두 채널 합침, 이 세 가지를 시험용 300문항에서
같은 조건으로 비교한다.

**왜 2순위인가**
채널 B 단독이 이미 기존 전체 파이프라인보다 좋아 보인다. 그렇다면 **"쿼리 변환기와 arXiv
키워드 검색을 계속 쓸 이유가 있는가"** 라는 질문이 생긴다. 이 판단이 남은 모든 작업의 방향을
정한다.

- 합치는 쪽이 낫다면 → 두 채널을 다 유지하고, 응답 속도 예산을 arXiv 호출 시간까지 포함해 잡는다.
- 채널 B 단독이 낫다면 → 구조를 크게 단순화할 수 있다. arXiv 호출이 사라지면 3초 간격 제한도,
  호출 실패도, 대기 시간도 없어진다. 서비스 품질이 통째로 좋아진다.

**반드시 시험용 300문항에서 판정한다.** 학습용 300문항에서 재면 채널 A 가 부풀려져
합치는 쪽이 유리해 보이는 **잘못된 결론**이 나온다.

### 3순위 — 서비스 경로와 화면을 새 구조로 옮기고, 만족도 지표를 도입한다

**무엇을**: `app.py` 를 새 검색 구조에 연결하고, 화면을 다시 구성하고(ISSUE #11),
만족도 평가(NDCG)를 실제 서비스 경로에 적용한다.

**왜 3순위인가 (그리고 왜 그렇게 낮지 않은가)**
정확도를 더 올릴 여지가 구조적으로 얼마 없다. 이론적 상한이 약 0.77 이고 지금 미확정값이
0.637 이므로, 남은 여지는 **0.13 정도**다. 그마저도 상당 부분은 시스템이 나빠서가 아니라
**지표가 원출처 논문 1편만 정답으로 세기 때문**에 생기는 격차다(ISSUE #14).

0.02 를 더 짜내는 일과, 사용자가 결과를 믿게 만드는 화면을 고치는 일 중에서는 **후자가
서비스 가치가 크다.** 그리고 지금이 옮기기 좋은 때다. 로컬 색인은 호출 제한이 없어 응답
속도와 후보 깊이를 자유롭게 정할 수 있으므로, 구조가 확정되는 순간 화면 설계도 함께 정해진다.

## 6. 서비스 관점 경고 — 성능 말고 이것들이 서비스를 망친다

### ① 검색 속도

| 단계 | 측정값 | 비고 |
|---|---|---|
| 로컬 의미 검색 (깊이 100) | 질문당 약 **0.17초** | 300문항 0.8분 |
| 로컬 의미 검색 (깊이 1000) | 질문당 약 0.22초 | 300문항 1.1분 |
| 교차 인코더 재정렬 | **후보 수에 비례해 늘어난다** | 질문 하나 기준 시간은 아직 안 쟀다 |

재정렬이 위험 요소다. 깊이 100 일 때 재정렬 대상은 23,748편이었고, 깊이 300 으로 늘리자
64,562편이 됐다. **2.7배다.** 게다가 이 계산은 GPU 한 장에서 일어나므로 **사용자가 여러 명이면
줄을 선다.** 사람은 30초를 넘으면 떠난다. **질문 하나 기준 응답 시간을 반드시 실측해야 한다.**
아직 안 쟀다.

### ② arXiv 정책 위반 상태 (공개 전 필수)

- **arXiv 메타데이터 출처 표기(CC0) 가 화면에 없다.**
- **"이 서비스는 arXiv 의 후원이나 보증을 받지 않았다"는 문구가 없다.**
  arXiv 이용 약관은 "arXiv 가 지원하거나 보증하는 것처럼 표현하지 말 것"을 **명시적으로 금지**한다.
- 지금 로컬에 저장한 것은 제목·초록·논문 번호 같은 **메타데이터뿐이라 저장 자체는 허용된다**
  (CC0). 다만 논문 원문(PDF·소스)을 우리 서버에서 제공하면 안 된다. 사용자는 arXiv 초록
  페이지로 보내야 한다.
- 둘 다 조치에 몇 시간이면 되는데 **안 하면 서비스를 내릴 수 없다.**

### ③ 화면 재구성 미완료 (ISSUE #11)

지금 화면은 요소가 한꺼번에 다 보여 사용자가 흐름을 따라가기 어렵다. 원래 계획은
첫 화면에 입력창 하나만 두고, 검색하면 원본 → 해석 → 변환 검색어를 가로 3단 카드로 보여준 뒤
그 아래에 결과를 놓는 것이다. **미착수.**

### ④ 새 구조가 만든 새로운 위험: "못 찾았다"고 말할 수 없게 된다

기존 arXiv 키워드 검색은 못 찾으면 **결과 0건**을 돌려줬다. 그런데 로컬 의미 검색은
**항상 상위 10편을 채워서 돌려준다.** 아무리 관련 없는 질문이어도 유사도가 가장 높은 10편이
나온다. 이것을 그대로 화면에 뿌리면 **무관한 논문을 추천으로 포장하는 서비스**가 된다.

→ 최소 관련도 기준선을 정하고, 그 아래면 "찾지 못했다"고 정직하게 말해야 한다.
   재정렬 점수를 그 기준으로 쓸 수 있는지 확인이 필요하다. **미착수.**

### ⑤ 배포에 필요한 자원이 커졌다

| 파일 | 크기 |
|---|---|
| 논문 71만 편 본문 | 1.03GB |
| 임베딩 | 2.93GB |
| 재정렬 모델 + 임베딩 모델 + 언어 모델 | 별도 |

시스템 메모리는 15GB 다. 명령어 한 줄로 설치·실행하는 배포 설정(docker)을 만들 때 이 크기를
전제로 잡아야 한다. **지금 배포 설정은 3만 편 시절 기준이라 다시 짜야 한다.**

### ⑥ 시험용 300문항이 마지막 남은 깨끗한 자료다

학습용 300문항은 이미 변환기 학습에 소모됐다. 편향 없이 판정할 수 있는 자료는
**시험용 300문항뿐**이다. 이것을 보면서 설정을 이리저리 바꿔 맞추면 시험용도 오염된다.
**시험용 300문항으로는 "확정" 판정만 하고, 개선 방향 탐색은 학습용에서 한다.**

### ⑦ 짝이 안 맞는 색인이 서비스에서 나면 최악이다

검색 개발 담당이 발견한 미완료 문제다. 색인과 코퍼스가 짝이 맞지 않으면 **엉뚱한 논문의
제목과 초록을 조용히 읽어온다.** 오류가 안 나고 결과도 그럴듯해 보이므로 알아채기 어렵다.
서비스에서 이게 나면 사용자에게 **존재하지 않는 조합의 논문 정보**를 보여주게 된다.
**서비스 연결 전에 반드시 고쳐야 한다.**
